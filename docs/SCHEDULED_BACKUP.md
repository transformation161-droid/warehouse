# Проверяемое расписание backup без дополнительного платного сервиса

Решение для текущей рабочей архитектуры SQLite: **компьютер владельца Windows + существующий Docker Desktop**,
Task Scheduler, персональная manager-учётная запись, проверенный HTTPS. Ничего не устанавливается и не
регистрируется на Amvera этой веткой. Сначала репетиция только на синтетическом стенде/новой копии.

## Сервер и проверка копии

В будущем согласованном v4-стенде явно установить `KSU_BACKUP_EXPORT_DIR=/data/export-work`.
Без этого флага старый endpoint сохраняет лимит16МиБ; для больших БД недостаточно только увеличить число.
Новый путь: один backup одновременно (429 при занятости), работа в отдельном приватном каталоге постоянного
тома, не в32МиБ tmpfs; резерв диска с учётом page_count/WAL и существующих файлов; SQLite Backup API
страницами по128 с deadline120с и фиксированным cap256МиБ; integrity/FK, очищенные сессии только в копии,
потоковый FileResponse и SHA-256. Временная копия убирается после ответа/ошибки, старые backup не трогаются.
Runtime задаёт volume root `/data`; symlink/внешний export directory запрещены. При недостатке места
копия отклоняется, тариф/лимиты автоматически не растут. Backup доступен только manager с CSRF, не viewer/inspector.

Owner-side job (`server.backup_job` в том же проверенном image): HTTPS с проверкой CA/hostname, никаких redirect,
пароль только в stdin, cookie только в памяти; download по64КиБ с лимитом/сроком и проверкой Content-Length/SHA.
Затем **каждый раз** независимое восстановление на новой внутренней копии, полная схема4/integrity/FK и
отпечатки всех16 бизнес-таблиц, отсутствие sessions/attempts. Успех записывается лишь после restore.
Backup/verification-файлы публикуются без перезаписи с fsync; failure не заменяет lastSuccess и не удаляет
прежние файлы. Последняя попытка failed или возраст более26ч означает unhealthy, даже если старая копия существует.
Работа клиента и проверка восстановления выполняются в Linux named volume, не на NTFS/SMB с SQLite WAL.

## Windows — сначала только синтетическая репетиция

Сначала собрать/проверить image и поднять [синтетический стенд](ANDROID_RELEASE_ACCEPTANCE.md).
Чтобы контейнер backup достиг Windows, использовать доступный частный IPv4 из сертификата, а не loopback
внутри другого контейнера. Не отключать TLS verification. `-CaCertificate` — **публичный** rootCA.pem, не ключ.

```powershell
.\tools\Register-OwnerBackup.ps1 -Origin 'https://192.168.1.20:8017' -Image 'ksu-offline:rc' -At '21:00' -CaCertificate 'D:\KSU-private\tls\rootCA.pem' -PlanOnly
```

PlanOnly строит объект ежедневной задачи без файлов/учётных данных/Docker/регистрации. CI проверяет
daily interval1, StartWhenAvailable, IgnoreNew, ограниченный principal и отсутствие секретов в аргументах.
После оценки плана владелец сам запускает ту же команду без PlanOnly **на синтетике**. Диалог запрашивает
персональный demo-manager этого нового стенда, не реальные пароли/токены в чате.

Будут созданы два новых уникальных задания (backup и health через45мин), приватный профиль
`%LOCALAPPDATA%\KSU-Control\backup-jobs\<UUID>` и отдельный volume. Image фиксируется по content ID,
pull запрещён. Manager-пароль сохраняется Export-Clixml/DPAPI только для текущего Windows-пользователя,
не в аргументах, env, конфигурационном JSON, Git или логах. При запуске передаётся контейнеру через stdin.
После успешного восстановления файлы копируются в новый exports-путь профиля, ещё раз проверяется SHA Windows.
Созданный на этот запуск stateless job-контейнер удаляется; volume, успешные/прежние backup не удаляются.
При ошибке контейнер/частичные файлы остаются для приватного разбора, задача возвращает ненулевой код.

Проверка вручную, где `<профиль>` — новый путь, напечатанный регистрацией:

```powershell
& '<профиль>\Invoke-OwnerBackup.ps1' -Directory '<профиль>'
& '<профиль>\Test-OwnerBackup.ps1' -Directory '<профиль>'
```

В Task Scheduler проверить Last Run Result0, History и следующую дату. В owner-status.json ожидается
lastAttempt=success, lastSuccess.restored=true, schema4, bytes/SHA и свежий verifiedAt. После повторной задачи
старый файл остаётся с прежним SHA. Health перепроверяет SHA Windows, возраст и lastAttempt; при ошибке
выводит локальное предупреждение владельцу и ненулевой код, без писем/внешних сервисов.

В коде задан предел2ГиБ на каталог клиента, резерв для download/restore около1,125ГиБ свободного места.
Это не retention: **автоматического удаления старых backup нет**. До достижения предела владелец должен
архивировать копии на одобренный носитель и отдельно согласовать хранение/очистку. Без этого задача остановится
с ошибкой; бесконечное хранение на фиксированном диске не обещается. Windows exports — дополнительная копия,
их объём тоже включить в расчёт места. Эти условия проверяются до рабочего включения.

## Восстановление и доказательства

Job уже выполняет независимый restore при каждой успешной копии. Для полной пользовательской репетиции
выбрать один свежий проверенный файл из exports и запустить `Prepare-Offline-Staging.ps1 -Backend sqlite`
из инструкции PR33 на **новом** стенде с новым deployment ID и loopback8016. Его Source read-only;
не перезаписывать рабочую SQLite или прежние backup. Войти обоими существующими аккаунтами, сверить
записи/фото/миниатюры/отчёты/аудит и receipts, viewer — только свою проекцию. Измерить реальный RTO владельца.
Это owner-local операция; корпоративные файлы не передавать в Codex/GitHub.

Автоматический Docker-прогон выполняет две настоящие HTTPS job для синтетической SQLite порядка150,5МиБ,
каждая independently restored; третья с viewer отвергается, lastSuccess/старые backup и бизнес-таблицы сохранены.
Сервер и клиент ограничены каждый0,5CPU/1ГБ. Unit-тесты проверяют резерв диска, timeout, corruption, stale/failed
health и запрет перезаписи manifest. Это не физическое выполнение Windows Scheduler/DPAPI и не проверка Amvera.
Нативные PG dump/restore, включая настоящий v3 archive → v4, проверяются отдельно. Автоматическое расписание
этого клиента предназначено для SQLite; PG-расписание не заявляется и не заменяет будущую миграцию PostgreSQL.

## Условия допуска

Текущий principal — Interactive: компьютер, этот Windows-сеанс, Docker и сеть должны быть доступны.
StartWhenAvailable догоняет пропущенный запуск после возвращения пользователя, но **не гарантирует RPO24ч
на выключенном компьютере**. До выпуска согласовать окно/ответственного, доступность машины,26ч health,
проверить минимум два фактических запуска расписания на Windows и поведение после пропущенного/ошибочного.
Иначе выбрать одобренный уже имеющийся постоянно доступный узел с этим же клиентом; платный сервис не создаётся.

DB-файлы содержат полную информацию и хеши паролей. DPAPI защищает credential, **не шифрует сам SQLite backup**.
Хранить их только на одобренном приватном/зашифрованном диске (политика владельца), вне Git/облачной синхронизации;
подтвердить защиту Docker volume и Windows exports. Корпоративная политика хранения, объём, RPO/RTO,
реальная копия, доступность Windows/Docker, ротация manager-пароля и свежесть backup остаются воротами выпуска.
Регистрация задачи на production origin требует отдельного разрешения; в этой работе она не выполнялась.

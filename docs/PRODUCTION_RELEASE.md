# Единый кандидат: подготовка рабочего выпуска

Это план будущих действий владельца на существующей Amvera. В этой работе нет merge,
deploy, доступа к рабочей SQLite или изменения ресурсов/настроек Amvera. Все CI-данные
синтетические. Рабочие БД, отчёты миграции, пароли, сертификаты и backup остаются только
у владельца, вне GitHub/Codex, репозитория и каталогов облачной синхронизации.

## Ворота допуска до рабочего окна

1. Владелец записывает приватно текущий SHA/образ и способ его повторной сборки/возврата,
   конфигурацию сервиса, точный путь активной SQLite, домен, роли/назначения и наличие офлайн-
   очередей. Нельзя определять активную БД по первому найденному файлу. Текущее состояние
   реальной Amvera здесь не запрашивалось и не подтверждено.
2. **Подтвердить файловую систему и блокировки `/data` у Amvera.** SQLite WAL не поддерживает
   сетевые FS вроде NFS. Успех на Docker/Linux или один успешный запуск на провайдере не
   доказывает поддержку WAL. Нужны подтверждённый подходящий том, один процесс/реплика,
   отсутствие внешних SQLite-писателей и доступ UID/GID 10001. Если том NFS/несовместим,
   выпуск блокируется до согласованного решения о хранении; нельзя молча менять journal mode
   или включать PostgreSQL/новый платный ресурс. Основание: [SQLite WAL](https://sqlite.org/wal.html).
3. Проверить фактические квоту/потребление/цену в кабинете и права на новый приватный каталог.
   Исторические сведения 5 ГБ и текущая публичная квота 7 ГБ расходятся; ни одно не считать
   текущим фактом. Лимит приложения 2 ГиБ не ограничивает счёт за весь аккаунт.
4. Отключить автодоставку GitHub→Amvera и прежние Actions backup/delivery **до будущего merge**.
   Выбрать ручную доставку согласованного source bundle в существующий сервис. Не передавать
   корпоративные файлы ни в Code/Artifacts, ни в CI. Подтвердить ответственного и окно остановки.
5. Согласовать RPO/RTO и хранение второй копии по разделу ниже. Постоянно включённого внешнего
   узла сейчас нет или он неизвестен. Гарантия ежедневного внешнего backup отсутствует.

Если любой пункт не подтверждён, выпуск остаётся Draft; подготовку копий у владельца можно
продолжать, рабочее приложение не обновлять.

## Воспроизводимая доставка исходников

CI `Production candidate operations` проверяет **head SHA** нового PR, собирает пакет
`production-source-<40-символьный SHA>` и образ **из этого пакета без build arguments**.
Скачать его можно из успешного запуска CI. Либо из чистого checkout утверждённого коммита:

```sh
python -m deploy.release_candidate.bundle --ref <FULL_SHA> --output <NEW_SOURCE_DIRECTORY>
python -m deploy.release_candidate.bundle --verify <NEW_SOURCE_DIRECTORY>
docker build -f <NEW_SOURCE_DIRECTORY>/Dockerfile.offline-release -t ksu-production:rc <NEW_SOURCE_DIRECTORY>
```

Пакет экспортируется из Git objects, а не из рабочей папки. Содержит только Python/SQL/runtime,
зависимости, принятые UI/assets, `.dockerignore`, release Dockerfile, сгенерированный `amvera.yml`
и хеши manifest. Нет `.git`, seed.json, тестовых аккаунтов, БД, backup, ключей или сертификатов.
Manifest — контроль целостности, не отдельная цифровая подпись: источник брать из успешного CI
в одобренном репозитории, `source_sha` сверять с утверждённым SHA. Не добавлять рабочие файлы.

В bundle-only `amvera.yml`: Dockerfile.offline-release, постоянный `/data`, порт 8000.
Только в bundle Dockerfile строка `ARG KSU_BUILD_SHA` получает значение SHA. Остальной
релизный код соответствует коммиту; `/api/health.build` и OCI revision должны совпасть с ним.
Корневой `amvera.yml` репозитория намеренно не переключается на новую доставку автоматически.
Владелец доставляет проверенный source bundle штатным ручным способом в **существующий** сервис
Amvera (его собственный deployment Git/интерфейс), после согласования. Не создавать отдельный
registry, CronJob, VM или второе платное приложение. Данные не входят в build context.

## 1. Заморозить записи и получить независимый backup

Действия ниже — только на компьютере владельца и в кабинете Amvera после разрешения окна.
Не использовать 8003/8018/8019/8020 и ранее принятые тестовые тома для репетиции.

1. Уведомить пользователей, завершить записи и отправить/проверить ожидающие offline receipts.
   Не очищать данные браузеров и неподтверждённые очереди. Если очередь не разрешена, её
   владелец сохраняет её приватно и согласует восстановление до снятия заморозки.
2. Закрыть доступ пользователям и остановить **всех писателей**, приложение и старый backup-
   процесс; не запускать старый и новый runtime одновременно. У провайдера подтвердить, что
   остановленный сервис не возобновит запись автоматически. Записать время заморозки UTC/МСК.
3. Скачать **полный замороженный `/data`** штатно в новый приватный/зашифрованный каталог
   владельца. Сохранить main-файл, `-wal`, `-shm`, `-journal`, если есть, и остальные данные.
   Не скачивать только live main-файл, не делать checkpoint/VACUUM на оригинале. Сохранить
   приватно текущую конфигурацию/образ отдельно от исходников.
4. Из проверенного кода/образа выполнить, подставив действительный путь активной БД относительно
   `/data` (при исходной установке обычно `ksu.sqlite3`, после перехода — `live-v4/ksu.sqlite3`):

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\New-Offline-Backup.ps1 `
  -FrozenDirectory 'D:\KSU-private\frozen-<time>' `
  -DatabaseRelativePath 'ksu.sqlite3' `
  -OutputDirectory 'D:\KSU-private\independent-<time>' `
  -ConfirmedStoppedCopy -Image 'ksu-production:rc'
```

Восстановление WAL выполняется только на приватной Linux-копии в новом volume; входной bind
read-only. Скрипт не контактирует с Amvera и не останавливает её сам. Проверить SHA и
`original_files_unchanged=true`, integrity/FK и версию схемы. Хранить frozen-набор и независимый
backup раздельно. Само присутствие файла или зелёный HTTP health не является проверкой restore.

## 2. Обновить схему на отдельной копии и проверить восстановление

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\Prepare-OwnerRelease.ps1 `
  -Source 'D:\KSU-private\independent-<time>\ksu-backup.sqlite3' `
  -OutputDirectory 'D:\KSU-private\prepared-v4-<time>' `
  -ConfirmedClosedBackup -Image 'ksu-production:rc'
```

Нужен заранее загруженный образ, собранный из согласованного bundle. Скрипт фиксирует его
content ID, запрещает pull, работает без сети и создаёт новый Linux volume/приватный output.
Не использует NTFS/SMB для SQLite WAL. Оригинал смонтирован read-only; существующий output
не перезаписывается. Образ по умолчанию работает UID 10001. Контейнер/том подготовки остаются
для разбора и удаляются владельцем только отдельно после проверки, не командой prune.

В output: `ksu.sqlite3`, `migration-report.json`, `restore-report.json`. Требования к отчётам:
`source_unchanged=true`, `schema_after=4`, `all_original_tables_preserved=true`,
`restored=true`, `integrity_fk=ok`, `business_tables_identical=true`, совпадающие SHA файла.
Миграция узнаёт только известные схемы 0/1/2/3/4, неизвестную или частичную отвергает.
Для каждого ранее существовавшего бизнес-стола сравниваются число строк и хеш содержимого;
после миграции проверяются все 16 таблиц, включая пользователей и хеши паролей, назначения,
records/акты, BLOB-фото/миниатюры, audit и receipts. Сессии/попытки входа очищаются **только
в копии**, поэтому после перехода нужен новый вход. Пароли не меняются, viewer автоматически
не создаётся. Существующий v4 также проходит копирование и проверки, без добавления данных.

Потребуется свободное место минимум `4 × размер исходного standalone backup + 128 МиБ`
для миграции; не планировать весь процесс вплотную к минимуму — frozen-набор, независимый
backup, Docker volume и экспортированная v4-копия занимают дополнительное место. Независимый
restore требует ещё до двух размеров копии; инструменты проверяют резервы. Все файлы и
табличные отчёты приватны, не вкладывать их в PR/чат. В GitHub достаточно отметки владельца
«copy migration/restore PASS», без содержимого и реквизитов корпоративной БД.

Если текущую схему/путь не удалось распознать или исходный хеш изменился, остановиться.
Нельзя применять `schema.sql`, `init-demo`, ORM/bootstrap или DDL прямо на рабочей базе.
При сбое подготовки старое приложение может быть возобновлено со **старым неизменённым**
набором; подготовленную копию тогда считать устаревшей и перед следующей попыткой повторить
заморозку/backup. Пока копия готовится, новые записи на старой базе не допускаются.

## 3. Обновить существующую Amvera

После отдельного go/no-go владельца, пока записи закрыты:

1. Сохранить исходный `/data/ksu.sqlite3` и журналы нетронутыми. Загрузить **только** подготовленную
   закрытую v4 в новый приватный `/data/live-v4/ksu.sqlite3`; сверить SHA после загрузки.
   Не загружать её в Code/Artifacts. Проверить владельца/права 10001:10001 и RWX на `/data`
   для lock/release-work/backup-v4. Runtime не исправляет chmod/chown и не мигрирует при старте.
   Убедиться в дисковом резерве с учётом обеих БД, старых backup, recovery-файлов и приложения.
2. В существующем сервисе задать точную конфигурацию, сохранив старую приватную копию настроек:

```text
KSU_DB=/data/live-v4/ksu.sqlite3
KSU_ORIGIN=https://<existing-production-host>
KSU_OFFLINE_MODE=off
KSU_OFFLINE_DEPLOYMENT_ID=<stable-production-32-lowercase-hex>
KSU_OFFLINE_USER_IDS=<approved-existing-inspector-IDs-or-empty>
KSU_VIEWER_ACCESS=off
KSU_BACKUP_EXPORT_DIR=/data/export-work
KSU_LOCAL_BACKUP_MODE=daily
KSU_LOCAL_BACKUP_DIR=/data/backup-v4
```

`KSU_OFFLINE_MODE=off` отключает offline-пакеты/приём, но оставляет online и receipts.
Для уже существующей production offline-установки сохранить её deployment ID; для первого
рабочего offline-контура создать новый **один раз**, отличный от синтетики/8020, и хранить
при обновлениях/откатах вместе с тем же HTTPS origin. Не переносить staging ID/пароли.
Если viewer уже используется в production, согласовать его короткое отключение в окне;
возврат только `KSU_VIEWER_ACCESS=enabled` с проверенными персональными назначениями.
`KSU_DATABASE_URL`/PG-флаги/старый `KSU_DB` не должны случайно переключить backend.
HTTPS терминирует существующая Amvera; локальные staging TLS-ключи не загружать. Не снижать
проверку TLS/CSRF/secure cookie и не менять origin для обхода ошибок. Одна реплика/worker.

3. Ручная сборка/перезапуск согласованного bundle в существующем сервисе. Убедиться, что старый
   runtime остановлен, build завершён, `/api/health` через штатный HTTPS отвечает 200,
   `data=application`, `build=<approved SHA>`, `offline=off`. До допуска записей дождаться
   `localBackup.healthy=true` и `lastAttempt=success`; это отдельная проверка backup, не liveness.
4. Короткая проверка **конкретного переноса данных** владельцем: вход существующим manager и
   inspector, выбранный старый объект/акт/фото/миниатюра, PDF/XLSX и audit; наличие прежних
   receipts и отсутствие повторной отправки уже подтверждённых операций. Сверить контрольные
   количества/хеши приватного отчёта до допуска записей. Это smoke миграции, полную UI/PWA-
   приёмку 8020 не повторять. Не создавать демонстрационные данные в рабочей базе.
5. Включить viewer с проверенными site ACL и подтвердить чтение своего объекта/фото/отчёта,
   отказ для чужого объекта и записи. До снятия заморозки выполнить owner-side backup export/
   restore на согласованное приватное хранилище вне Amvera. Лишь затем открыть online-записи.
6. По отдельному решению включить `KSU_OFFLINE_MODE=pilot` и согласованный список inspector
   IDs; не `*`. Контролировать receipts/конфликты, 5xx, место, первый плановый backup. Режим
   off остаётся быстрым выключателем offline без возврата старой схемы.

## Откат без потери новых записей

| Когда обнаружена ошибка | Безопасное действие |
| --- | --- |
| До запуска новой версии / до разрешения любых новых записей | Остановить новый runtime; вернуть сохранённый старый образ/конфигурацию, указать **старый неизменённый** путь БД. Убедиться, что после заморозки нигде не было бизнес-записей; новый v4-набор сохранить отдельно для разбора. |
| После разрешения записей, offline commits или изменения ACL/пользователей | Закрыть доступ и новые записи. Сначала оставить **тот же v4-код и текущую v4-базу**, выключить offline/viewer флагами. Сделать новый frozen-набор и независимый restore. Исправление/возврат возможны только на совместимую v4-версию с сохранением новых данных, истории и receipts. |
| v4 runtime не стартует / повреждение хранилища | Остановить автоматические рестарты/писателей, сохранить все main/WAL/journal и текущую конфигурацию. Восстановление делать на новом пути, отдельно проверить; определить записи после точки backup и согласовать их восстановление/потерю. Не накатывать старую v0–v3 базу поверх новых записей. |

После первого перехода предыдущая **рабочая** версия может быть v0–v3, несовместимая с v4.
У №35 есть совместимый v4-код, но он не имеет всех операционных исправлений этого кандидата;
его использование как запасного варианта потребует собственной проверенной сборки и одобрения.
Нельзя просто указать старому бинарнику новую SQLite: runtime/автомиграция старых веток могут
изменить её. Не использовать `git revert`, data reset, удаление receipts или общий `docker prune`
как способ восстановления данных. Сохранять тот же production deployment ID при совместимом
откате; иначе старые офлайн-очереди нельзя считать безопасно продолженными.

## Backup при выключенном Windows: простой вариант и его предел

**Предлагается:** один существующий Amvera-контейнер, SQLite на подтверждённо подходящем `/data`,
ежедневная локальная проверяемая копия + штатные backup провайдера, если они уже включены в
оплаченный тариф + вторая приватная копия на Windows при доступности компьютера и перед каждым
обновлением. Новые ресурсы/платные услуги и GitHub-расписание для корпоративной БД не нужны.

`KSU_LOCAL_BACKUP_MODE` по умолчанию **off**; `daily` включает daemon внутри runtime. Первый
запуск/пропуск более 24ч догоняется при старте, затем проверка расписания раз в минуту;
после ошибки повтор через 15мин. Это не отдельный CronJob и не дополнительная реплика.
Каждая SQLite snapshot-копия проходит независимый restore, schema4/integrity/FK, SHA и
fingerprints всех 16 бизнес-таблиц, без живых сессий. Только после успеха обновляется статус
и удаляется самая старая **собственная проверенная** копия до двух экземпляров. Предыдущая
успешная копия защищена; старые/чужие/неподтверждённые файлы не удаляются. Экспорт и локальная
копия используют общий semaphore, несколько писателей backup не расходуют резерв одновременно.

Резерв перед запуском — `3 × 256 МиБ + 128 МиБ = 896 МиБ`, проверяется и физический free,
и занятость всего `/data` относительно лимита 2 ГиБ. Это позволяет БД вырасти во время
snapshot. При лимите БД 256 МиБ две постоянные локальные копии занимают до 512 МиБ.
Проверять также размер исходной/старой базы, WAL, старых backup и export-work. Если резерв
не помещается, новая копия не создаётся, предыдущая не удаляется, расширение диска/тарифа
не запрашивается. Runtime продолжает обслуживать приложение, а backup health становится false.
После аварийного kill могут остаться `.local-work-*`; не удалять автоматически неизвестные
файлы. Владелец разбирает их после остановки backup/писателей и проверки нужных копий.

`/api/health.localBackup.healthy` означает: последняя попытка успешна, независимый restore
прошёл, файл существует/размер соответствует, возраст не более 26ч. На каждом health-запросе
полный файл повторно не хешируется; SHA полностью проверяется при создании/restore. Health
приложения остаётся 200 при неудаче backup — не считать зелёный liveness доказательством
свежей копии. Полный приватный статус — `/data/backup-v4/status.json` и verification manifests.
Без внешнего узла нет независимого автоматического наблюдателя: назначенный владелец проверяет
backup health ежедневно, после простоев/перезапусков и перед обновлениями. Автоматические
сообщения/новые сервисы здесь не подключаются.

По [документации Amvera backup](https://docs.amvera.ru/applications/backups.html) автоматические
копии доступны с «Начальный Плюс», хранятся за последние два дня; подготовленная ссылка на
скачивание доступна два часа. Владелец должен проверить, включено ли это **уже** в его текущем
сервисе, какова точка восстановления и можно ли восстановить выбранный frozen-набор. Не
считать provider copy проверенным независимым SQLite restore или защитой от потери аккаунта.
Смена тарифа не согласована и не выполняется.

Публичный [прайс](https://docs.amvera.ru/general/price.html) на момент подготовки: «Начальный
Плюс» 0,5 CPU / 1 ГБ / 7 ГБ SSD, около 490 ₽ за 720ч, сверхквотный диск 35 ₽/ГБ/720ч;
учитываются Code, Artifacts, Data и репозиторий. Это ориентир, **не** подтверждение счёта или
жёсткого бюджетного стопа. Старые сборки/репозиторий тоже занимают место. Никакой ресурс не
создан, лимиты не повышены; очистка провайдера и расходы требуют решения владельца.

[Windows-задачи](SCHEDULED_BACKUP.md) сохраняются как дополнительный внешний pull. Interactive
principal требует включённого ПК, входа владельца, Docker и сети. StartWhenAvailable догоняет
пропуск, но не делает выключенную машину доступной. DPAPI защищает пароль, не сам backup;
нужен согласованный защищённый диск/носитель и место под Linux volume **и** Windows exports.
Две новые action definitions включают process-only Bypass; существующие зарегистрированные
задачи автоматически не изменятся. После разрешения владелец перерегистрирует их из новой
версии: сначала записать и отключить точные старые backup/health task names, сохранить их
профили/копии, проверить `-PlanOnly`, зарегистрировать новую пару с новым профилем, выполнить
backup+health, затем убрать старые задания отдельно. Не запускать старую и новую пару параллельно.

**Оставшийся риск:** две локальные копии находятся на том же томе; штатные provider backups
в том же аккаунте. При потере тома/аккаунта восстановление ограничено последней доступной
внешней копией на Windows/носителе, её возраст может быть больше суток. Обещать RPO24ч для
такой аварии нельзя. До критичной эксплуатации владелец либо принимает этот конкретный
RPO/процесс частного копирования, либо подтверждает уже имеющийся постоянно включённый
корпоративный NAS/сервер для того же проверяемого pull. Новый платный узел здесь не создаётся.

## Проверки кандидата и остающиеся риски

Новый CI проверяет сохранность принятого кода/ancestry, миграции синтетических v0 и настоящего
артефакта v3 в v4, API ACL/запреты viewer и права manager/inspector, ошибки backup/disk/restore,
native Windows task argv и запуск обоих дочерних PowerShell при Restricted-контроле. Отдельный
job строит source bundle, запускает настоящий release image (в том числе его SQLite 3.40.1 и
SQL authorizer), проверяет старт/рестарт/догон пропуска/ротацию/ошибку диска. Нет повторного
визуального/PWA тестирования и нет корпоративных данных в artifacts. Новые ресурсы — только
временные синтетические контейнеры CI, не хостинг.

Реальная миграция/restore, права UID/FS/WAL, доступный объём, способ ручной доставки и отключение
внешних автосвязей остаются проверками владельца. RTO измеряется на его копии, не выводится
из CI. Ресурсный предел 0,5 CPU / 1 ГБ проверяется для backup в образе, но не доказывает любую
будущую нагрузку и рост базы. При достижении 256 МиБ требуется отдельное решение о хранении.
Короткий перечень действий и решений: [OWNER_RELEASE_CHECKLIST.md](OWNER_RELEASE_CHECKLIST.md).

Между пилотом и №30 большая цепочка, а не три независимых небольших патча. Поэтому нельзя просто
направить Amvera на ветку №30. Здесь отдельный Dockerfile и entrypoint, прежние права планирования:
руководитель планирует, инспектор завершает назначенный выезд, но не создаёт/переносит/отменяет план.
Серверные проверки чужих объектов/записей, CSRF, сессий, optimistic locking и аудит сохраняются.
Существовавшие функции инвентаризации сохранены ради совместимости; их развитие не входит в релиз.

В образ не копируются `server/seed.json`, `experiments/`, тесты и исходный демонстрационный интерфейс.
Нет регистрации пользователей, известных паролей, публичной выдачи пакетов или тестового сброса.
Существующие аккаунты и записи, даже если их имена содержат «ДЕМО», **не переименовываются и не удаляются**.
Офлайн-HTML/JS доступны как оболочка входа; данные выдаются только после авторизации и проверки ACL.

## Конфигурация кандидата

| Переменная | Значение / правило |
|---|---|
| `KSU_OFFLINE_MODE` | Обязательно `off`, `staging` или `pilot`. Сначала `off`. |
| `KSU_OFFLINE_DEPLOYMENT_ID` | Обязательный случайный 32-символьный hex; уникален для staging и production, стабилен при рестартах и обновлениях. Не пароль. |
| `KSU_OFFLINE_USER_IDS` | Явный список существующих **ID** инспекторов через запятую, не логины и не `*`. В `off` может быть пустым. |
| `KSU_ORIGIN` | Точный HTTPS origin без пути и завершающего `/`. |
| `KSU_DB` | Явный путь новой подготовленной копии под `/data`; не менять исходный `/data/ksu.sqlite3`. |
| `KSU_DATABASE_URL` | На рабочей SQLite-установке должен отсутствовать. Только отдельные PG-стенды используют restricted runtime DSN. |
| `KSU_SCHEMA_MODE` | `verified`: runtime не выполняет DDL. Явный инструмент миграции запускают отдельно с другим значением. |
| `KSU_OFFLINE_VISIT_LAB_ID`, `KSU_BOOTSTRAP_DEMO` | Отсутствуют. Lab/bootstrap-флаги отвергаются. |

Новый entrypoint требует /data mount и права отдельного непривилегированного пользователя, одну реплику,
проверенную схему v3 и идентификатор сборки в образе. Не создаёт БД при пропавшем mount и не исправляет
права/схему при запуске. Проверяется не только список таблиц v3, но и ожидаемые определения таблиц/триггеров.
Сессии HTTPOnly/Secure/SameSite=Strict, HTTPS и исходные проверки Origin обязательны.
`/api/health` возвращает build SHA и режим без данных/секретов. Старый запуск без release env сохраняет старый health API.

`KSU_OFFLINE_MODE=off` запрещает новые пакеты и отправки с mutationId, но сохраняет онлайн-работу,
авторизованное чтение receipts и локальные данные. Уже committed акт подтверждается клиентом через receipt
даже после выключения функции. Для частично отправленного выезда очередь сохраняется до решения оператора.
Смена deployment ID, origin или очистка профиля не являются способом отключения функции.

## Безопасная независимая SQLite-копия — только на компьютере владельца

Не использовать одиночный main-файл из работающей SQLite: последние commit могут быть в WAL.
Не использовать старый HTTP-backup для больших БД: его прежний лимит 16 МиБ в этой работе не увеличивается.
Новый механизм принимает **полностью выгруженную замороженную папку** после подтверждения остановки всех
писателей. Amvera не опрашивается и не останавливается этим кодом. До будущей операции владелец отдельно
согласует окно и способ выгрузки полного `/data`, включая `ksu.sqlite3-wal`, `-shm`, `-journal`, если они есть.
Хранить нетронутые исходные файлы и прежние резервные копии отдельно от staging.

1. На Windows загрузить полный замороженный каталог в приватную папку вне Git/OneDrive/общих дисков.
2. Образ кандидата должен быть собран/загружен **до** подключения корпоративной копии. Никаких сетевых загрузок из образа.
3. В локальном Docker запустить `server.release_backup` с входным каталогом read-only и **новым** выходным каталогом.
   Он копирует файлы в приватную рабочую папку, восстанавливает WAL только на копии, применяет SQLite Backup API,
   проверяет integrity/FK и неизменность всех входных файлов. SHM на копии строится заново, исходный не меняется.
4. Полученный standalone backup и `.verification.json` оставить у владельца. Сессии/попытки входа в backup очищены;
   пользователи, хеши паролей, записи, фото, миниатюры, аудит и прочие бизнес-таблицы сохраняются.
5. `server.release_schema inspect` открывает **эту независимую копию** read-only, печатает только версию/имена таблиц.
   Версия 0 = пилот без decision_records, 1 = реестр, 2 = версии решений, 3 = offline. Это классификация
   структуры, не `PRAGMA user_version`; неизвестная/частичная схема блокирует дальнейшие действия.
6. `prepare-copy --closed-backup` создаёт **новый** каталог и обновляет только внутреннюю копию до v3.
   Сравнивает отпечатки всех исходных бизнес-таблиц. Вход неизменен, повторное использование назначения запрещено.
   Частичный результат при ошибке не запускать; сохранить для приватного разбора, выбрать новое назначение.

Пример PowerShell без установки Python: новый выходной каталог **ещё не должен существовать**.
SQLite recovery, Backup API и hard links выполняются в новом Linux Docker volume, а готовый
standalone-файл копируется на Windows с проверкой SHA-256. Поэтому WAL не открывается на NTFS/SMB.

```powershell
.\tools\New-Offline-Backup.ps1 -FrozenDirectory 'D:\KSU-private\frozen-data' -OutputDirectory 'D:\KSU-private\backup-new' -ConfirmedStoppedCopy
```

Скрипт не скачивает данные и не обращается к Amvera. Требует заранее собранный `ksu-offline:rc`,
отвергает существующее назначение и запись внутри Git, назначает приватный ACL только новому каталогу.
Готовые backup, отчёт и Docker volume сохраняет; автоматического удаления нет. В отчёте
проверить `original_files_unchanged=true`, schema_version, backup_bytes/hash. Не использовать
частичный результат при ошибке. Подтверждённые файлы брать только из нового выходного каталога.

Проверка неизменности обнаруживает изменение входа, но не доказывает остановку удалённых писателей:
подтверждение владельца и полная замороженная выгрузка обязательны. Инструмент не использовать прямо на томе Amvera.
SQLite cap 256 МиБ не повышен. Учитывать WAL, отдельные backup, временную копию и резерв диска: миграция
проверяет минимум `4 × размер БД + 128 МиБ`, recovery `3 × размер входных файлов + 128 МиБ`.
Это минимумы инструмента, не расчёт полной ёмкости production.

## Изолированный staging Windows/Docker

Это подготовленный путь для владельца; корпоративный staging в Codex не запускался.
Docker Desktop/Linux и доверенный локальный сертификат устанавливает владелец. Сертификат для
`localhost`, `127.0.0.1` (например, mkcert с локально установленным CA); приватный CA-ключ никому не передавать.
Не нажимать «продолжить небезопасно». Стенд публикуется **только на loopback**, по умолчанию 8016; 8003 запрещён.
Точный перечень инспекторских ID владелец получает из своей приватной копии, без пересылки базы или списка сюда.

Сборка на исходниках проверенного SHA, ещё без данных:

```powershell
$sha=git rev-parse HEAD
docker build -f Dockerfile.offline-release --build-arg "KSU_BUILD_SHA=$sha" -t ksu-offline:rc .
```

Затем из корня репозитория:

```powershell
.\tools\Prepare-Offline-Staging.ps1 -Source 'D:\KSU-private\backup-new\ksu-backup.sqlite3' -Backend sqlite -UserIds '<существующий-ID-инспектора>' -CertificatePath 'D:\KSU-private\tls\cert.pem' -KeyPath 'D:\KSU-private\tls\key.pem'
```

Скрипт создаёт новый UUID-каталог `%LOCALAPPDATA%\KSU-Control\private-staging`, отдельную копию,
контейнер и deployment ID; исходный файл read-only, проверяется его SHA. Ничего не перезаписывается и
автоматически не удаляется. Runtime получает только новый Linux named volume `/data` (SQLite WAL не на NTFS/SMB bind); env-файлы администратора находятся отдельно
в `secrets/` и в контейнер приложения не монтируются. Приватный migration-report копируется владельцу через Docker cp. Для приватной папки задаётся ACL текущего владельца;
если политика Docker Desktop запрещает доступ — исправление согласует владелец, скрипт не расширяет ACL исходной копии.
Лимиты приложения 0,5 CPU / 1 ГБ, readonly rootfs, tmpfs 32 МиБ, без capabilities.
`stage.json` содержит `ready=false`: сообщение о старте контейнера **не означает успешной приёмки**.

Для отдельного PG-регрессионного стенда скрипт принимает доверенный `.ksubackup` и `-Backend postgres`.
Использует заранее загруженный pinned PostgreSQL 17 image, новый volume/контейнер, новые сервисные пароли,
не публикует порт БД. Admin DSN существует только в одноразовом restore helper; runtime не получает superuser.
Это не предложение переносить рабочую SQLite в PG при данном выпуске. Все существующие PG, особенно 8003, не затрагиваются.

Открыть `https://127.0.0.1:8016/`; проверить вход существующего руководителя и инспектора, прежние объекты,
количество/состав записей, видимость по ACL, две известные фотографии/миниатюры, историю и XLSX/PDF.
Сверить исходный приватный migration-report: все старые таблицы сохранены. Затем:

1. Руководитель назначает **проверочный выезд только в staging-копии** разрешённому инспектору.
2. Инспектор открывает `/offline-visit/`, входит своей существующей учётной записью, видит «Проверочный стенд».
3. Задаёт отдельную локальную фразу, загружает выезд и пакет, выключает сеть в DevTools, заполняет ответы,
   два нарушения и два фото. Дожидается «Сохранено на устройстве», затем «Ожидает отправки».
4. Закрывает/открывает Chrome без сети, разблокирует той же фразой: ответы/фото/очередь на месте.
5. Возвращает сеть, при необходимости входит тем же инспектором; отправляет до «Принято сервером».
   Руководитель сверяет акт, два нарушения, фотографии, статус выезда и историю, повтор не создаёт дубли.
6. Конфликт испытывает на **другом** проверочном выезде: руководитель меняет план после загрузки;
   клиент показывает «Конфликт», ничего автоматически не перезаписывает, локальные данные остаются.
7. Останавливает/запускает **только staging-контейнер**, повторяет входы/просмотр. Исходный backup и рабочая Amvera не меняются.
8. Отдельно фиксирует количество строк, контрольные фото, build SHA, время restore и результат.
   В GitHub передаёт только обезличенный pass/fail и агрегаты, никаких выгрузок/скриншотов с данными.

Статус `ready=false` менять вручную только после выполнения всего перечня; это приватная запись владельца,
не автоматическое разрешение на production. Команды остановки конкретного созданного контейнера печатает launcher.
Удаление контейнеров, volume, профиля браузера и backup автоматически не выполняется.

Android: физическая приёмка PR №30 уже принята 09.11.2026. Новую оболочку/группу/отключение нужно проверить
отдельно на синтетике. Для устройства loopback Windows недоступен: использовать только отдельный синтетический
стенд по частному LAN-адресу, сертификат с SAN этого адреса и доверенный CA на Android. Не публиковать
корпоративную staging-копию в LAN/интернет этим скриптом. Телефон и Windows в одной сети; CA-ключ не переносить.
Сохранять origin неизменным на всём испытании. Прежняя инструкция этапа 2 описывает локальный HTTPS подробнее,
но её demo-launcher не использовать для корпоративной копии.

## Будущий план Amvera — выполнять только после отдельного согласования

1. Зафиксировать полный SHA/образ кандидата, фактическую схему, объём БД+WAL+тома, доступное место,
   тариф и политику backup. Текущую остановленную сборку не запускать ради этой проверки.
2. Подтвердить поддержку SQLite WAL/locking на постоянном томе Amvera и одну реплику. Уточнить UID mount.
3. Закрыть все ворота ниже, согласовать окно недоступности, ответственного и критерии остановки выпуска.
4. Подтвердить в Amvera способ передать `KSU_BUILD_SHA` при Docker build либо использовать заранее
   проверенный неизменяемый образ. Dockerfile без полного SHA намеренно не собирается. Если платформа этого
   не поддерживает — выпуск заблокирован до выбора проверяемого способа доставки; не подставлять произвольный SHA.
5. После разрешения владельца заморозить все записи, сделать независимый full-/data backup указанным выше
   способом, восстановить его отдельно и подписать результат staging. Старую сборку/backup сохранить.
6. Подготовленную v3-копию разместить в **новом** `/data/offline-<release>/ksu.sqlite3`, не поверх
   `/data/ksu.sqlite3`. Отдельно подготовить права UID10001 и резерв диска. Выполнение/перенос делает владелец
   после согласования, не эта ветка. Не подключать общие import-jobs старой установки.
7. Только для будущего согласованного выпуска скопировать настройки из `deploy/offline_release/amvera.example.yml`;
   действующий `amvera.yml` сейчас не меняется. Тот же проект, тот же `/data`, порт8000, одна реплика;
   Dockerfile.offline-release. Не создавать второй Amvera-проект/платные сервисы.
8. Установить release env из таблицы: `off`, новый стабильный production deployment ID, HTTPS origin,
   новый KSU_DB, без `KSU_DATABASE_URL`, bootstrap и lab. Секреты хранить только у владельца/в Amvera.
9. Пока пользователи не допущены к записи: проверить health с нужным SHA, оба входа, ACL/CSRF,
   старые записи/историю/медиа/отчёты, повторный рестарт без reseed. Проверять на согласованном стенде;
   не создавать синтетические записи в рабочей базе без отдельного согласования.
10. После успешных проверок и разрешения владельца включить `pilot` только выбранной группе,
    с инструкцией и подтверждённым backup-расписанием. При сбоях немедленно `off`, сохранить очередь/receipts.
    Контролировать ошибки401/403/409/507, задержку receipt, рост SQLite/WAL, RAM/CPU/диск и фактический баланс Amvera.
    Никакого автоматического увеличения тарифа или рестарта до исчерпания бюджета.

Расходы в рамках этой подготовки: платные ресурсы не создавались. Будущий дополнительный Amvera-тариф
не назначен; текущие лимиты/стоимость и запас места подтверждает владелец в кабинете. Локальный Docker-staging
не требует второго облачного проекта. Расписание остановки по балансу остаётся задачей владельца:
задать бюджет/дату остановки и проверить уведомление, не полагаться на вымышленные настройки провайдера.

## Backup после выпуска и откат

Новый runtime **не запускает старый rotator с удалением старых daily-файлов**. Ранее созданные backup
не трогает. Автоматическое независимое расписание backup новым entrypoint пока не организовано:
**замена прежнего ежедневного покрытия, RPO/RTO, хранение вне /data, мониторинг результата и место — блокер выпуска**.
Разовый pre-release backup не заменяет ежедневную копию. Старый endpoint16МиБ не считать решением для150МиБ.
Согласовать с владельцем регулярные замороженные выгрузки либо отдельную проверенную backup-job, без платного
сервиса и без удаления существующих файлов. До подтверждения расписания production не включать.

Предпочтительный оперативный откат: `KSU_OFFLINE_MODE=off`, **тот же v3 binary/БД**, прежний deployment ID,
сохранённые receipts и онлайн-интерфейс. Это останавливает новые синхронизации без потери уже принятых данных.
Локальную очередь не чистить; конфликт разрешает человек. До остановки/смены binary заморозить записи,
снять новую независимую копию с уже принятыми операциями и сохранить их receipts.

Возврат к старому binary и нетронутому `/data/ksu.sqlite3` допустим лишь если доказано отсутствие любых
записей после переключения. **После новых записей возврат старого backup потеряет данные и запрещён**:
сохранять текущую v3-БД, отключить offline, сверять дельту и готовить отдельный согласованный recovery.
Автоматического downgrade/delete/merge нет. Старый binary не умеет новые receipts/пакеты, поэтому его запуск
на новой v3-БД не является проверенным откатом. Срок/порядок возврата к штатной работе подтверждает владелец.

## Ограничения MVP и ворота допуска

Один выезд на локальный зашифрованный профиль; максимум20 фото (одно на вопрос), до98 нарушений,
пакет ограничен сервером и сроком, синхронизация только при открытой странице. Нет фоновой отправки,
автоматического объединения, массовой загрузки, общего архива нескольких выездов или восстановления забытой
локальной фразы. Нельзя безопасно объявлять массовый много-выездный режим: нужен отдельный этап архива/смены
выезда. Пока группа должна быть согласна на один выезд в выделенном профиле; до нового выезда сохранить
проверенный зашифрованный экспорт и согласовать процедуру нового профиля, не удаляя старые данные.
Очистка данных Chrome/удаление профиля/поломка устройства могут уничтожить несинхронизированную копию.
Шифрование IDB не защищает от XSS/захваченного разблокированного устройства. Старый онлайн pending/cache
в localStorage не переводится автоматически в новый vault; политика устройств и старых черновиков требует проверки.
UI `offline/` производен от прототипа: до будущих исправлений требуется прогон обеих версий тестов, чтобы избежать расхождения.

| Ворота | Статус в этой работе |
|---|---|
| Автотесты SQLite/PG, повтор commit/receipt, роли, restart, обратная совместимость | См. `OFFLINE_RELEASE_TESTS.md` |
| Новая release-оболочка на физическом Android с cohort/off и доверенным HTTPS | Не выполнено, прежняя приёмка относится к PR30 |
| Фактическая схема и полный состав рабочей БД | Неизвестны; owner-local probe независимой копии |
| Независимый backup реальной установки и restore/staging с двумя существующими входами | Не выполнено здесь; только владелец локально |
| Целостность действующей онлайн-очереди, политика устройств и сохранение локальных черновиков | Требует проверки владельца |
| SQLite WAL/locking тома, UID, одна реплика, immutable build delivery | Требуют подтверждения Amvera/владельца |
| Свободное место, фактические CPU/RAM, RPO/RTO, независимый backup по расписанию, бюджет/остановка | Не подтверждены, блокеры |
| Одобрение узкого MVP/cohort, окна, rollback и production-запуска | Не получено; эта подготовка его не предполагает |

Рекомендация: следующий шаг — owner-local staging на независимой копии SQLite и закрытие ворот,
после чего отдельное решение о небольшом пилотном включении. PostgreSQL при данном выпуске не вводить.

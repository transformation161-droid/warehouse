# Issue #11 — самостоятельное планирование выездов инспектором

Реализация в отдельной ветке от `feat/issue-4-amvera-pilot`. Работающий проект Amvera не обновляется; слияние и выпуск — после завершения пилота #4 и безопасной процедуры обновления с независимой копией.

## Правила

«Свой» выезд — назначенный авторизованному инспектору через `assignedTo`. Это включает план, созданный руководителем для инспектора. Автор создания (`createdBy`) сохраняется; после переназначения прежний автор-инспектор теряет право редактирования, если он больше не исполнитель.

| Действие | Inspector | Manager |
|---|---|---|
| Создать план | Себе на доступном объекте | Активному исполнителю с доступом к объекту |
| Изменить дату, объект, вид, цель | Свой запланированный выезд; новый объект доступен | Запланированный выезд |
| Переназначить исполнителя | Запрещено | Разрешено в запланированном выезде |
| Отменить | Свой запланированный, с причиной | Запланированный, с причиной |
| Выполнить | Штатный чек-лист и новый акт назначенного исполнителя в том же запросе | По тем же правилам, без подмены исполнителя акта |
| Править завершённый/отменённый | Запрещено | Запрещено |

`assignedTo` инспектора устанавливается из серверной сессии; чужое значение отклоняется 403. Имя `assignee` берётся из аккаунта, а не из формы. Менеджеру snapshot возвращает только список активных исполнителей с ID, именем и назначениями объектов (`assignees`); инспектору этот список не раскрывается.

При отмене обязательна `cancellationReason` (1–1200 символов после удаления пробелов по краям). `cancelledBy` и `cancelledAt` (UTC) устанавливает сервер. Отмена не удаляет запись. В одном запросе отмены/выполнения нельзя одновременно заменить дату/объект/вид/цель/исполнителя: эти правки делаются до перехода статуса и отражаются отдельно в истории. Нельзя создать сразу отменённый/завершённый выезд, привязать старый акт, использовать один акт для нескольких выездов или заново открыть завершённый план.

Изменения и журнал фиксируются одной транзакцией. В новых событиях выездов в `before`/`after` сохраняется `version`, автор события — серверная личность, время — UTC. Старые события не переписываются. Устаревшая допустимая правка получает 409; чужой выезд — 403 даже при подложной версии. Повтор того же mutationId не создаёт дубли. Запрос с запрещённой операцией целиком откатывается, включая журнал и новый акт.

Ограничения дублируются в SQLite-триггерах. При открытии существующей БД триггеры заменяются атомарно; записи, аккаунты, пароли и прежний аудит не изменяются и не переинициализируются. Добавлены только необязательные поля JSON выезда, таблицы не дублируются. Завершённые/отменённые записи прежнего пилота сохраняются как есть, задним числом причины и версии истории не придумываются.

План остаётся в `visits`, факт проверки — в неизменяемом `inspections`; связь `inspectionId` создаётся штатным завершением. Календарь #2 сможет использовать существующий ID плана, дату, статус и версию. Календарь, PostgreSQL #9 и импорт Excel #10 в эту работу не входят.

## Проверка владельцем на отдельной тестовой копии

1. Открыть приложение в двух независимых браузерных сессиях: inspector и manager. Использовать только демонстрационные данные.
2. Inspector → «План выездов» → «Запланировать выезд»: доступный объект, дата, вид, цель «ДЕМО · Самостоятельный выезд». Исполнитель фиксирован текущим пользователем. Сохранить. Manager должен увидеть тот же выезд без ручного переноса.
3. Inspector → «Изменить»: перенести дату, изменить цель/вид, при необходимости выбрать другой доступный объект. Manager видит обновление. В «Истории» — первоначальные/новые реквизиты и версии.
4. Inspector → «Отменить»: пустая причина не принимается. Ввести «ДЕМО · Объект закрыт», подтвердить. Запись остаётся в плане, показывается причина, действия изменения/отмены отсутствуют. История содержит автора, дату UTC, причину и очередную версию.
5. Manager создаёт выезд самому себе. Inspector может видеть его в пределах общего доступного объекта, но не видит действий изменения/отмены/выполнения. После назначения inspector действия появятся. Акты уже выполненных выездов остаются доступны для просмотра, правка закрыта обеим ролям.
6. На отдельном запланированном выезде открыть форму в двух сессиях одного инспектора. Сохранить разные правки: первая проходит, вторая получает конфликт; использовать существующее восстановление запроса и сравнить актуальную запись.

Локально: **44 unittest успешно, без пропусков**, включая реальный локальный TLS, restart/restore на синтетической БД; 14 тестов Issue #11 покрывают разрешения, второй ID инспектора, HTTP/SQL запреты, аудит/версии, конфликты, идемпотентность и обновление правил существующей БД. Три браузерных сценария прошли; новый проверяет мобильное создание/перенос/отмену, причину и историю у руководителя, скрытие чужих/завершённых действий, переназначение и штатный акт. Прежние сценарии подтверждают фото, отчёты, черновик и повтор после потери связи.

CI server-tests также выполняет новый браузерный сценарий для PR в ветку пилота. Доставка Amvera по-прежнему относится только к main; её workflow и настройки не меняются. Локальные тесты и CI не являются приёмкой обновления на работающей Amvera.

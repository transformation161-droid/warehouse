## Проверки

- Реальные HTTP upload → preview → commit в PostgreSQL для XLSX ровно 18/30 МБ (десятичные МБ).
  Preview не меняет бизнес-таблицы. Сверяется каждая строка, все 17 полей, исходный ID/стиль,
  ведущие нули, комментарии, нули и кэш формул. Количество, стоимость, остаточная стоимость,
  подлежащая возмещению и возмещённая суммы сравниваются через Decimal, без float.
- Повтор того же файла не добавляет строки, import header или audit. Две разные книги 18 МБ
  накапливаются. Второй файл 30 МБ после 18 МБ и 18 МБ после 30 МБ явно отклоняется текущим cap,
  без изменения сохранённых строк/импортов/истории. Автоувеличения нет.
- Manager/inspector читают разрешённые объекты; дополнительный inspector только s1 не видит s2,
  его фото/детали и чужую историю, не импортирует s2. Проверяется и непосредственный SQL RLS.
  Anonymous получает 401; inspector и неверный CSRF не получают backup. Остальные Origin/CSRF,
  владельцы чужих записей и SQL-ограничения проверяются общими PostgreSQL-контрактами.
- Страницы по 100: первая, середина, последняя; фильтры s1/s2; `/api/state` без реестра списаний.
  Вся история проходит по keyset-страницам для двух ролей, сверяется checksum после восстановления.
  Потоковый CSV проходит целиком, со сверкой всех пяти итогов и checksum.
- Две независимые HTTP-копии одной большой БД, SHA-256 и одинаковые fingerprints восьми бизнес-таблиц.
  Восстановление второй копии в пустую БД другого PostgreSQL, проверка всех строк/денег/истории,
  фото, отчётов CSV/XLSX/PDF, прав, отзыва прежних сессий и конфликтов версий. Затем новый импорт,
  изменение выезда и новая HTTP-копия восстановленной БД. Первая копия остаётся целой.
- Ошибка БД на строке Excel 500 откатывает предыдущие вставки, header и audit; повтор успешно восстанавливает
  импорт. SIGKILL worker и timeout 1 с не меняют сохранённые данные; API health опрашивается параллельно.
  Kernel OOM намеренно не воспроизводится; его фактические counters и OOMKilled учитываются отдельно.

## Изменения, потребовавшиеся по результатам нагрузки

CSV теперь использует именованный серверный курсор PostgreSQL с порцией 64 строки: обычный клиентский
курсор psycopg загружал весь SQL-результат, несмотря на потоковый HTTP-ответ. SQLite сохраняет свой
обычный итератор. Полный реестр не попадает в Python list или `/api/state`.

История PostgreSQL использует прямой keyset-запрос к audit с существующим RLS. Избыточный JOIN с
полным реестром удалён. В этой транзакции work_mem ограничен 64 КиБ, чтобы планировщик использовал
индексные проверки прав для страницы вместо повторного hash-набора всего реестра. На диагностическом
EXPLAIN для inspector исходный запрос занял 4 710 мс, ограниченный индексный запрос — 7 мс. Это
иллюстрация причины исправления; HTTP-измерения полного прохода находятся в JSON. Доступ к чужому
аудиту не расширен, политики/схема/данные не менялись.

`KSU_IMPORT_PHASE_TIMEOUT_SECONDS` позволяет только уменьшить прежние 240 с (минимум 1 с) для
контролируемой проверки отказа; default и максимальная граница прежние. Offline restore получил
необязательный `--backup-role`: проверенная существующая read-only роль получает SELECT для новой
схемы, чтобы резервирование продолжало работать после restore. Для рабочего контура роли и секреты
по-прежнему готовит администратор; автоматического создания инфраструктуры нет.

## Ограничения до эксплуатации

SHA-идемпотентность не является логическим замещением исправленной книги. Probe с одинаковым ID и
новым SHA хранит обе стоимости 10 и 12, наивная сумма — 22. Это **блокер публикации KPI** до
[#21](https://github.com/transformation161-droid/warehouse/issues/21); текущий PR версионирование и аналитику не реализует.

Cap 256 МиБ — admission guard размера конкретной БД плюс консервативная оценка новой транзакции,
не квота всего PostgreSQL-хранилища. WAL, другие БД, staging и независимые копии считаются отдельно.
После транзакционного rollback PostgreSQL может оставить занятые страницы/WAL; успешный логический
откат не означает немедленного уменьшения диска. Пики стенда включают генератор/HTTP-клиент;
переносить их буквально в платный тариф нельзя.

Нужна отдельная ручная приёмка Windows Docker Desktop/BitLocker/ACL владельцем (#14), подтверждение
целевого persistent storage, TLS, backup/PITR и RTO/RPO. Целевой провайдер, сетевые задержки и
массовая одновременная работа пользователей здесь не испытывались. Самостоятельное восстановление
из доверенного пакета проверено локально; pg_restore исполняет SQL и не принимает недоверенные архивы.

Расчёт годового накопления и варианты согласования лимитов: [POSTGRESQL_CAPACITY.md](POSTGRESQL_CAPACITY.md).

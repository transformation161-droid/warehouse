## Исходные проверки

Оба теста падали из-за `.parents[1]`: искали файлы в родительской папке. В smoke-тесте также был жёсткий путь `/mnt/data/ksu_v2` для снимков и отключалась браузерная защита. ## Выявлено и исправлено

| Проблема | Решение |
|---|---|
| Переключатель роли подменял авторизацию | Индивидуальные серверные аккаунты; роли нельзя задать через API |
| У разных браузеров разные базы | Общая SQLite-БД за API, опрос каждые 3 секунды |
| Доверие валидации интерфейса | Строгие модели, серверные проверки связей, прав и переходов состояний |
| Нет границ полномочий | Руководитель управляет справочниками и планом; исполнитель пишет собственные операционные записи только по назначенным объектам. SQL-триггеры дополнительно ограничивают запись |
| Перезапись при параллельной работе | Версия каждой записи, атомарные пакеты, HTTP 409 при конфликте |
| Повторная отправка могла создавать записи | Идемпотентный идентификатор запроса и хеш его тела |
| Нет полной истории | Неизменяемый через API журнал до/после, автор, UTC-время, транзакция вместе с записью |
| Фото в браузере и без защиты | Закрытые BLOB в БД, авторизация и объектный доступ, декодирование/повторное JPEG-кодирование без исходных метаданных, миниатюры |
| CSV принимал несуществующие даты; повтор создавал дубли | CSV/XLSX, сопоставление, предпросмотр, проверка календарной даты и чисел, атомарный импорт, хеш файла; исходный файл сохраняется в закрытой БД |
| Не было подтверждения устранения | Для закрытия нужны результат и фото-подтверждение |
| Недостачи без стадий | Первичное → подтверждено → расследование → утверждённый итог → взыскано; снято корректировкой — отдельная ветвь. Переходы подтверждает руководитель с основанием |
| Экспорт без нативного XLSX/PDF | Серверные отчёты, XLSX с диаграммой, PDF с кириллицей, CSV; защита от формул в текстовых ячейках |
| Старые акты зависели от текущих вопросов | Неизменяемые завершённые акты, серверный снимок текста и раздела вопроса |
| Повторность менялась задним числом | Признак определяется при создании и сохраняется при редактировании |
| Ошибки путей README | Актуальная структура и инструкции запуска в README и README_START.txt |

`schema.sql` — исторический неиспользуемый проект Supabase, а не миграция локальной версии. Его политики позволяли всем участникам менять нарушения/инвентаризации/строки и не обеспечивали версионирование. Он не прошёл PostgreSQL-проверку и не должен применяться при развёртывании. Действующая схема — `server/database.py`, проверена API-тестами и прямыми попытками обхода триггеров. SQLite не предоставляет отдельного сетевого SQL-доступа: чтение ограничивает API, запись — API и триггеры с идентичностью соединения. Администратор с доступом к файлу БД остаётся доверенным.

## Архитектурное решение

Для первого совместного локального пилота сохранён исходный HTML/CSS/JS, чтобы не менять одновременно интерфейс и модель доступа. `sync.js` отделяет сессии, API, синхронизацию и восстановление запросов; сервер разделён на контракты, БД, бизнес-проверки, импорт и отчёты. Перенос на React/TypeScript из долгосрочного HANDOFF в этом этапе не выполнен. PostgreSQL/Supabase, SSO, внешние интеграции и публичное размещение не подключались. Выбор согласованной инфраструктуры нужен до работы с корпоративными данными.

## Практические пределы пилота

- Два аккаунта и назначения объектов создаются локально администратором; самообслуживания пользователей нет.
- SQLite подходит одному серверу с локальным постоянным диском и небольшому пилоту. Для нескольких реплик нужен отдельный проект миграции PostgreSQL с RLS и нагрузочной проверкой.
- Синхронизация при открытом редактировании приостановлена; конфликт проверяется на сохранении. Введённые изменения не перезаписываются автоматически.
- Отправляемый пакет сохраняется в IndexedDB по аккаунту; черновик чек-листа дополнительно сохраняется раз в секунду и восстанавливается после перезагрузки; остальные незавершённые формы живут в памяти до нажатия «Сохранить». Есть предупреждение при уходе со страницы формы. Полностью автономная работа без доступа к ранее открытой странице не реализована.
- Хеш защищает от повторного импорта байт-в-байт одного файла. Изменённый или пересохранённый файл считается новым; смысловую дедупликацию разных файлов нужно согласовать отдельно.
- Переход финансовой стадии применяется ко всему пересчёту, взыскание — полной сумме первичных недостач после утверждения. Частичные корректировки/взыскания по строкам, сложные акты и юридическое подтверждение — следующий этап. Ни первичная, ни подтверждённая стадия не считаются автоматически ущербом.
- Фильтры, CSV/XLSX/PDF, недельная сводка и акты есть; библиотека сохранённых шаблонов и составные группировки ещё не реализованы.
- TLS-примеры подготовлены для администратора; DNS, сертификат и размещение на внешнем сервере здесь не проверялись.

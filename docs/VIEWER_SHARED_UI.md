# Viewer в общем интерфейсе — доработка на базе PR №34

База: `release/viewer-branding-backup`, `5a9b3b615a56e3be0e5a523ab52066bccbaf2b07`.
Работа ведётся в отдельной ветке `fix/viewer-shared-interface`, для отдельного Draft PR
с base `release/viewer-branding-backup`. Amvera, main, рабочая SQLite и порт 8003 не используются.
Merge/deploy не выполняются. Прежние ручные ворота выпуска остаются открытыми.

## Один интерфейс, разные права

Отдельный `renderViewer` удалён. Все три роли используют один `app.js`: sidebar, навигацию,
карточки, таблицы, фильтры, модальные окна и общий `styles.css`. `viewer.js` теперь содержит
только ограничения действий общего интерфейса. Бейдж показывает «Только просмотр».
У viewer доступны обзор, объекты и их карточки, проверки/акты, план выездов, нарушения,
инвентаризации/строки, аналитика/отчёты и применимые сведения в настройках.

Существующие карточки актов и нарушений показывают результаты по пунктам, операционные
комментарии, фото нарушения и подтверждение устранения. Поля общей формы карточки отключены;
кнопки сохранения/создания/редактирования/импорта/изменения статуса и загрузки файлов отсутствуют.
Фильтры, поиск, переходы, разрешённые печать/выгрузки и выход работают.
Manager/inspector сохраняют прежние интерфейсы, права и офлайн-сценарии.

## Серверная граница

| Данные / действие | Правило viewer |
|---|---|
| Вход и объекты | Персональный вход; только явные `user_sites`. Без ACL все данные и чек-лист пусты. Нет автоматического доступа ко всем объектам. |
| Разрешённое чтение | Явный типизированный белый список для объектов, выездов, результатов проверок, нарушений, инвентаризаций и строк. Неизвестные поля и вложенные объекты вместо скалярных полей исключаются. |
| Структурированные персональные поля | Не выдаются ФИО проверяющих/ответственных/исполнителей, `storekeeper`, `pm`, `createdBy`, пользователи/assignees, raw imports, аудит, receipts, сессии или хеши паролей. Собственная учётная запись видна пользователю. |
| Операционный текст и изображения | Описание, комментарии к пунктам/устранению, бизнес-показатели и привязанные фото разрешены в пределах объекта. Свободный текст и фото могут содержать сведения о людях; их состав и персональные ACL владелец проверяет до реального допуска. Автоматическое распознавание/маскирование лиц и текста не заявляется. |
| Вложения | Для оригинала и миниатюры заново проверяются текущий ACL, собственный объект media и ссылка из разрешённого акта/нарушения на том же объекте. Известный URL другого объекта, неподключённое фото и отозванный ACL дают 404. |
| Выгрузки | JSON/CSV/XLSX/PDF строятся из текущей серверной проекции viewer. Явный чужой объект/чужая инвентаризация дают 404. Выгрузка строк пересчёта проверяет родителя. Фото-ссылки привязаны к ожидаемому пользователю, поэтому cookie manager из другой вкладки не расширяет viewer-доступ. Браузер выгрузок передаёт expected-user; смена cookie не подменяет viewer-выгрузку данными manager. Печать повторно подтверждает сессию/ACL. |
| Изменения | Все бизнес-POST/PUT/PATCH/DELETE запрещены до разбора тела, включая некорректное тело/неизвестный endpoint; login/logout остаются операциями сессии. Независимые SQL guards/RLS и запрет в `apply_changes` сохранены. |
| Офлайн / backup / история | Новые пакеты, отправки, фото-upload, receipt API, backup и журнал с персональными данными запрещены. Viewer не открывает IndexedDB с очередями/черновиками. Старые очереди других аккаунтов не удаляются. |

Клиентские кнопки не являются границей безопасности. Даже подставленная кнопка, прямой API-запрос
или вызов `mutate` не создают запись/очередь viewer. API/media/выгрузки имеют `no-store`.
Ранее доставленную на устройство информацию нельзя отозвать задним числом; новые запросы после
отзыва доступа проверяются независимо. Ограничение и off-флаги PR №34 сохранены.

## Схема и совместимость

SQLite остаётся **v4**, без новых таблиц, DDL при старте и изменения данных/учётных записей.
PG также сохраняет табличную схему v4; явно добавляются/обновляются ограниченные функции чтения
`viewer_records`, `viewer_media_links`, `viewer_media(text,boolean)` и маркер `viewer_read_version()=2`.
Raw `records/media/users/audit/imports` через viewer actor по-прежнему закрыты RESTRICTIVE RLS.
Функции с SECURITY DEFINER имеют фиксированный `search_path`, проверяют actor/ACL и не выполняют запись;
PUBLIC лишён EXECUTE, runtime получает только явные grants.

**Существующий PG v4 требует явного administrator upgrade на новой закрытой staging-копии**
через `server.pg_admin upgrade` с прежними runtime/backup ролями по инструкции PostgreSQL.
Пароли/DSN передаются прежним приватным способом, не в чат/аргументах. Это не команда для рабочего PG.
Без маркера новой capability закрыты только запросы viewer; manager/inspector продолжают работать.
Runtime сам функции не устанавливает.
Миграция v3 и независимый native restore устанавливают функции в новом target автоматически
внутри явного admin-инструмента. Отпечатки старых таблиц/данных проверяются; модель receipts не меняется.

## Windows: переключение pilot/off

`Set-Release-Acceptance.ps1` читает JSON через `docker container inspect <имя>` и `ConvertFrom-Json`.
Go template с вложенными кавычками больше не передаётся в native `docker.exe` Windows PowerShell 5.1.
До stop/rm/run проверяются единственный контейнер, точное имя и метка владельца профиля.
Чужая метка/имя или повреждённый JSON прерывают операцию, не меняя state.json/контейнеры.
Смена режима сохраняет origin/deployment ID и named data volume; 8003 запрещён.

Регрессионный Windows-тест `tests/windows_acceptance.Tests.ps1` компилирует временный native
`docker.exe`-стаб, проверяет настоящую передачу argv и переходы pilot/off/stop, а также отказы
при чужом контейнере и повреждённом JSON. Docker daemon, рабочая установка и credentials не нужны.
Это дополнение к parser-тесту; физический Docker Desktop владельца всё равно требует ручной проверки.

## Проверка владельцем — только синтетический стенд

По [Android-инструкции](ANDROID_RELEASE_ACCEPTANCE.md) собрать новый SHA из этой ветки и создать
новый синтетический профиль. Существующий стенд PR №34 может содержать старые JS/копию скрипта:
не считать его автоматически обновлённым. Порт 8003 и рабочие БД не использовать.

1. В отдельных профилях войти manager, inspector и viewer. Сравнить меню, карточки и модальные окна
   на компьютере/Android: одинаковые разделы и стиль, у viewer бейдж и нет команд записи.
2. Открыть объект → акт с результатами и фото; нарушение → описание/фото/подтверждение;
   инвентаризацию → строки; отчёты → фильтры и CSV/XLSX/PDF. Защитные персональные поля не показываются.
3. Unassigned viewer получает пустые данные. Viewer видит только s1; фото/выгрузка s2 по прямому URL
   недоступны. После отзыва s1 старый URL фото и новая выгрузка тоже недоступны.
4. Переключить новый стенд pilot → off → pilot исправленным скриптом. Viewer сохраняет чтение,
   офлайн-отправки запрещены; очередь inspector и данные сохранены. Отдельный viewer off-флаг закрывает роль.
5. Manager/inspector выполняют прежний полный выезд, устранение и отчёты без изменения поведения.

## Автоматические проверки

Команды в среде с requirements-dev, Chromium и локальным Docker, только синтетика:

```sh
CADDY_BIN=/path/to/caddy python -m unittest discover -s tests -v
python -m tests.offline_stage1_environment --release --output /tmp/private-shared-viewer-pg
python -m tests.viewer_browser --backend sqlite
python -m tests.viewer_browser --backend postgres
python -m tests.offline_stage2 --release --backend sqlite
python -m tests.offline_stage2 --release --backend postgres
```

Browser-тест сравнивает пиксели навигации всех трёх ролей на 1280/390 px (скрыт только динамический
счётчик нарушений), computed styles общих компонентов и прохождение деталей/фото/выгрузок.
Он также проверяет сохранность заголовков карточек, запрет подставленных write-кнопок, прямого
mutate/API, отсутствие IDB, пустой ACL, смену cookie и отсутствие изменений бизнес-таблиц.
Синтетические PNG сохраняются в `var/viewer-ui/<backend>`; CI публикует только эти изображения.
CI запускается и для нового Draft PR с base `release/viewer-branding-backup`, включает прежние
контейнеры/backup, оба backend и настоящий Windows native-argv тест.

## Права

| Возможность | manager | inspector | viewer |
|---|---|---|---|
| Вход | Персональный | Персональный | Персональный, без анонимного/common guest |
| Объекты | Все, как раньше | Назначенные ACL | Только явно назначенные ACL; без ACL — пусто |
| Планирование | Прежние права | В релизе PR33 — только завершение назначенного выезда | Нет |
| Запись/изменения, фото, импорт | Прежние права | Прежние права | Все запрещены, включая прямые POST/PUT/PATCH/DELETE и неверное тело запроса |
| Офлайн-пакеты/синхронизация | Как в PR33 | Только явная группа в pilot/staging | Запрещены в pilot и off |
| Вложения/миниатюры, история | Прежние ACL | Прежние ACL | Запрещены, даже если известен URL |
| Финансы/источники, отчёты/выгрузки/backup, администрирование | Прежние права/флаги | Прежние ограничения | Запрещены |

Viewer получает отдельную серверную проекцию: имя объекта; дата/вид/статус выезда;
дата проверки; заголовок/статус/критичность/дата/срок нарушения. Нет описаний и комментариев,
ФИО ответственных/авторов, источников импорта, фото, инвентаризационных сумм, истории и перечня сотрудников.
Белый список полей одинаков на SQLite и PG; вложенные объекты в строковых полях не выдаются.
Состав этой проекции должен утвердить владелец: доступный заголовок тоже может содержать деловую информацию.
Расширение доступа к фото/экспорту не включено «по умолчанию», потребует отдельного решения.

В SQLite ограничения записи обеспечены SQL-триггерами и read-only authorizer actor-соединения,
чтение — явной SQL-проекцией с ACL. Файл БД принадлежит доверенному сервису/владельцу, не пользователю viewer.
В PG дополнительная RESTRICTIVE RLS закрывает старые permissive-политики; viewer не читает исходные
records/media/imports/users/audit. SECURITY DEFINER функция с фиксированным search_path возвращает
только разрешённую проекцию. Runtime не получает права администратора.

Интерфейс viewer не содержит редакторов, экспорта и офлайн-очереди, не загружает прежние черновики в IndexedDB.
API имеет no-store; ответы не попадают в SW Cache. Заголовок expected-user защищает от смены cookie
в другой вкладке, при возврате из BFCache требуется подтверждение сессии. Manager/inspector очереди не удаляются.
Ранее законно полученную офлайн-копию нельзя отозвать у отключённого устройства: раздельные профили/устройства,
локальная фраза инспектора и политика доступа обязательны. Viewer не выдавать фразу чужого vault.
Это ограничение не обходится очисткой данных: автоматического удаления локальных очередей нет.

`KSU_VIEWER_ACCESS=off` отключает чтение viewer без изменения пользователей/ACL/БД, остальные роли работают.
Допустимы `enabled` (по умолчанию для явно созданных персональных viewer) и `off`.
Роль сама не появляется: существующие manager/inspector не преобразуются и общий guest не создаётся.
`KSU_OFFLINE_MODE=off` отдельно останавливает новые офлайн-отправки, сохраняя GET receipt и обычную работу.

## Миграции и совместимость

V4 расширяет CHECK роли users и добавляет ограничения viewer. Таблицы бизнес-данных и формат receipts
не меняются. Для SQLite перестройка users выполняется **только на внутренней новой копии** с сохранением
всех колонок, паролей, PK/FK, данных и триггеров. Неизвестные колонки/таблицы/итоговые ограничения отвергаются.
Сравниваются отпечатки всех старых бизнес-таблиц, integrity/FK, SHA исходного файла; исходник неизменен.
Runtime не выполняет DDL и отказывает на v3. Даже обычный Database не перестраивает старую таблицу users
автоматически. Исходный `/data/ksu.sqlite3` не открывался в этой работе.

PG v3 → v4 — явная administrator migration, без запуска на8003. Native backup формата v1 со схемой1/2/3
восстанавливается в новую пустую БД и явно обновляется до4; схема4 также поддерживается. Grant/RLS проверяются.
Формат v3-пакетов, media IDs/SHA, mutationId/expectedVersion и содержимое receipts сохранены.
В тесте база из настоящего PR33 сохраняет все16 таблиц, прежний receipt/фото; старый пакет завершает
выезд после обновления, повтор не создаёт дубли. База из рабочего кода3e3771ec также проверяется на синтетике.
Sessions/attempts очищаются только в независимой копии, как в PR33; учётные записи и хеши паролей сохраняются.

Владелец сначала выполняет backup и `Prepare-Offline-Staging.ps1` из инструкции PR33 **локально**;
в этой ветке prepare-copy выдаст schema_after4. Корпоративную копию в Codex/GitHub не переносить.
Для персонального viewer есть CLI `server.viewer_admin` **только для закрытой staging/candidate-копии**:
пароль и username/name/siteIds передаются JSON через stdin, не в аргументах или Git. Обязательны
`--database <копия> --closed-copy`. Site IDs проверяются, пустой список означает отсутствие доступа;
создание отражается в audit без пароля. Нет HTTP-администрирования или изменения существующего аккаунта.
Пример структуры stdin (пароль вводит владелец локально через защищённый диалог, не вставлять его в командную строку):
`{username, name, password, siteIds:[...]}`. На действующем томе этот инструмент не запускать.

## Ворота выпуска и откат

Пока не подтверждены: фактическая схема/объём рабочего тома, owner-local backup/restore/staging реальной копии;
физический Android с новым брендингом и pilot/off/viewer; whitelist полей и персональные ACL;
том Amvera WAL/locking/UID/одна реплика, pinned build delivery, запас CPU/RAM/диска и бюджет;
работа расписания/DPAPI/Docker на Windows владельца, свежесть backup и согласованные RPO/RTO;
приемлемость одного выезда на зашифрованный профиль; окно и ответственность за выпуск/остановку/откат.
Платные ресурсы не создавались; дополнительный облачный сервис для backup не нужен, но место/доступность
компьютера владельца и текущие расходы Amvera требуют подтверждения.

Оперативный откат функции: viewer_access=off и/или offline_mode=off на **том же v4 binary и БД**,
с прежними origin/deployment ID; не удалять users/ACL/receipts/фото/локальную очередь.
Возврат v3 binary на v4 не поддержан, сервер откажет при проверке схемы. Старую рабочую БД и backup
сохранить отдельно. После любых новых записей возврат к старой копии теряет данные и запрещён:
сначала freeze, новая независимая копия и отдельное согласование recovery/сверки дельты.
Никаких автоматических merge/downgrade/очисток и production-deploy в этой ветке нет.

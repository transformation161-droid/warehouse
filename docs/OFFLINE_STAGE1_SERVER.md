Основание: принятый PR #28 `95952d36dc2098e0f033c8a7abe08551387ae671`, включающий
PR #27 `9ab36f1702a972931afe93a026c8f865739c1b37`. Отдельная ветка

Только синтетика. Новые API не подключены к IndexedDB/Service Worker/очереди этапа 0.

## API и авторизация

Прежние cookie-сессия, Origin, CSRF, ограничения тела/изображений и `no-store` сохранены.
Автор и роль назначаются сервером. Новые маршруты:

| Маршрут | Контракт |
|---|---|
| GET `/api/checklists/current` | Текущий снимок `{id, questions}` |
| GET `/api/checklists/{id}` | Неизменяемый исторический снимок |
| POST `/api/media` | Прежние `siteId`, Base64 `content`; необязательная пара `mutationId` + `sha256` |
| GET `/api/receipts/{mutationId}` | Сохранённый результат текущего пользователя |
| POST `/api/offline/packages` | `{"siteIds":["s1"],"ttlHours":24}` |
| POST `/api/offline/changes` | Прежний batch изменений плюс `packageId`; ответ — receipt |

Прежний POST `/api/changes` возвращает прежнее состояние. Новые операции этого
маршрута тоже сохраняют receipt, который затем можно запросить отдельно.

## Чек-листы

ID версии — SHA-256 канонического UTF-8 JSON вопросов, отсортированных по ID,
включая версию отдельного пункта. Вопрос: `id`, `version`, `section`, `title`.
Изменение справочника manager через batch сохраняет версии до/после успешной операции.
При неудаче частичные версии откатываются. Чтение текущего чек-листа идемпотентно
регистрирует исходный снимок, если его ещё нет. Прежний аудит справочника сохранён.

Новый акт может передать `checklistVersion`. Сервер сверяет полный набор ответов
и сам подставляет исторические заголовки/разделы. Без поля старый клиент использует
текущую версию, сервер записывает её ID в новом акте. Прежние акты/их снимки
не переписываются; история версий до внедрения задним числом не выдумывается.

## Фото и receipts

Для идемпотентной загрузки передаются **оба** поля: стабильный `mutationId` (UUID)
и `sha256` декодированных отправляемых байтов. Сервер проверяет hash и прежние лимиты:
JPEG/PNG/WebP <=3 000 000 байт, <=20 Мп; сжатый выход <=1600 px, миниатюра <=240 px.
Ключ дедупликации — `(пользователь, объект, hash)`: равенство байтов, не визуальное
сходство. Другие пользователи/объекты не получают общий URL. Старые фото не переиндексируются.

Фото, ключ дедупликации и receipt записываются одной транзакцией. Повтор ID возвращает
тот же receipt/URL; другой ID с теми же байтами/пользователем/объектом также не создаёт BLOB.
Без новых полей сохраняется старое поведение. Фото/миниатюры по-прежнему требуют
авторизации через `/api/media/{id}`.

Идентичность операции — `(user_id, mutationId)`, общий namespace для изменений/фото.
Новые изменения хешируются в каноническом Pydantic-представлении; фото — по объекту
и проверенному hash байтов. Старые `mutations` сохраняют прежний алгоритм/hash.
Другое содержимое или вид операции с занятым ID дают 409.

Receipt: `mutationId`, `kind`, `status`, `committed`, `recordedAt`, `records`
(ID/объект/зафиксированная версия); для фото `url`, `sha256`, для конфликта `detail`.
Без паролей, исходного batch и бизнес-содержимого записей. GET возвращает HTTP 200
с сохранённым status; отсутствие/чужой аккаунт/отзыв доступа дают 404. Текущие права
и назначение выезда перепроверяются. Receipt не даёт новых полномочий.

Успех фиксируется атомарно с бизнес-записями, аудитом и mutation. При потере ответа
после commit повтор не выполняет изменения снова, новая сессия видит тот же receipt.
Старый `/api/changes` при повторе возвращает актуальное состояние; receipt — исходные версии.

`expectedVersion`: 0 — создание, N — изменение ровно версии N. Записи сериализованы
SQLite-транзакцией/PG advisory transaction lock. При 409 откатывается весь batch
до savepoint, затем сохраняется конфликтный receipt. Нет частичных записей/аудита
или успешного mutation. Повтор конфликта стабилен; после сравнения данных нужен новый ID.
Автоматического merge/last-write-wins нет.

401/403/404/422, неверный hash/фото, transient 5xx и disk-full не являются принятыми
операциями и не создают новый receipt. Старым операциям первоначальный receipt
достоверно восстановить нельзя: их retry работает, GET даёт 404. Нельзя автоматически
повторять их под новым ID без проверки наличия бизнес-записи.

## Ограниченный пакет

Привязан к аккаунту: версия чек-листа, разрешённые объекты, назначенные ему
запланированные выезды и собственные незакрытые замечания с версиями.
Лимиты: **1–5 уникальных объектов, 50 выездов, 50 замечаний, 1–200 вопросов,
2 МиБ UTF-8 JSON, 1–24 часа, 20 действующих пакетов/аккаунт**.
Превышение состава — 413 без обрезания; числа — 429. Фото-BLOB, пользователи,
пароли, реестр списаний, инвентаризации и общая история не входят. Приватные URL
в замечаниях не делают фото публичными.

`/api/offline/changes`: разрешены `visits`, `inspections`, `findings` по объектам пакета.
Изменение существующей записи использует версию из пакета и проходит текущий
expectedVersion; новые записи — 0. Акт обязан использовать checklistVersion пакета,
даже если справочник изменился. Новый batch после истечения пакета — 409; retry уже
принятой операции может получить прежний receipt при сохранённых правах.
Пакет не обходит актуальные ACL/неизменность завершённых актов/выездов.
Каждый POST подготовки создаёт новый снимок; это не бизнес-mutation. TTL проверяется
новым `/api/offline/changes`, не меняет правил прежнего онлайн `/api/changes`.

## Базы и обновление

Новые append-only таблицы: `checklist_versions`, `operation_receipts`, `media_keys`,
`offline_packages`. SQLite обновляется добавочно при открытии; прежние данные не
переписываются. Это частная БД: ACL чтения — в API, вставка/неизменность — также триггеры.

PostgreSQL использует **схему v3**, RLS по пользователю/текущим объектам, runtime
без владения/superuser и только SELECT/INSERT на новые таблицы. Runtime не делает DDL
и отказывается стартовать на v2 без явного upgrade. На отдельной синтетической установке,
задав admin DSN защищённой переменной окружения:

```sh
python -m server.pg_admin upgrade --runtime-role ksu_runtime --backup-role ksu_backup
```

Upgrade идемпотентен и сохраняет прежние таблицы. Рабочую Windows-установку PR #27
с этой веткой не обновлять в рамках этапа 1. Реальные обновление/окно записи/backup/откат
согласуются отдельно. Старый runtime v2 не рассчитан на v3; нужен соответствующий комплект.

Все новые таблицы входят в manifest/fingerprints/native backup. Контейнер копии прежний,
новый manifest schema_version=3. Restore v1/v2 проверяет прежние таблицы перед upgrade.
Finalize проверяет полный набор таблиц соответствующей v2/v3-схемы. Старые инструменты
не должны молча игнорировать v3. Операций с рабочими данными/Amvera не было.

Python 3.12+, зависимости `requirements-dev.txt`; для PostgreSQL — локальный Docker.
Нет облачной БД/платных ресурсов. Пароли тестов случайны, в исходники/логи не выводятся.

```sh
python -m unittest tests.test_offline_stage1.Offline tests.test_offline_upgrade -v
python deploy/get_caddy.py --output /tmp/ksu-caddy
CADDY_BIN=/tmp/ksu-caddy python -m unittest discover -s tests -v
python -m tests.offline_stage1_environment --output var/offline-stage1-checks
```

ограниченный runtime, настоящие PG17 backup-клиенты. Удаляются только ресурсы теста.
CI публикует лишь aggregate summary, не БД/архивы/книги/ключи. Лог приватный.

## Ограничения

- Нет интеграции UI/очереди/автоповтора, скачивания фото в пакет, бинарной загрузки,
  разрешения конфликтов человеком, push. Подключение UI — только после согласования.
- Сервер не может стереть скачанный пакет с отключённого устройства. Шифрование,
  локальная фраза/блокировка/очистка — ответственность будущего клиента; этап 0 не ослаблен.
- Нет автоматического удаления receipts/версий/пакетов. До production нужны retention/GC,
  мониторинг роста/backup. Истечение пакета не удаляет строку. DB/data caps не повышены.
- Base64 и общая сериализация PG-записей сохранены для совместимости. Большой парк
  офлайн-клиентов требует отдельной нагрузочной приёмки.
- Физическая приёмка синхронизации на Android остаётся отдельным последующим этапом.

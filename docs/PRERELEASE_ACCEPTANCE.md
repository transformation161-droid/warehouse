# Предрелизная оптимизация и удобство — Issue #25

Основа — Draft PR #24, `feat/issue-15-writeoff-analytics`, точный коммит `17521cd3386924e1483edd0cf68913998f720a50`. Использованы только синтетические данные. Существующая рабочая ветка #25 продолжена; дубликаты веток и PR не создавались.

## Подтверждённые причины задержки

Исходный запрос при свежих после импорта статистиках недооценивал размер соединений под RLS. EXPLAIN ANALYZE показал повторное чтение набора из 24 000 фактов 720 раз и около **17,3 млн отклонённых сочетаний**. Обновление статистики через ANALYZE на отдельном тестовом стенде сокращало SQL примерно с 9,8 до 1,7 секунды. Поэтому исходное различие «первый / прогретый» нельзя объяснять только файловым кэшем.

Дополнительная проверка обнаружила отличие плана SELECT от плана `DECLARE CURSOR`: аналитика читает серверный курсор полностью, а планировщик по умолчанию ориентируется на первые 10%. Один промежуточный вариант исправлял первое открытие, но давал около 58 секунд после ANALYZE. Он **отклонён**, не опубликован как улучшение. Финальный стенд сохраняет планы обоих видов, а не только обычного SELECT.

SQL, JSON, Decimal/группировка, сериализация и отрисовка измерены отдельно. Сериализация небольшого ответа занимала доли миллисекунды, поэтому новый формат ответа, библиотека графиков или повышение ресурсов не требовались.

## Изменения

- Метаданные версий, связей записей и объектов материализуются внутри **одного SQL-снимка**. Повторные проверки большой стороны соединения исключены; исходные ячейки XLSX не попадают в материализованные метаданные.
- PostgreSQL читает доступные архивные ID один раз через `NOT IN`. Эквивалентность прежнему ACTIVE обеспечена непустым первичным ключом `decision_retirements.record_id`; RLS применяется к этому чтению. В SQLite сохранён исходный `NOT EXISTS`.
- В транзакции аналитического чтения задан только `cursor_tuple_fraction=1`: курсор действительно потребляется до конца. Схема, индексы, политики RLS, глобальные настройки PostgreSQL и квоты не менялись.
- Убраны повторное создание JSON-декодера, неизменного Decimal-предела и конфигурации кодирования отпечатка. Подготовка выбранных текстовых условий выполняется один раз для неизменяемого запроса. Decimal, проверки точности и формат отпечатка сохранены; постоянного кэша результатов нет.
- Период и объект всегда доступны, дополнительные фильтры раскрываются отдельно. Применённые условия можно снимать по одному. Переход к текущему составу документа не помечает его историческим.
- Количество показано точно: например `104,000 013`, с визуально выделенной дробной частью и точным значением для скринридера/подсказки. Единицы явно обозначены как неоднородные. Есть счётчик и переход к дробным строкам; дробность не считается ошибкой автоматически. Выгрузки не округляются.
- Старый раздел назван **«Операционные отчёты»**: проверки, нарушения, первичные расхождения инвентаризаций и недельная сводка. **«Списания и аналитика»** работает с готовыми результатами списаний и решений. Прежние источники и CSV/XLSX/PDF сохранены.
- Загрузка показывает состояние, сетевую ошибку и повтор. Через 30 секунд запрос браузера прерывается с понятным сообщением; фильтры сохраняются. Проверены отказ сервера, повтор и реальный AbortController под виртуальными часами браузера.

## Методика сравнения

Одна физическая PostgreSQL с одними и теми же **24 000 действующими фактами**, 720 документами, несколькими объектами и месяцами, неизвестными датами/суммами, нулями и реальным исправлением XLSX. Сравниваются точный исходный коммит и текущая версия. Стенд проверяет маркер версии каждого ответа, чтобы рабочая папка Python не подменила baseline.

Для каждой версии — **30 первых открытий** с перезапуском API и неизменной статистикой после свежего импорта, затем **30 прогретых запросов** после одного ANALYZE. Пятёрки запросов чередуются, порядок версий меняется. Итого **120 настоящих HTTP-замеров**. Для воспроизводимости автовакуум отключён только на таблицах временного синтетического стенда; рабочая конфигурация приложения не менялась. Очистка ОС/файлового кэша не заявляется: «первое открытие» здесь — API после перезапуска и статистика свежего импорта, а не выключенный диск.

Приложение с тестовым клиентом и эталоном ограничено **0,5 CPU / 1 ГиБ**; отдельные PostgreSQL source/restore — каждая **0,5 CPU / 1 ГиБ**. Лимит базы **256 МиБ** сохранён. Во всех ответах сравниваются независимые целочисленные суммы, покрытие пустых значений и отпечаток состава. Отпечаток всех сравнительных запросов должен совпадать, несмотря на разные SQL и серверы.

p95 рассчитан методом ближайшего ранга, медиана — по всей выборке (локально n=30, в CI n=20 на фазу и версию); сырые значения опубликованы. Это измерение стенда, не SLA. Профилирование с дополнительными вызовами часов/cProfile вынесено за пределы выборок latency и отдельно отмечено как диагностическое.

Автоматический порог проверяет улучшение p95 первого открытия относительно baseline **того же хоста** (не менее 40%); абсолютный ориентир 5 с не выдаётся за независимый от железа SLA. Для прогретого режима сохранён отдельный порог регрессии. CI публикует все абсолютные медианы/p95 в аннотациях и артефактах, включая сбои; это не маскируется зелёным результатом сравнения.

В приведённых локальных замерах API перезапускался перед каждым первым запросом. В CI используется `--block-restarts`: перезапуск перед каждой пятёркой, одинаково для обеих версий, при неизменной статистике свежего импорта. Локальная выборка — 30+30 на версию (120 запросов); выборка CI — 20+20 на версию (80 запросов). Внутри каждого стенда условия и число запросов обеих версий одинаковы; выборки не объединяются. Приложение не кэширует результаты, соединение PostgreSQL и SQL-снимок создаются для каждого запроса. Так исключены десятки не входящих в измеряемую latency загрузок Python/авторизаций, которые на общем CI-хосте приводили к 30-минутному тайм-ауту. Квоты и тайм-аут не увеличивались. По доступным аннотациям первого полного CI его исходный первый запрос имел медиану 26,28 с, новый — 8,99 с: одинаковые квоты не означают одинаковую скорость разных физических CI-хостов. Это также подтверждает необходимость сравнения с baseline того же стенда, а не выдачи локальных секунд за SLA.

| Режим (n=30 на версию) | До: медиана / p95 | После: медиана / p95 |
| --- | --- | --- |
| Первое открытие, свежая статистика | 9.691 / 10.092 с | 2.895 / 3.119 с |
| Прогретое, после ANALYZE | 2.440 / 2.518 с | 2.685 / 2.721 с |

**Первое открытие ускорено примерно в 3,35 раза. Прогретый запрос немного медленнее исходного (примерно +0,25 с по медиане); его p95 остаётся ниже ориентира 3 с. Это явный компромисс ради устойчивого первого открытия, а не заявление об ускорении всех режимов.**

## Корректность и регрессии

Проверены **87 серверных тестов SQLite и 51 PostgreSQL** — 138 методов, без включения пропущенных PostgreSQL-классов в число SQLite-проверок. Сохраняются точные суммы/null, активная 12 вместо 10+12, история, атомарность исправлений, конкурирующие изменения, ограниченный инспектор, неизменность исходных фактов и аудит. Новый тест подтверждает, что БД запрещает связать строку с версией другого документа: оптимизированное соединение опирается на этот проверяемый инвариант.

**14 браузерных сценариев**, по семь на каждом backend, включают календарь месяц/неделя/день, выезды, импорт, версии, права, отчёты и новую последовательность: период/объект → график → исходная строка → текущий состав/история → выгрузка. Отдельно проверены дробные строки без округления, снятие фильтра, видимые основные поля, разделы отчётов, ошибка/повтор/тайм-аут, 1440/390/320 px и отсутствие внешней горизонтальной прокрутки/JS-ошибок.

CI также выполняет прежний полный цикл XLSX **18/30 МБ**, накопление, версии и независимое восстановление; локально повторён отдельный backup/restore ≥150 МиБ. В сравнительном стенде дополнительно накапливаются **24 000 архивных строк** с сохранением активных итогов и проверяется восстановление этой истории в другой PostgreSQL.

## Воспроизведение и ограничения

```bash
python -m unittest discover -s tests -v
python -m tests.pg_environment --image ksu-postgres:test --output var/postgres-checks
python -m experiments.prerelease.run --image ksu-postgres:test --baseline-source /path/to/pr-24-source --output var/prerelease-checks
```

Baseline должен содержать именно `17521cd3386924e1483edd0cf68913998f720a50`; CI извлекает его через `git archive`. Опубликованы только агрегированные метрики, планы, профили и синтетические скриншоты; БД, книги, дампы, сертификаты и окружение в артефакты не включаются. Ссылки на результаты CI размещены в отдельном Draft PR.

Аналитика остаётся **предварительной, не официальной отчётностью**. Проверка бизнес-ключа и исторических пересечений владельцем процесса, ручная приёмка реальных типовых документов, инфраструктурные решения и выпуск остаются отдельными условиями. Дробное количество не даёт оснований автоматически присвоить единицу измерения или округлить источник. Amvera не запускалась, её настройки не менялись; платные ресурсы не создавались, PR не объединялись.

# Интернет-пилот Amvera — задача №4

## Статус

Выбран Amvera, бюджет владельца — **не более 500 ₽ за 30 дней**, только вымышленные данные. Oracle исключён; эта ветка основана на `main` и не содержит Oracle Terraform или действий создания Oracle-ресурсов. Переиспользованы только общие решения безопасности/HTTPS/резервирования. UI и схема таблиц SQLite сохранены; календарь №2 и Битрикс24 №3 не разрабатывались.

**На Amvera приложение ещё не создано/не опубликовано. Платные ресурсы не запускались.** Владелец сообщил, что аккаунт Amvera есть, но он не авторизован в этой среде. Сетевой прокси отклоняет сайты/API Amvera и `api.github.com`; подготовленный черновик разрешений ещё не применён. Локальный контейнер и тестовый TLS-прокси не считаются публичным развёртыванием, доступом из РФ или проверкой физических устройств.

## Смета до подтверждения запуска

Из актуального текста issue #4 (решение владельца от 01.11.2026): «Начальный Плюс», 0,5 vCPU, 1 ГБ RAM, 7 ГБ SSD, опубликовано 490 ₽/30 дней и 0,68 ₽/час. **0,68 × 720 часов = 489,60 ₽**, остаток до лимита — 10,40 ₽. Это предварительная арифметика, а не полученная из аккаунта оферта. Страница https://docs.amvera.ru/general/price.html пока недоступна из среды; окончательную ставку/НДС/регион/порядок начислений агент проверяет через аккаунт перед предложением владельцу подтвердить платный запуск.

- Одна реплика, один worker, без дополнительной БД, VPS, Caddy-сервера, платного домена или хранилища. HTTPS и бесплатный домен предоставляет Amvera.
- Дополнительный 1 ГБ по указанным в issue 35 ₽/30 дней нарушит бюджет. Live SQLite ограничена 256 MiB; `/data` консервативно ограничен 2 GiB, локальные копии — две. Превышение блокирует запись с 507; лимиты не увеличиваются автоматически.
- 30 дней — ровно 720 часов, не календарный месяц из 31 дня. Дата старта, крайний срок остановки и подтверждённая сумма должны быть зафиксированы перед запуском.
- **Ни Docker CPU/memory, ни `budget.py`, ни остановка процесса внутри контейнера не являются банковским/провайдерским ограничением списаний.** Приостановку/остановку ресурса на стороне Amvera, отключение автопополнения и поведение при исчерпании баланса агент обязан проверить в аккаунте. Не обещать автоматическую остановку биллинга без такой проверки. Новые платные услуги/продление/превышение — только отдельное подтверждение владельца.

## Действия владельца — только авторизация и подтверждение оплаты

1. В защищённых настройках среды заполнить подготовленное несекретное поле `AMVERA_LOGIN` и секрет `AMVERA_PASSWORD`, затем применить настройки. Секрет направляется только `id.amvera.ru`; не передавать его в чат, issue, GitHub или исходники. Подготовлены сетевые разрешения для Amvera/GitHub; их применение — разрешение доступа среды, не запуск платного приложения.
2. Если MFA/политика аккаунта не допускает вход официального CLI, владелец подтверждает разрешённый способ авторизации в интерфейсе Amvera. Не отключать MFA и не просить одноразовые коды в чате. Предпочитать выделенную учётную запись/доступ к пилоту, если это поддерживает тариф; доступность и права ещё не проверены.
3. Агент после авторизации сам читает тарифы, готовит настройки существующего/нового приложения и предъявляет точную смету. Владелец отдельно подтверждает создание/старт тарифа и пополняет счёт, если это требуется. Пока такого подтверждения для конкретного ресурса нет — ничего платного не создавать.
4. Если нужен доступ Amvera к GitHub, владелец только подтверждает OAuth/доступ к **этому одному** репозиторию в интерфейсе. Настройки, файлы, команды, секреты CI и GitHub выполняет агент; пользователь не должен запускать терминал или создавать PR вручную.

Официальный CLI `amvera-cloud/cli` v1.2.3 изучен через help; архив сверён с опубликованным SHA256 GitHub-релиза. Его login поддерживает user/password, а не проверенный нами device-code flow. Реальная авторизация и совместимость с MFA пока не проверялись. Нельзя считать наличие поля токена или неподтверждённый URL готовым подключением.

## Конфигурация приложения (выполняет агент после доступа)

`amvera.yml` выбирает Docker, `Dockerfile`, внутренний порт 8000 и постоянное монтирование `/data`. Формат соответствует доступным примерам/контракту задачи; принятие файла реальным валидатором Amvera ещё не проверено из-за отсутствия доступа. `replicas=1` задаётся в Amvera; внутри `/data` действует дополнительный exclusive lock, отвергающий второй экземпляр на том же томе.

Dockerfile закреплён digest Python 3.12 slim, использует frozen constraints, устанавливает кириллический шрифт. `.dockerignore` разрешает только необходимые исходники: `.git`, пароли, локальные БД, ключи и фото не отправляются в build context. Сессионный CA при локальной сборке передаётся отдельным build secret, не сохраняется в слоях. Нельзя отключать TLS/checksum/signature verification.

Начальная подготовка `/data` выполняется контейнерным bootstrap, затем PID 1 и API работают как UID/GID 10001. База/аккаунты/копии 0600, каталог 0700. Публичный код в образе доступен на чтение после исправления исходных режимов 0600 из checkout. Файлы данных в образ не входят.

Настройки аккаунта приложения, без секретов в Git:

| Переменная | Значение |
|---|---|
| `KSU_ORIGIN` | точный `https://` origin бесплатного домена Amvera, без завершающего `/` |
| `KSU_DB` | `/data/ksu.sqlite3` |
| `KSU_SECURE_COOKIES` | `1` (также принудительно в runtime) |
| `KSU_REQUIRE_INITIALIZED` | `1` |
| `KSU_BOOTSTRAP_DEMO` | `1` только на первом согласованном запуске; затем агент удаляет переменную |
| `KSU_DB_MAX_BYTES` | `268435456` (256 MiB) |
| `KSU_DATA_MAX_BYTES` | `2147483648` (2 GiB) |
| `KSU_BACKUP_KEEP` | `2` |
| `KSU_CONCURRENCY_LIMIT` | `16`; один worker, две рабочие сессии |

Runtime проверяет реальное монтирование `/data`, а не только существование папки. При отсутствии БД без явного bootstrap — отказ, а не новая пустая база. Если файл аккаунтов сохранился, а БД пропала — отказ/восстановление. Повторный bootstrap не заменяет записи и пароли. Инициализация аккаунтов/справочников атомарна.

База и фото живут в `/data`; файл `/data/demo-accounts.txt` содержит только случайно созданные тестовые аккаунты и извлекается агентом через разрешённый доступ без записи в логи/CI/репозиторий. Никакого публичного маршрута к нему нет. Создание долгоживущих аккаунтов сотрудников/корпоративных данных не входит в пилот.

API слушает `0.0.0.0:8000` внутри контейнера; наружу его публикует HTTPS ingress Amvera. Secure/HttpOnly/SameSite Strict cookies, Origin/CSRF, Host allowlist и ограничения API сохраняются. Forwarded IP не считаются доверенными автоматически: CIDR ingress не угадывается и wildcard `*` не включается. Приёмка должна проверить сохранение публичного Host на ingress. Статический сервер `/data` не включён; исходники/секреты/БД закрыты.

## GitHub → Amvera

`ksu-tests.yml` запускает unit/TLS, desktop/mobile и отдельный контейнерный тест с 0,5 CPU/1 GiB. `.github/workflows/ksu-amvera-release.yml` доставляет **только успешный актуальный commit main** после KSU server tests в уже существующий подтверждённый проект. Устаревшие/внешние fork-commit отвергаются. По умолчанию job выключен: `KSU_AMVERA_RELEASE_ENABLED` отсутствует.

После авторизации/проверки тарифа/подтверждения платного запуска агент:

- создаёт или выбирает приложение и проверяет одну реплику/постоянный том/домен;
- настраивает protected environment `amvera-pilot` и разрешения;
- задаёт проверенный `AMVERA_GIT_URL` без user/password в URL, фактическую ветку приёмника, безопасные Git credentials либо использует штатную GitHub-интеграцию Amvera;
- только затем включает release flag. Скрипт `release.py` не создаёт приложения, не меняет тариф, не масштабирует, не пополняет баланс, не делает force push. Git credentials передаются через временный ASKPASS из защищённых bindings, не сохраняются в URL/файлах кода/выводе.

Совместимость Git endpoint/прав/ветки будет проверена после доступа; CI-релиз ещё не выполнялся. Не включать одновременно два конкурирующих автоматических механизма доставки.

## Копии, внешний независимый экземпляр и восстановление

В issue отмечены провайдерские копии `/data` только за два дня; их доступность и восстановление агент проверяет в аккаунте. Они не заменяют независимую копию вне Amvera.

- Supervisor делает проверенный SQLite snapshot при старте и раз в сутки, хранит две собственные `daily-*` копии. После неуспешного нового snapshot старые не удаляются. WAL, фото, исходные импорты, журнал и права попадают в единую консистентную БД. Сессии/счётчики входа на копии очищаются.
- `POST /api/admin/backup` требует аккаунт руководителя, HTTPS/session и CSRF; исполнитель/анонимный пользователь не могут выгрузить БД. Экспорт ограничен 16 MiB и одним одновременным формированием. После отправки временная копия удаляется. Большая копия блокируется и требует отдельного решения, а не платного увеличения квот.
- `independent_backup.py` проверяет структуру/integrity/FK и шифрует копию **AES-256-GCM CMS** публичным сертификатом владельца. Приватного ключа расшифровки в CI нет. Временный cleartext удаляется, в artifact публикуется только ciphertext. Локально проверены расшифровка и полное совпадение БД.
- `.github/workflows/ksu-amvera-backup.yml` по умолчанию выключен (`KSU_BACKUP_ENABLED` отсутствует). После проверки бесплатных GitHub allowance агент настраивает Origin, защищённый пароль тестового manager и публичный сертификат. Максимум 16 MiB × 7 суток ≈112 MiB, но квоты аккаунта общие: до включения агент проверяет остаток бесплатного хранения и запрещает платное превышение. Расписание не включалось и копии в GitHub ещё не создавались.
- Потеря приватного ключа делает encrypted copies невосстановимыми. Агент готовит ключ владельцу через безопасное хранилище при фактическом подключении, не коммитит его и проверяет восстановление до включения расписания.

Восстановление выполняет агент: остановить приложение на стороне Amvera, сохранить текущую копию, восстановить выбранную SQLite **в новый путь** через `python -m server restore`, проверить оба аккаунта, фото, историю и отчёты, затем переключить `KSU_DB` на восстановленный файл. Исходную БД/том не удалять. Само завершение процесса не доказывает остановку биллинга — статус ресурса проверяется отдельно.

## Реальные проверки и оставшаяся приёмка

Локальный Docker-образ тестировался с реальными cgroup 0,5 CPU и 1 GiB, readonly rootfs, постоянным volume и tmpfs. Сценарий: две сессии, 1000 строк инвентаризации, JPEG 4000×3000, одновременные XLSX/PDF/чтение/фото. Метрики — [AMVERA_BENCHMARK.json](AMVERA_BENCHMARK.json). Это небольшой прогон, не SLA и не измерение сетевой задержки из РФ.

Контейнерный тест также проверяет TLS с доверенной тестовой CA без insecure flags, UID 10001, отказ второй реплики, приватные API/файлы, перезапуск, удаление/создание нового контейнера на том же томе, сохранность фото/журнала, отдельную копию и восстановление. Исправлен найденный отказ из-за режимов исходников 0600. Unit-тесты проверяют бюджет, лимиты, отказ тихого сброса, атомарность bootstrap, права на экспорт и authenticated encryption/decryption. CI-конфигурация подготовлена; удалённый GitHub Actions run не объявляется выполненным без подтверждения.

После авторизации агент обязан выполнить **настоящую Amvera-приёмку**: проверить финальный тариф, подтверждение платного запуска, parser amvera.yml, фактическую ФС `/data` и UID/права, HTTPS сертификат/Host/headers, два аккаунта, UI с ПК/мобильного контекста, restart и rebuild из GitHub, сохранность записей/фото/журнала, внешнюю зашифрованную копию и восстановление. Затем проверить URL из РФ и, отдельно, физический телефон. Локальный bind volume не доказывает идентичные гарантии ФС провайдера.

Публичный HTTPS URL и реальные затраты появятся в отчёте только после этих действий. Пока задача №4 не закрыта.

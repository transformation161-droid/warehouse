# PostgreSQL: локальная миграция и независимое восстановление (#9, #14)

Основа — `feat/issue-17-visit-calendar`, `c16e2cd`: календарь, самостоятельное планирование
и реестр решений сохранены. Это дополнительный локально проверяемый backend, **без переключения
работающей Amvera**. По умолчанию прежняя команда запуска остаётся на SQLite. PostgreSQL
выбирается явно через приватную переменную `KSU_DATABASE_URL`; образ `Dockerfile.postgres`
отказывается запускаться без неё. Запуск приложения не создаёт схемы, пользователей или ресурсов.

## Данные и граница доступа

- Те же API и ID, коллекция `visits`, календарные даты, версии, mutationId/body_hash и аудит.
  JSON хранится как исходный TEXT с проверкой JSONB: перенос не меняет сериализацию старых записей.
  Фотографии/миниатюры — BYTEA с побайтовой сверкой, не PostgreSQL large objects.
- `server/postgres/001_initial.sql` устанавливается отдельно администратором одной транзакцией.
  Исторический `schema.sql` (Supabase) не используется. Runtime проверяет версию схемы и наличие RLS.
- Runtime — LOGIN, NOSUPERUSER, NOINHERIT, NOBYPASSRLS, без CREATE ROLE/DB/REPLICATION,
  владения объектами и членства в других ролях. Он не может менять роли сотрудников,
  справочник назначений, аудит или удалять первичные записи.
- Сессия API задаёт ID через transaction-local `set_config`; роль берётся функцией из активного
  пользователя БД, а не из JSON клиента. RLS ограничивает чтение и запись по объекту/автору/назначению.
  SQL-триггеры сохраняют правила стадий, выездов, версий, неизменяемого акта и append-only аудита.
  Подключение сервера — доверенная граница: DB credentials не выдаются конечным пользователям.
- Доступ к журналу отделён от `state_revision()`: чужое событие не раскрывается, но доступный
  общий выезд своевременно обновляется в браузере. Исходники чужих импортов закрыты RLS;
  дедупликация получает только boolean, карточка разрешённой строки — только метаданные стилей.
- Для совместимости с SQLite запись пока сериализуется advisory transaction lock. Это сохраняет
  409/idempotency/atomic batch, но **не является обещанием высокой параллельной пропускной способности**.
  Используется один API worker; локальные задания XLSX пока не распределённая очередь.
- Для внешнего PostgreSQL требуется `sslmode=verify-full` и доверенный CA. DSN только в приватной
  среде, без URL в Git/логах/аргументах pg_dump. Неявные service profiles не поддерживаются.

## Перенос: только в пустой подготовленный PostgreSQL

Команды выполняет администратор на локальной синтетике; доступы передаются через закрытый
`.env.pg` **вне Git**, не значениями в командной строке. Нужен Python из образа, а не на компьютере:

```sh
docker build -f Dockerfile.postgres -t ksu-postgres:offline .
# В приватной среде администратора: KSU_PG_ADMIN_DSN, KSU_PG_RUNTIME_PASSWORD,
# KSU_PG_BACKUP_PASSWORD. Новые служебные пароли — случайные, от 20 символов.
python -m server.pg_admin provision-roles --runtime-role ksu_runtime --backup-role ksu_backup
python -m server.pg_admin init --runtime-role ksu_runtime --backup-role ksu_backup
python -m server.pg_admin migrate-sqlite /private/source.sqlite3
```

Приведённые `python -m` также запускаются через `docker run --entrypoint python` с приватным
`--env-file`, read-only mount подготовленного согласованного снимка и приватным рабочим томом. Нельзя
подключать один главный WAL-файл без его sidecar-файлов: это не полный снимок. Для исходной
WAL-базы SQLite Backup API требуется доступ к каталогу и sidecars; подключение к самой БД
открывается mode=ro. Изолированную копию можно подготовить в journal_mode=DELETE для
физически read-only standalone mount, не меняя исходник. Удалённые DSN и контейнеры
из примера не создаются автоматически. Для тестов всё поднимает только локальный harness ниже.

Перенос делает консистентный SQLite Backup API snapshot **в приватном рабочем каталоге на диске**,
не прямую копию открытого WAL-файла. Только эта копия получает обновление схемы старого пилота.
`KSU_PG_MIGRATION_DIR` задаёт рабочее место явно; по умолчанию — приватный подкаталог рядом с источником.
Неизвестные таблицы отвергаются; данные не пропускаются молча. SQLite integrity/FK, counts и SHA-256
каждой таблицы сверяются с PostgreSQL в одной транзакции COPY. Сортировка для checksum — C/binary,
порядок сериализации JSON и BLOB сохранён. При ошибке транзакция откатывается. Сессии/attempts не
переносятся, нужны новые входы. Пользователи и хеши паролей сохраняются.

Источник не изменяется. Повторный перенос в непустой target запрещён. Лимит исходной SQLite
и целевой БД остаётся 256 МиБ по умолчанию; никакого повышения тарифа/лимитов. На PostgreSQL
выполняются консервативные проверки ёмкости перед изменениями/импортом; это admission control,
а не физическая квота PostgreSQL для WAL, индексов и служебных файлов. Нужны отдельные дисковые
квоты и мониторинг администратора. При нехватке места/квоты запись не становится частичной.

## Независимый backup/restore — один формат PostgreSQL

`POST /api/admin/backup` использует новый путь только в режиме PostgreSQL. Прежний SQLite-лимит
16 МиБ не изменён. Требуются manager, действующая сессия, CSRF и Origin. GET/public URL не создаётся.

Настройки: `KSU_PG_BACKUP_DSN` — отдельная read-only роль с BYPASSRLS (никаких прав записи/owner),
`KSU_PG_BACKUP_DIR` — приватный **дисковый** каталог, `KSU_WORK_DIR` — приватное локальное staging.
Пароль backup роли отделён от runtime. `pg_dump` и manifest используют общий exported snapshot.
Архив содержит `database.dump` и counts/checksums, SHA-256 пакета возвращается HTTP-заголовком.
Сессии и attempts исключены. Копия формируется на диске, HTTP отдаёт FileResponse порциями.

Формат `.ksubackup` — ZIP_STORED над custom pg_dump без сжатия: предсказуемый расход памяти,
но BYTEA в дампе может быть примерно вдвое больше исходной SQLite. Новый фиксированный cap
пакета — 512 МиБ, дедлайн инструмента 600 секунд; один backup на БД и один экспорт на API-процесс.
Допуск требует места под dump + пакет + запас; отслеживаются размер и свободный диск во время dump.
Частичные файлы приватны и удаляются; готовый файл публикуется atomic/no-overwrite. Роль inspector
не может вызвать экспорт. При обрыве отправки источник и уже скачанная копия сохраняются.

```sh
# CLI: DSN из приватной среды; для backup используется KSU_PG_BACKUP_DSN.
python -m server.pg_admin backup /private/off-host.ksubackup
# В другом пустом PostgreSQL, KSU_PG_ADMIN_DSN уже указывает только на него:
python -m server.pg_admin restore /private/off-host.ksubackup --runtime-role ksu_runtime
```

Восстановление принимает только доверенный администратором pg_dump: дамп содержит исполняемый SQL.
Проверяются формат/состав архива и SHA до pg_restore, `--single-transaction --exit-on-error`, затем
все таблицы/ограничения/пустые сессии и выдача ограниченных прав runtime. Непустой target не заменяется.
Если последующая проверка не прошла, экземпляр **не запускать**, диагностировать отдельно; источник
и независимая копия не перезаписываются. `KSU_PG_RESTORE_DIR` — отдельное дисковое рабочее место.

Копию хранить вне исходного сервера и Git, с доступом только владельца/администратора, на шифрованном
носителе (например, BitLocker). Пакет сам по себе не шифрует данные: он содержит фото и хеши паролей.
Нужны утверждённый владелец ключей, срок хранения и периодическая репетиция восстановления;
провайдерские 7 дней backup не заменяют независимую копию.

## Windows без установки Python

Подробно: [POSTGRESQL_WINDOWS.md](POSTGRESQL_WINDOWS.md). В репозитории есть два PowerShell-скрипта:
`tools/Backup-Postgres.ps1` — HTTPS login/CSRF и потоковое скачивание с checksum и ACL, без сохранения
пароля; `tools/Restore-Postgres.ps1` — полностью новый локальный экземпляр, сверка и запуск интерфейса
через заранее подготовленные Docker-образы. Restore работает без Интернета (`--pull never`).
Windows CI проверяет синтаксис скриптов; реальный backend/restore проверен Linux-контейнером.
Интерактивная работа именно Docker Desktop/ACL на компьютере владельца ещё не принималась.

## Проверки и локальные агрегаты

```sh
python -m pip install -r requirements-dev.txt
python -m playwright install chromium
docker build -f Dockerfile.postgres -t ksu-postgres:test .
python -m tests.pg_environment --image ksu-postgres:test --output "$PWD/var/postgres-checks"
CADDY_BIN=/tmp/ksu-caddy python -m unittest discover -s tests -v
```

Harness создаёт только временные локальные контейнеры/роли и вымышленные данные, удаляет их по завершении.
29 real-PG контрактов + 67 прежних SQLite-контрактов. Отдельные пять browser-сценариев запускаются на
каждом backend. PG-проверки включают HTTP/SQL ACL, аудит, даты, конфликты, CSV/XLSX, дедупликацию,
суммы, отчёты, legacy migration на копии и отказ от пропуска неизвестной таблицы.

Большая приёмка: источник 168 148 992 байт, фактически скачанный пакет около 335,6 МБ; второй независимый
PostgreSQL, оба входа, фото, таблицы/checksums, история, CSV/XLSX/PDF, финансовый CSV и повтор CSV/XLSX
без дублей после restore. Проверяются inspector/CSRF/Origin, обрыв скачивания, дедлайн/byte cap без
публикации partial, повреждённый пакет и непустой target. **Весь стенд** (две БД + API + клиент + инструменты)
работает в одном cgroup: 0,5 CPU / 1 ГиБ, /tmp 32 МиБ, read-only root, сеть отключена, непривилегированный UID.
Данные/снимки лежат на дисковом томе. Агрегаты — `postgres-backup-metrics.json` в артефакте CI;
базы, пакеты, пароли и сертификаты туда не загружаются. Raw cgroup peak включает page cache и небольшие
пакетные превышения учёта ядра; отдельно публикуются anonymous peak и OOM kills (0).

Полный нагрузочный прогон именно PG-импорта книг 18/30 МБ не подменяется этой проверкой большой БД:
здесь проверены контракты импортов и большая автономная копия, включая реестр решений. Для production
нагрузочного SLA нужен отдельный профиль реальных объёмов на согласованной инфраструктуре.

## Безопасный будущий cutover, rollback и PWA

1. Утвердить регион, доступ, TLS, бюджет, резервирование и RPO/RTO. Не менять Amvera сейчас.
2. Завершить активные импорты, заморозить запись, снять независимую копию; старый источник оставить.
3. Перенести в пустой PostgreSQL, сверить counts/checksums, роли, фото, аудит, суммы/отчёты; выполнить restore.
4. Только после отдельного разрешения переключить конфигурацию приложения и запросить новый вход.
5. До открытия новых записей rollback — прежний код/конфигурация и неизменённая SQLite. После новых
   записей нельзя просто вернуть старый SQLite: нужен restore PostgreSQL/совместимый код. Обратная
   миграция PostgreSQL → SQLite не реализована, автоматического rollback/cutover нет.

ID, expectedVersion и mutationId остаются стабильны; после смены сессии очередь IndexedDB может
повторить запрос с новым CSRF. Применённый mutationId не дублируется; 409 требует сравнения копий,
а не last-write-wins. Это база будущей PWA, не реализация полного offline-first/service worker.

Параметры размещения и смета: [POSTGRESQL_OPTIONS.md](POSTGRESQL_OPTIONS.md).

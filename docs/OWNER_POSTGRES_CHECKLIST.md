# Владелец: запуск на managed PostgreSQL

SQLite-выпуск №36 остановлен: `/data` Amvera не поддерживает WAL. Приложение сейчас
остановлено, активных пользователей нет. Ни платная PG, ни merge/deploy пока не разрешены.
Подробные команды и откат: [POSTGRES_PRODUCTION.md](POSTGRES_PRODUCTION.md).

## До заказа и внедрения согласовать

- Бюджет: ориентир **1 016 ₽/30 дней** за существующее приложение + одну PG-реплику
  1 ГБ RAM + пример storage 2 ГБ. Это превышает прежние 500 ₽; подтвердить калькулятор/регион,
  число реплик и стоимость backup/storage. Автоувеличение и дополнительные сервисы не заказывать.
- Отдельное разрешение на создание managed PG17 и отдельно go/no-go ручного внедрения.
- У Amvera: CA и SAN/hostname для TLS verify-full с приложения и Windows, совместимость
  shipped libpq17/pg_dump с выбранным endpoint, право bootstrap создать три обычные роли.
  При ALPN/TLS-ошибке не отключать проверку сертификата и не начинать импорт.
- Штатный managed PG backup ежедневно/глубина/процедура restore; допустимые RPO/RTO,
  ответственный и защищённый внешний носитель. Без постоянно включённого узла ежедневная
  независимая копия вне провайдера не гарантирована. Одна реплика не даёт HA.

## Действия после соответствующего разрешения

1. **Сохранить остановленную установку.** Не запускать SQLite/WAL на `/data`. Скачать полный
   frozen-набор и текущую конфигурацию/образ в защищённый каталог владельца. Получить
   standalone backup через `New-Offline-Backup.ps1` с новым образом и точным относительным
   путём SQLite. Integrity/FK и хеши должны пройти; при повреждении разбирать provider-копию.
2. **Создать одну новую PG17** в кабинете Amvera: согласованный тариф/регион/БД/initial owner.
   Не создавать pgAdmin/VM/CronJob. Записать реальные endpoint/CA и конфигурацию приватно.
3. **Подготовить образ и секреты.** Скачать managed source bundle успешного CI, сверить SHA/
   manifest, собрать `ksu-managed:rc`. В приватном owner-only каталоге вне Git создать
   отдельные bootstrap/admin/backup env и JSON трёх новых служебных паролей. Реквизиты,
   CA/пароли/backup не передавать в чат, Codex, GitHub/Actions или Code/Artifacts.
4. **Bootstrap → migration → verify.** Через `Invoke-ManagedPostgres.ps1` создать три роли,
   перенести закрытую копию в пустую PG, сверить `migration.json` и все 16 fingerprints.
   Пароли сотрудников, пользователи, фото, audit, receipts сохраняются; сессии копии очищаются.
   При отказе не повторять поверх частичной схемы, сохранить отчёты и исходник.
5. **Backup → independent restore.** Выполнить owner backup ролью `ksu_backup`, затем
   `Test-ManagedPostgresBackup.ps1`: новая локальная Docker PG, без портов/облачного admin,
   совпадение SHA/всех таблиц/constraints/пустых сессий. Сохранить приватный `restore.json`.
   Измерить RTO. Успех pg_dump без restore не является допуском.
6. **Подготовить существующее приложение.** Отключить внешнюю автодоставку и старые backup/
   deploy Actions до будущего merge. По отдельному разрешению вручную доставить managed
   bundle. Передать только runtime DSN с verify-full; убрать KSU_DB, admin/backup/PG default
   credentials, SQLite daily mode. Одна реплика, UID10001, origin прежний, стабильный production
   deployment ID, offline/viewer сначала off. Старую SQLite сохранить, не открывать её.
7. **Короткий smoke переноса:** health build/SHA и backend=postgresql, вход прежними manager/
   inspector, выбранные старые акт/фото/отчёты/history/receipts. Включить персональные viewer ACL,
   проверить свои/чужие данные и запрет записи. Полную UI/PWA-приёмку 8020 не повторять.
   Только затем разрешить записи; offline pilot включить по утверждённым inspector IDs.
8. **Эксплуатация:** ежедневно смотреть свежесть provider backup, место/ошибки/receipts;
   независимый backup+restore выполнять по согласованному порядку и перед обновлениями.
   Отключить старую Windows SQLite-задачу и health по точным именам, сохранив файлы/профили.
   PG owner tools используют process-only ExecutionPolicy Bypass; глобальную политику не менять.

До первых новых PG-записей можно отменить переход, сохранив исходную установку **остановленной**.
Повторно запускать WAL на несовместимом томе нельзя. После новых PG commits возврат старой
SQLite теряет данные: остановить запись, свежий PG backup/restore и совместимое исправление/
сверка дельты. Автоматической обратной миграции PG→SQLite нет.

Корпоративную миграцию/restore владелец выполняет только у себя. В PR достаточно отметки
«PASS» без файлов/данных. CI доказывает поведение синтетических PostgreSQL-контейнеров,
не наличие/настройки ещё не созданной Amvera PG.

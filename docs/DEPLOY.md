# HTTPS интернет-пилот — задача №4

## Текущее состояние и проверенные границы

Подготовлен исполняемый комплект для Oracle Always Free VM, без смены FastAPI + SQLite. **Публичная VM ещё не создана, публичного URL нет:** аккаунт OCI не подключён; владелец сообщил, что ему нужна регистрация Free Tier. Создание PR через GitHub API также блокируется текущей сетевой политикой (`api.github.com → Forbidden`). Сохранённый черновик сетевых настроек ещё не применён.

Локально реально выполнены: 27 тестов (включая настоящий Caddy HTTPS с проверкой доверенной тестовой CA, два сеанса, перезапуски, фото и восстановление), оба браузерных сценария desktop/390 px, Caddy validate, Terraform validate и 3 mock-плана, проверка синтаксиса systemd с подстановкой существующих локальных путей исполняемых файлов, shell/JS/Python-проверки. **Это не проверка публичного адреса или двух физических устройств.** Установка root-служб на настоящей Ubuntu ARM VM, Let's Encrypt, DNS и OCI apply ещё не выполнялись.

Выбор и ограничения бесплатности: [FREE_HOSTING.md](FREE_HOSTING.md). Календарь и Битрикс24 не входят в этот этап; интерфейс, бизнес-логика и схема SQLite не менялись.

## Неизбежные действия владельца

1. Зарегистрировать собственный [Oracle Cloud Free Tier](https://www.oracle.com/cloud/free/), включить MFA, не переходить на paid/PAYG. Возможные действия проверки личности/платёжного средства выполняются только на стороне Oracle. Не отправлять пароли, карточные данные, OTP или приватные ключи в чат. Если условия требуют неприемлемого финансового действия, остановиться.
2. После регистрации подтвердить технический API-доступ: в OCI Console, профиль пользователя → API Keys → Add API Key загрузить **подготовленный агентом публичный ключ**. Приватная часть хранится только в исключённой из Git закрытой папке среды. После подключения этот ключ даёт права пользователя OCI, поэтому предпочтителен выделенный технический пользователь/политика для пилота. Требуется явное согласие владельца на подключение; не создавать ключ от имени другого владельца.
3. Передать агенту несекретный сгенерированный OCI configuration snippet (user OCID, tenancy OCID, fingerprint, region; **без private key**). Публичный ключ и локальный путь приватного ключа не коммитятся. Передать также домашний регион, если он отличается от показанного в профиле. Программирование, команды, Terraform, установку и GitHub выполняет агент.
4. В настройках среды применить подготовленные сетевые разрешения для GitHub API/официальной документации. После выбора региона агент добавит точные OCI API endpoints, затем — разрешение защищённого SSH/HTTPS-доступа к конкретной VM. Не требуется открывать весь Интернет. Изменение настроек среды не равно публикации приложения.

Остальные пункты ниже — **runbook агента/администратора**, а не задания владельцу выполнять команды.

## Провижининг (только после доступа и проверки нулевой стоимости)

- `deploy/oracle/main.tf`: фиксированы A1 1 OCPU / 6 GB, Ubuntu 24.04, boot 50 GB + data 50 GB; сеть с Internet Gateway, без NAT/LB/managed DB. SSH — только IP агента `/32`; публичны 80/443, API-порт 8000 не открыт. Data volume защищён `prevent_destroy`.
- `free_tier_verified=false` по умолчанию блокирует план; запуск вне home region тоже блокируется. Агент проверяет актуальный тариф, пометку Always Free, все оставшиеся суммарные квоты и свободную ёмкость, затем сохраняет план. Terraform не является гарантом стоимости и не знает всех ресурсов аккаунта.
- В ignored `.tfvars` агент задаёт только необходимые несекретные идентификаторы/SSH PUBLIC key. Аутентификация идёт через закрытую OCI-конфигурацию; приватные ключи не передаются как Terraform variables, metadata или `user_data`. State/plan/локальные значения исключены из Git.

```sh
terraform -chdir=deploy/oracle init -lockfile=readonly
terraform -chdir=deploy/oracle validate
terraform -chdir=deploy/oracle plan -out=pilot.tfplan
# Только после проверки плана агентом и подтверждённой бесплатности:
terraform -chdir=deploy/oracle apply pilot.tfplan
```

Если нет бесплатной ёмкости, остановиться. Не менять shape на платную, не повышать аккаунт, не включать оплату автоматически. В этой сессии `apply` не запускался.

## Постоянный том и код

1. После создания проверить ID/размер нового data volume и его paravirtualized attachment. На VM сверить `/dev/oracleoci/oraclevdb`, `lsblk`, `blkid`, отсутствие любых данных/разделов/монтирований. **Никогда не форматировать том по одному имени устройства и не трогать boot volume.** Только подтверждённо новый пустой 50 GB data volume форматируется ext4 и монтируется по UUID в `/srv/ksu-data`; запись `fstab` обеспечивает повторное монтирование.
2. Подготовить `git archive` точного проверенного commit, доставить без `.git`, `.venv`, `var`, `.env` в `/srv/ksu/releases/COMMIT`. Проверить checksum архива и commit; нельзя включать локальные аккаунты/БД/ключи в релиз. Не создавать worktree без отдельного запроса.
3. Бесплатный hostname: `ksu.IP-WITH-DASHES.sslip.io`, либо подтверждённый собственный домен. Проверить A-запись и отсутствие чужого IP/неожиданной AAAA. `sslip.io` — внешний бесплатный DNS с собственными ограничениями и без SLA; при отказе сервиса не покупать домен автоматически.
4. Агент запускает на VM `sudo deploy/install_vm.sh HOSTNAME /srv/ksu/releases/COMMIT` из доставленного релиза. Установщик требует Ubuntu 24.04 и уже смонтированный локальный ext4/xfs data volume, не форматирует диски и не удаляет данные.

Установщик ставит зависимости через подписанный APT и закреплённые Python constraints, проверяет официальный SHA512 Caddy 2.11.7, создаёт непривилегированные `ksu`/`caddy`, проверяет Caddyfile, инициализирует тестовые аккаунты только при отсутствии БД, делает копию перед обновлением, переключает symlink `current`, устанавливает systemd-службы и таймер. Код/root-owned releases отделены от данных; секреты не копируются в checkout. Скрипт сохраняет существующие OCI firewall/metadata rules, добавляя только 80/443, не flush-ит firewall.

## HTTPS и границы доступа

- `deploy/Caddyfile` — только reverse proxy, **без file_server**. Caddy хранит сертификаты в `/var/lib/caddy`, обновляет их автоматически; Let's Encrypt требует рабочие DNS и входящие 80/443. В конфигурации нет платного сервиса сертификатов.
- FastAPI слушает `127.0.0.1:8000`. `KSU_ORIGIN=https://HOSTNAME`, `KSU_SECURE_COOKIES=1`, `KSU_REQUIRE_INITIALIZED=1`. При пропаже тома/БД сервис отказывает в запуске вместо создания пустой базы; systemd дополнительно требует mountpoint.
- `KSU_TRUST_LOCAL_PROXY=1` доверяет forwarded headers только от loopback Caddy; внешний клиент не должен иметь прямого доступа к 8000. Caddy самостоятельно формирует цепочку forwarded IP; не включать глобальное доверие к клиентским заголовкам.
- Сессии HttpOnly/Secure/SameSite Strict, Origin + CSRF, Host allowlist, HSTS, CSP. Статически доступны только перечисленные HTML/CSS/JS. Фото требуют входа и назначения объекта.
- Два тестовых пароля генерируются **на VM**, файл `/srv/ksu-data/demo-accounts.txt` имеет 0600 и не раздаётся по HTTP. Агент передаёт их владельцу безопасно, не публикует в GitHub/логах/PR. Публичные данные пилота строго вымышленные.

## Приёмка настоящего адреса (выполняет агент)

`deploy/accept_live.py` проверен тем же локальным настоящим TLS-стеком. Он генерирует только синтетическую картинку и записи на объекте `ДЕМО`, использует две независимые сессии и полноценную проверку сертификата/hostname. Пароли получает через защищённые process bindings `KSU_TEST_MANAGER_PASSWORD` / `KSU_TEST_INSPECTOR_PASSWORD`; не через CLI, Git или shell history. В публичном режиме используются стандартное системное доверие и унаследованный разрешённый HTTPS-прокси; нет флага отключения TLS.

1. Проверить публичный HTTPS сертификат, HTTP→HTTPS, health, HSTS/CSP; без входа API/фото → 401, `.env`/БД/исходники/копии → 404.
2. Выполнить `python deploy/accept_live.py --origin https://HOSTNAME --phase create`. Он проверяет, что назначенный руководителем тестовый выезд видит исполнитель, замечание и фото видит руководитель, журнал присутствует; создаёт excluded `pilot-acceptance.json` без паролей.
3. Агент перезапускает `ksu` и Caddy, затем выполняет `--phase verify` с тем же receipt: записи/фото должны остаться. Повторить после смены release symlink и после перезапуска VM/повторного монтирования data volume. Пробы успешны только при реальном достижении URL.
4. Прогнать браузерный сценарий через desktop и мобильный контекст по публичному origin; отдельно владелец при желании открывает полученный URL на физическом телефоне. Два автоматизированных сеанса/эмуляция не обозначаются как проверка двух физических устройств.
5. Только после этих проверок передать итоговый публичный URL и открыть приёмку №4. **Сейчас эти публичные проверки ещё не выполнены.**

## Копии и восстановление

- Ежедневный `ksu-backup.timer` запускает `deploy/rotate_backups.py`: SQLite Backup API, проверка integrity + FK + структуры, сброс сессий/счётчиков попыток на копии, атомарная публикация без перезаписи существующего файла, 0600. Хранятся семь `daily-*` копий; удаляются только свои старые копии и только после успешной новой. Ручные/pre-release копии не удаляются.
- Фото, исходные импорты и аудит входят в ту же БД. Обычный `cp` работающей WAL-базы запрещён. При пропаже/повреждении исходной БД новая пустая база не создаётся.
- Отдельная проверенная копия **вне VM** обязательна перед объявлением устойчивости к потере VM. Агент может выполнить `deploy/fetch_backup.py` через уже разрешённый SSH с обязательным host-key checking; он сохраняет ignored локальную копию 0600 и проверяет её. Из среды SSH требует поддержанного TCP grant/proxy; не отключать проверку host key и не обходить сетевые правила.
- Локальные копии на том же томе не защищают от потери этого тома. Сейчас внеоблачная репетиция выполнена на временных каталогах; облачный off-host backup ещё не настроен. Если нужен Object Storage, сначала проверить оставшиеся бесплатные квоты и подготовить отдельную ограниченную политику; не включать тарифицируемые storage/egress автоматически.

```sh
# Агент на VM:
cd /srv/ksu/current
.venv/bin/python -m server backup /srv/ksu-data/backups/manual-UNIQUE.sqlite3 --db /srv/ksu-data/ksu.sqlite3
# Восстановление всегда под НОВЫМ путём, без замены действующей БД:
.venv/bin/python -m server restore /srv/ksu-data/backups/CHOSEN.sqlite3 /srv/ksu-data/restored-UNIQUE.sqlite3
```

Остановить службу, сохранить текущую проверенную копию, восстановить выбранную в новый путь, протестировать оба аккаунта/записи/фото/аудит/отчёты через временный запуск. Только затем изменить `KSU_DB` и перезапустить. Старые сессии должны стать недействительны. Для отката кода переключить `current` на совместимый предыдущий релиз; схема БД этим этапом не менялась. При неудаче не удалять исходную БД или том.

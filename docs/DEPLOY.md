# Подготовка HTTPS-размещения и откат

Это инструкция для администратора согласованного сервера. Фактическая публикация не выполнялась. Сначала тестовый пилот, только синтетические данные. Разрешение владельца инфраструктуры, рабочие аккаунты, домен, правила хранения и резервного копирования необходимы до обработки корпоративных данных.

## Один сервер Linux

1. Подготовьте Python 3.12+, `fonts-dejavu-core` (кириллица PDF), локальный постоянный диск; установите согласованный HTTPS-прокси Caddy. SQLite нельзя хранить на NFS/сетевой папке и использовать для нескольких независимых реплик.
2. Создайте системного пользователя `ksu`. Код разместите в `/srv/ksu`, данные — `/srv/ksu-data` с владельцем `ksu` и правами 0700. Не используйте Git worktree без отдельного запроса: обычного checkout достаточно.
3. В `/srv/ksu`: `python3 -m venv .venv`, затем `.venv/bin/python -m pip install -r requirements.txt`. Запустите API- и браузерные проверки из README на тестовой БД.
4. Инициализируйте **тестовые** аккаунты командой `.venv/bin/python -m server init-demo --db /srv/ksu-data/ksu.sqlite3` под пользователем `ksu`. Пароли вводятся без отображения. Не используйте константы из тестов. В этой версии нет публичной регистрации или изменения роли через браузер. Для рабочих пользователей нужен отдельный согласованный процесс администрирования/SSO.
5. Создайте `/etc/ksu/ksu.env`, владелец root, чтение только группе службы (0640). Пример настроек в `.env.example`. Сам файл `.env` автоматически не читается.

```ini
KSU_DB=/srv/ksu-data/ksu.sqlite3
KSU_ORIGIN=https://ksu.example.org
KSU_SECURE_COOKIES=1
```

6. Замените домен в `deploy/Caddyfile`. Настройте DNS, корпоративный сертификат или одобренную выдачу сертификата. Конфигурацию проверяйте `caddy validate --config /path/to/Caddyfile`. При стандартном ACME Caddy понадобится согласованный сетевой доступ к центру сертификации.
7. Установите `deploy/ksu.service`. Служба слушает **только 127.0.0.1:8000**, доступ извне — через HTTPS-прокси. `KSU_ORIGIN` обязан в точности совпадать с публичным origin (схема, домен и нестандартный порт). Нельзя отключать Secure cookies для HTTPS. CORS не включён, API и интерфейс обслуживаются с одного origin. Прокси должен сохранять исходный Host. Переданные IP-заголовки приложением не считаются доверенными.
8. Проверьте службу и HTTPS health-check; проверьте cookie `HttpOnly; Secure; SameSite=Strict`, заголовки CSP/HSTS и два независимых аккаунта. Без входа `/api/state`, `/api/reports/xlsx`, `/api/history`, фото должны быть недоступны. Файлы БД, резервные копии, Python/SQL-исходники нельзя раздавать статическим сервером: публичны только явно перечисленные HTML/CSS/JS.

Предоставленные Caddy/systemd-файлы — примеры; на этой машине нет Caddy/systemd-службы и корпоративного DNS, поэтому реальный TLS и служебные конфигурации ещё не проверены. Разрешены только тестовые данные до отдельной приёмки размещения.

## Резервное копирование

В БД находятся записи, фото, исходные импортированные файлы и аудит. Нельзя копировать только файл работающей WAL-базы обычным `cp`.

```sh
.venv/bin/python -m server backup /srv/ksu-data/backups/ksu-2026-11-01.sqlite3 --db /srv/ksu-data/ksu.sqlite3
```

Используется SQLite Backup API, затем `integrity_check`. Существующий файл не перезаписывается. В копии удаляются активные сессии, чтобы после восстановления нужно было войти заново. Команда копирует все остальные таблицы, включая историю, фото и исходные файлы. Права нового файла — 0600. Папка резервных копий должна быть закрытой (0700).

Примеры ежедневного расписания: `deploy/ksu-backup.service` и `.timer`. Проверьте `systemd-analyze verify` в целевой системе до включения. Администратор настраивает защищённую внешнюю копию, шифрование, срок хранения, мониторинг успешного создания и регулярную тренировку восстановления. Один локальный файл не защищает от потери сервера. Автоматическое удаление старых копий здесь не включено, чтобы не удалять их без согласованной политики.

## Проверяемое восстановление и откат

1. Остановите службу. Создайте проверенную копию текущего состояния и сохраните версию кода. Сохраните пользовательские незакоммиченные изменения, если они есть.
2. Не заменяйте рабочую БД вслепую. Сначала восстановите выбранную копию **под новым путём** в закрытой папке; выполните `PRAGMA integrity_check` и `PRAGMA foreign_key_check` через SQLite.
3. Направьте временный тестовый запуск на новую БД через `KSU_DB`; проверьте вход обоих аккаунтов, план, акт, фото, журнал и контрольные суммы отчёта. Старая cookie должна быть недействительна; после входа выдана новая.
4. Для отката кода используйте сохранённую совместимую версию и соответствующую копию БД. Новые миграции в будущем требуют отдельного плана обратимости; автоматического downgrade нет.
5. Только после проверки переключите путь БД в `/etc/ksu/ksu.env` и перезапустите службу. Старую БД и копию не удаляйте до приёмки. Пользователям потребуется повторный вход.

Прямой доступ администратора к SQLite-файлу — доверенная граница. Триггеры обеспечивают дополнительную защиту от ошибок серверного кода, но не делают администратора файловой системы недоверенным пользователем. Отдельные PostgreSQL-роли/RLS нужны при переходе на сетевую БД; исторический `schema.sql` для этого не прошёл приёмку.

## Что согласовать до рабочей эксплуатации

Корпоративный хостинг/БД, домен и сертификат, SSO или управление учётными записями, назначения объектов, хранение фотографий и резервных копий, политика журналов и лимитов, нагрузка, восстановление и бизнес-правила частичного подтверждения/взыскания. Внешние FaceKit, Битрикс24, 1С и БИТ.Строительство не подключаются этой конфигурацией.

# Исправленные XLSX и действующие версии списаний — Issue #21

Основа — `test/issue-20-postgres-large-registry` (PR #22). Календарь, выезды, отдельный реестр списаний,
PostgreSQL и потоковый импорт 18/30 МБ сохранены. Графики/аналитика #15 не добавляются.

## Как исправить документ

1. Руководитель открывает «Списания и решения» → «Импорт XLSX», загружает книгу и проверяет лист,
   диапазон, сопоставление колонок и ошибки. Файл и выбранные строки ещё не записаны в реестр.
2. В «Назначение книги» выбирает полное замещение либо частичную коррекцию, находит конкретный
   документ по объекту/названию/дате/ID и указывает основание. Один акт коррекции относится к одному
   выбранному документу и одному объекту. В частичном режиме отмечает старые строки, которые
   требуется заменить или исключить. Остальные остаются действующими с прежними ID.
   Если в книге несколько документов, выбирает диапазон нужного документа и выполняет коррекции
   отдельно: строки другого действующего акта нельзя случайно добавить в выбранный.
3. Нажимает «Сравнить версии». Согласованный ключ сопоставления: **объект (стабильный siteId) +
   поле «Документ» + исходный ID строки** внутри выбранного документа. Текстовые ID/ведущие нули
   не преобразуются в числа. SHA обеспечивает идемпотентность загрузки; номер Excel служит только
   указателем в текущем файле. Они не выбирают заменяемый документ или прежнюю строку.
4. При пустом или повторяющемся ID открывает ручное сопоставление: выбирает конкретную прежнюю
   запись либо явно подтверждает добавление. Выбор старой строки в частичном режиме включает её
   в набор коррекции. Одна прежняя запись не заменяется двумя новыми. Строки вне выбранного
   документа/объекта не допускаются. Если ID совпал с невыбранной строкой частичного набора,
   сначала нужно включить её в набор.
5. Проверяет добавленные, изменённые, исключённые и неизменённые строки, все поля «до/после»
   и пять итогов: количество, стоимость, остаточная стоимость, к возмещению, возмещено. Отсутствующие
   в новой книге строки исключаются только из явно выбранного набора; при полном замещении —
   из всего документа. Числа суммируются Decimal, включая нули и четыре десятичных знака.
   Пустое значение остаётся пустым в исходной записи; итог суммирует заполненные числа. Изменение
   пустого значения на явный ноль отмечается как изменение, хотя численная сумма не меняется.
6. Отдельно нажимает «Подтвердить версию». После изменения выбора/основания требуется новое
   сравнение. При конкурирующей коррекции старое подтверждение отклоняется: нужно заново сравнить
   актуальный состав. Повтор подтверждённого запроса не добавляет версию или строки.

Реестр по умолчанию и обычный CSV показывают действующие строки. Итоги тоже считаются по ним.
«Версии» открывает автора, основание, изменения и исторический состав; архивные строки помечены
явно. Просмотр старой версии не меняет действующую. На смартфоне таблицы имеют собственную
горизонтальную прокрутку, наборы/сравнения загружаются страницами, ручное сопоставление свёрнуто
до необходимости. Целиком реестр в `/api/state`, DOM или Python list не загружается.

Инспектор сохраняет обычный импорт и чтение разрешённых объектов, включая их версии. Подтверждение
замещения — только manager, с действующей сессией/Origin/CSRF. Чужой операционный аудит по-прежнему
ограничен прежними правилами; журнал версий документа доступен по объекту. При повторном ID
в обычном новом импорте приложение требует явного решения руководителя, а не добавляет вторую сумму.

## Сохранность и атомарность

Исходные `decision_records`, исходный import header и старый audit не изменяются и не удаляются.
Добавлены четыре append-only таблицы: `decision_documents`, `decision_versions`, `decision_entries`,
`decision_retirements`. Связи показывают, какой версией введена новая строка, какую старую она заменяет
и какой версией исключена старая. Отдельное audit-событие содержит автора/время/основание, предыдущую
версию, число изменений и точные итоги. Политики RLS и SQL-триггеры защищают доступ и запрет изменения.

Подтверждение проверяет токен конкретного сравнения, текущую роль, права на объект и parent version,
затем в одной транзакции сохраняет import header, версию, source facts, исключения, связи и audit.
SQLite сериализует записи через BEGIN IMMEDIATE, PostgreSQL — существующим advisory transaction lock.
Уникальны номер версии документа, operation key, физическая исходная строка и факт её исключения.
Ошибка, cap, смерть worker или устаревшая версия не дают частичного действующего результата.

Полный исправленный документ сохраняется целиком, включая неизменённые строки и исходные ячейки:
это происхождение новой книги, а не перезапись прежних фактов. Поэтому архив и audit увеличивают
хранилище. Cap БД 256 МиБ и остальные квоты не повышаются; большая коррекция требует места для
обеих версий и может быть явно отклонена. Пересмотр лимитов — отдельное решение владельца.

## Миграция существующей БД

PostgreSQL schema version теперь **2**. Startup не выполняет DDL и отказывает для v1. Перед будущим
обновлением владелец должен сделать независимую проверенную копию старым образом PR #22,
остановить запись и применить новым образом offline-команду (DSN/пароли — только приватная среда):

```sh
python -m server.pg_admin upgrade --runtime-role ksu_runtime --backup-role ksu_backup
```

Команда создаёт первые версии прежних групп «импорт + объект + поле Документ» и проверяет неизменность
fingerprints всех восьми прежних бизнес-таблиц. Она не угадывает, какие ранее загруженные книги были
исправлениями, не удаляет и не связывает их задним числом. Старые источники и аудит остаются целыми.
Перед публикацией KPI требуется разрешить неоднозначности фактического набора документов владельцем.
В этой разработке используются только заново созданные синтетические БД, эксплуатационный cutover не выполняется.

SQLite обновляется транзакционно при открытии, без повторного seed. Миграция SQLite→PostgreSQL по-прежнему
работает на приватной копии; включает новые связи и не меняет исходный файл.

Независимый `.ksubackup` сохраняет все 12 бизнес-таблиц, связи/исключения, старые строки и audit.
Проверяются counts/SHA, FK и отсутствие сессий. Restore принимает schema v1 и v2: для v1 сначала сверяет
восемь оригинальных fingerprints, затем переводит пустой восстановленный контур в v2 без изменения
этих данных. Пакет v2 требует нового совместимого приложения; старый код безопасно его отклонит.
Целевой PostgreSQL должен быть пустым; доверенный пакет не заменяет действующую БД.

## API и проверки

- `POST /api/decision-imports/{id}/version-preview`: documentId, expectedVersion, full/partial, reason,
  targetIds и ручные matches (Excel-строка текущей книги → прежний record ID; пустое значение — добавление).
  Большое сравнение выполняет ограниченный worker; основная БД пока не меняется.
- `GET .../{id}/comparison?page=&limit=` и `version-inputs` — ограниченные страницы сравнения/новых строк.
- `POST .../{id}/version-confirm` с token актуального сравнения — отдельное подтверждение manager.
- `GET /api/decision-documents`, `/api/decision-documents/{id}/versions` — документы и их версии.
- `GET /api/decisions` по умолчанию active; явные history/documentId/version дают историческое чтение.
  `/api/decisions/totals` и обычный `/api/decisions/export.csv` по умолчанию active. Будущие KPI должны
  использовать тот же предикат `decision_versions.ACTIVE`, а не складывать всю физическую таблицу.

Серверные контракты: `tests/test_decision_versions.py` и `tests/test_postgres_versions.py`.
Браузер: `decision_versions_flow_test.py` на обоих backend, включая смартфон 390 px.
Проверяются 10→12, полный/частичный состав, неоднозначные/пустые ID, другой объект, права, неверный
token/CSRF, два независимых обработчика, ошибка посреди транзакции, SQL guards, upgrade и восстановление.
Дополнительно сохранён стенд `experiments/postgres_large`: нормальные XLSX 18/30 МБ, 22 189 строк,
полная коррекция 18-МБ книги и частичная версия после независимого restore, при прежнем cap.

Локальный снимок: [DECISION_VERSIONS_ACCEPTANCE.json](DECISION_VERSIONS_ACCEPTANCE.json).
Пример 10.0000→12.0000 даёт одну действующую строку и итог 12.0000, две исходные строки сохраняются.
В отдельной книге 18 000 000 байт одного документа — 11 086 строк: изменена одна стоимость на +2,
11 085 строк не изменились. Все 17 полей сверены, архив содержит 22 172 исходные строки. Сравнение —
3,94 с; размер БД после полного замещения — 210,70 МиБ. После независимого restore исходная версия
сохранилась, частичная коррекция дала версию 3 и итог +3 к исходному. Весь расширенный стенд —
606,14 с; anon peak приложения вместе с генератором/клиентом — 251,83 МиБ, OOM kills=0. Каждый
контейнер отдельно ограничен 0,5 CPU/1 ГиБ, swap выключен; total включает файловый cache. Это
локальные измерения, не SLA; CI публикует отдельные агрегаты в `postgres-large-registry`.

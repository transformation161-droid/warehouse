## 2. Сейчас: только сверка владельцем, без изменения настроек

Открыть **существующее приложение** в кабинете Amvera и отдельно уже существующий ресурс БД.
Не нажимать «Создать», «Пересобрать», «Перезапустить», «Восстановить», смену тарифа/реплик.
Не присылать снимок вкладки с секретами. Если вкладка/терминал недоступны — отметить
«не подтверждено»; не устанавливать инструменты в production.

| Где смотреть | Что записать в приватный лист выпуска | Что можно сообщить без секретов |
| --- | --- | --- |
| Приложение → «Репозиторий», «Конфигурация», последние успешные логи сборки | Источник (Git Amvera / GitHub + ветка / файлы), последний delivery commit, Dockerfile/entrypoint; отдельно application source SHA | Способ, ветка, SHA, имя Dockerfile |
| Приложение → адрес/«Домены» (либо «Настройки» → сеть), браузер | Точный прежний HTTPS origin; открыть `/api/health` по нему | `status`, `build`, `backend`, `offline`; сам адрес можно оставить приватным |
| Приложение → «Переменные»/секреты | Какие KSU-привязки реально заданы; приватно проверить user/dbname/host в runtime DSN; не копировать значение целиком | Только имя роли и выбранный transport profile; флаги `KSU_WRITEOFF_ANALYTICS_ENABLED`, `KSU_INVENTORY_PLAN_ENABLED`, `KSU_OFFLINE_MODE`, `KSU_VIEWER_ACCESS` |
| Консоль приложения, если доступна; иначе существующее приватное подключение к БД | Read-only preflight/SQL из [команд](PR46_RELEASE_COMMANDS.md#проверка-существующего-приложения-и-бд) | PG major, schema=4, роль, schema owner, наличие feature markers, результат RLS/preflight |
| Ресурс PostgreSQL → статус, «Бэкапы», «Настройки»/метрики | Это именно БД runtime-подключения; дата последней успешной точки, активность расписания, фактическая глубина, занято/свободно, реплики, текущая стоимость | Время/успех backup, PG major, объём/запас, число реплик; без DSN/дампа |

Health с `backend=postgresql` подтверждает ответ конкретного приложения, но не заменяет
проверку роли/схемы. Delivery commit Git Amvera и встроенный `health.build` могут отличаться:
первый упаковывает source bundle, второй должен равняться его `release-manifest.json.source_sha`.
Если health не содержит этих полей, определить образ/исходник по успешной сборке и консоли;
не принимать название ветки за доказательство версии. Не печатать `env`, `printenv`, Docker
`Config.Env`, полный DSN или логи с паролями.

## 3. Совместимость и GO/STOP

**GO возможен только после заполнения всех неизвестных полей и отдельного согласования.**
Минимальная подтверждённая конфигурация:

- Существующая PostgreSQL **17**, схема `ksu` **v4**, те же пользователи/ID/хеши паролей,
  объекты, назначения, медиа, аудит, версии и receipts. Все 16 бизнес-таблиц входят в backup;
  сессии/attempts намеренно исключаются из пакета и при независимом restore пусты.
- `ksu_admin` владеет схемой; приложение работает как `ksu_runtime`, не owner/superuser,
  без BYPASSRLS, INHERIT, membership/DDL; backup — `ksu_backup`, SELECT-only и полные read policies.
  Runtime не получает admin/backup/bootstrap секреты. `preflight` и открытие candidate на
  независимой копии должны пройти прежние RLS/ACL-проверки.
- Совместимый прежний production код установлен по полному SHA. Синтетически проверен
  возврат к PR41 `cc0b182...` на той же v4 БД **после импорта PR46**. Иной фактический старый
  SHA сначала сравнить с этим baseline; тест baseline не доказывает совместимость произвольной версии.
- Проверить дополнительные markers **отдельно от номера v4**: viewer reader v2;
  при уже включённом `KSU_INVENTORY_PLAN_ENABLED=on` — `inventory_count_version()=1`,
  миграция `005_inventory_count.sql` и runtime EXECUTE. PR46 SQL не меняет.
  Отсутствующую миграцию **не применять в рамках этой инструкции**: STOP и отдельный план.
- Сохранены нынешние HTTPS origin, `KSU_OFFLINE_DEPLOYMENT_ID`, ID пользователей, cohort,
  `KSU_VIEWER_ACCESS`, inventory flag и транспорт. Кандидат PR46 принимался с
  `KSU_OFFLINE_MODE=off`. Если в production pilot/staging или неотправленные очереди —
  STOP перед сменой режима; сначала согласовать сохранение/доставку, не выключать их наугад.
- Для импорта нужен контейнерный scratch `/tmp/ksu-managed-work` на локальной ФС,
  свободно **не менее 768 МиБ**; для экспорта 256 МиБ. `/data` не использовать для SQLite/WAL
  или scratch. Лимит БД приложения прежний 256 МиБ, данных 2 ГиБ, backup-пакета 512 МиБ;
  не увеличивать лимиты/диск/тариф автоматически. Проверить фактический запас и RAM.
- DSN/профиль не менять ради выпуска. Для Amvera external только `require` и точный
  закреплённый host; internal только уже подтверждённый частный маршрут/разрешённое имя
  `cnpg-instrakt-ksu-rw`, `disable`, `confirmed-private`. Не подменять имя из кабинета:
  несовпадение с allowlist — STOP. У остальных провайдеров обязателен `verify-full`.
  [Ограничения Amvera TLS](AMVERA_PG_TRANSPORT.md) сохраняются: ни сквозной TLS, ни
  проверенная подлинность PG-сервера для этих Amvera-профилей не заявляются.

**STOP:** SQLite/неизвестный backend, неподтверждённый SHA/источник/роль, другая схема/major,
неизвестные миграции/очереди, нет свежего успешного backup+restore или проверенного кода
отката, мало места, несовпадение manifest/CI, необходимость новых платных ресурсов.
Не запускать bootstrap/init-schema/init-production/migrate/init-demo/seed/reset.

## 4. Поставка: отдельный PostgreSQL source bundle, без merge в main

Успешный CI текущего **полного SHA** публикует `PR46-Production-Source` и `PR46-Owner-Tools`.
Первый — существующий проверяемый exporter `deploy.release_candidate.bundle --profile postgresql`:
только committed source, pinned базовые Docker images/зависимости, `release-manifest.json`,
`Dockerfile.managed-postgres` с этим SHA по умолчанию, managed entrypoint, порт 8000, `/data`.
В нём нет тестового seed, БД, XLSX владельца, паролей, сертификатов или backup.
`PR46-Preview` — отдельный локальный комплект; его `demo.py`/фикстуры в Amvera не доставлять.

Полный delivery source SHA берётся из manifest **и сверяется с SHA зелёного CI и итогового
отчёта Codex**, а не с изменяемой HEAD ветки. Принятые application files остаются как в
`366c7c4...`; новый SHA добавляет только подготовку выпуска. Проверка этого равенства есть в CI.
Это воспроизводимый **набор исходников**, не обещание одинакового image digest при повторной
сборке: системные apt-пакеты не заморожены. Сохранить фактический build/image ID владельцем.

**Корневой `amvera.yml` полного GitHub checkout выбирает старый SQLite Dockerfile. Его
не отправлять и не подключать ветку PR46 напрямую к автосборке.** Безопасный выбранный путь:
владелец после GO доставляет только проверенный source bundle отдельным commit в Git
**существующего** приложения Amvera, сохраняя историю/старую точку возврата. Команды подготовки
и отдельно запускающий поставку push — [здесь](PR46_RELEASE_COMMANDS.md#поставка-после-отдельного-go).
Если фактический способ иной, сначала согласовать переключение источника/отключение
автосвязи, не выполнять его в процессе сверки. Слияние PR46 в его baseline не является
необходимым условием bundle-поставки; main/PR base сейчас не менять, PR остаётся Draft.

По [официальной схеме сборки Amvera](https://docs.amvera.ru/applications/build.html)
push в `master` запускает сборку и затем deployment автоматически. Это **операция внедрения**,
не загрузка «на потом». У сборочного контейнера возможна временная плата по текущему тарифу;
новых постоянных ресурсов/реплик этот план не создаёт. Сумму/баланс подтверждает владелец.

## 5. Окно обновления: backup → off → smoke → on

1. **До окна.** Согласовать ответственного/время и RTO; сохранить прежний source commit/пакет
   и приватную конфигурацию (секреты в существующем защищённом хранилище). Подготовить локально
   delivery commit и проверить diff, manifest/CI, образ owner CLI. Откат кода должен быть готов
   до push. Ничего не создавать в облаке; replica count не менять.
2. **Закрыть запись организационно.** Два пользователя прекращают изменения/импорт, дают
   завершиться запросам. На **каждом исходном устройстве/аккаунте** проверить очередь,
   синхронизировать разрешённые операции либо сохранить приватный экспорт и явно отложить
   выпуск. Не очищать localStorage/IndexedDB, cookies, PWA и не переустанавливать приложение.
   Копия БД **не содержит неотправленные данные телефона**. Не менять origin/deployment ID.
3. **Свежая согласованная копия существующей PG.** Проверить provider backup и создать
   контрольную точку по разрешённому текущему механизму, если доступен свободный слот.
   Выполнить `Invoke-ManagedPostgres.ps1 -Operation backup` ролью backup и независимый
   `Test-ManagedPostgresBackup.ps1` **на ПК владельца**. Снимок/pg_dump консистентен, БД
   не останавливается. Требуются `verified=true`, все 16 fingerprints, тот же package SHA256,
   constraints/grants/RLS и пустые sessions/attempts; backup и приватные отчёты остаются у владельца.
   При ошибке — STOP, прежний код продолжает работать. Перед самым push подтвердить, что
   после точки копирования бизнес-записей не было; иначе сделать новую копию.
4. **Этап A, только после отдельного GO.** В переменных запуска существующего приложения
   выставить **`KSU_WRITEOFF_ANALYTICS_ENABLED=off`**, остальные значения сохранить.
   Изменение env/restart тоже выполнять только в согласованное окно. Доставить PG bundle
   ручным push, проверить правильный Dockerfile/entrypoint, прежний порт/domain/ресурсы.
   Не перезапускать БД. Health: `ok`, `postgresql`, exact source SHA, прежний offline mode.
5. **Короткий smoke прежнего функционала.** Manager и inspector входят прежними паролями;
   открывают существующий объект/акт/фото, видят прежние записи/права. Чужой объект/фото
   inspector недоступны, viewer остаётся в прежних границах. Analytics API/assets закрыты
   (404 после аутентификации). Проверить сохранённую очередь/receipt; при `off` не ожидать
   отправки новых offline-операций. Не создавать тестовые акты в production.
6. **Этап B, отдельная отметка владельца.** В тех же переменных изменить только
   **`KSU_WRITEOFF_ANALYTICS_ENABLED=on`**, применить штатный перезапуск приложения.
   Флаг глобальный: технического manager-only rollout/cohort у аналитики нет. Ограничение
   пилота организационное — сначала работает manager, затем inspector по своим назначениям;
   inspector импортировать не может, viewer аналитика недоступна. Перенастраивать ACL не нужно.
7. **Одна сопровождаемая загрузка.** Только проверенный построчный «Отчёт по списаниям»,
   не образец «Аналитика инвентаризаций». Приватно проверить SHA файла, лист, диапазон,
   утверждённые aliases существующих объектов, формулы/кеш и отчётный `2026-Q2` до commit.
   Если такой источник/документ уже есть — сверить действующие версии, не повторять импорт
   как новый период. Контроль: **39 строк / 5 нулевых / 56 ед. / 356787.50 полная /
   113827.87 остаточная**; суммы **113827.87 к возмещению** и **116992.36 фактически**
   независимы, без вычитания. Июльская дата акта не переносит отчётный Q2 в Q3. Q1 не создавать
   до его отдельного исходника. При расхождении preview — не подтверждать импорт.
8. **Smoke аналитики и завершение.** Один график → паспорт → полная ведомость → исходная
   ссылка Битрикс → CSV/XLSX со всеми строками/исходными суммами; inspector видит только свои
   объекты, чужой прямой URL/выгрузка закрыты. Сохранить запись «SHA/время/backup/результат»
   без данных. Сделать свежую независимую копию после принятой загрузки; наблюдать ошибки,
   место, provider backups. Полную приёмку PR41/PWA не повторять.

## 6. Отключение, откат кода и авария данных — разные действия

| Событие | Действие владельца |
| --- | --- |
| Не сходятся preview/график/экспорт; ошибка только аналитики | Остановить новые импорты; дождаться текущего commit/проверить его итог. Перевести **только analytics flag в `off`**, перезапустить приложение, открыть страницу заново. Новые запросы закрыты, импортированные данные/версии остаются в БД; уже скачанные данные флаг не отзывает |
| Ошибка доступа/утечка, непрерывные 5xx, нарушение целостности | Немедленно ограничить доступ/запись приложения и сохранить приватную диагностику. Не выполнять новые импорты или исправлять SQL вручную |
| Ошибка нового кода, старая версия подтверждённо совместима | Сохранить свежий снимок текущей PG; вернуть **предыдущий code bundle/config с analytics=off к той же текущей БД**. В подготовленном Git Amvera checkout — revert delivery commit, обычный push после согласования; без force/reset БД. Health должен показать прежний source SHA, затем старый акт/фото/receipt. Сохраняются и записи после выпуска |
| Старый SHA неизвестен/несовместим либо повреждены данные | STOP, оставить запись закрытой, сохранить текущую PG и очереди; отдельный план восстановления/сверки дельты. **Не накатывать предрелизную копию поверх production**: она потеряет новые записи/receipts |

Для Docker не рассчитывать на кнопку быстрого rollback: [контроль версий Amvera](https://docs.amvera.ru/applications/version-control.html)
официально поддерживает проекты **без Dockerfile**. Прежний код хранить приватно, а не
надеяться на retained image. Возврат исходников может требовать новой сборки, поэтому RTO
надо измерить/согласовать; не обещать мгновенный rollback.

## 7. Backup, расходы и оставшиеся риски

[Актуальная документация managed PostgreSQL](https://docs.amvera.ru/databases/postgreSQL.html)
описывает бесплатные scheduled backups (последние **три**) и до трёх ручных. После остановки
кластера расписание выключается; проверить его фактическую активность. Это **не прежнее
утверждение о семи днях** и не backup `/data` приложения. Не удалять старую точку ради слота
без проверенной другой копии. Provider restore **создаёт новый сервис**: цену/endpoint/последствия
нужно согласовать отдельно; не нажимать восстановление для «безопасной проверки» сейчас.

Независимый restore перед выпуском — только локальный Docker PostgreSQL17 из существующего
скрипта, без облачной реплики/публикации порта. `.ksubackup` содержит фото, историю и хеши
паролей, сам по себе не зашифрован: хранить вне Git/облачной синхронизации на защищённом диске
и второй доступной владельцу защищённой копии. Проверка restore создаёт приватные локальные
env/volumes; учесть место для dump+package+restore, не выполнять общий Docker prune.
Windows может быть выключен: ручной/локальный Scheduled Task не гарантирует ежедневную
внешнюю копию. Практичный текущий минимум — provider расписание + owner-local backup/restore
перед каждым обновлением/важным импортом, регулярная проверка свежести назначенным владельцем.
RPO до суточного интервала provider (или дольше при его сбое), RTO пока не измерен на production.
Постоянно включённый внешний узел неизвестен; новая платная инфраструктура не предлагается.

Readiness Windows исправляется только в тестовом комплекте: временный stderr больше не
прерывает ожидание под PowerShell5.1; лимит/CA/health/backend/pinned SHA проверяются,
диагностика не печатает секреты. Это не свидетельство неисправности production Amvera.
CI проверяет реальные Docker/PG и native PS5.1 с временными отказами; физический первый
запуск нового комплекта на ПК владельца этим не объявляется пройденным и не требует нового UI-цикла.

## Проверки подготовки

Целевой PG17-сценарий проверяет off/on/off, неизменность прежних строк/паролей/назначений,
добавление аудита импорта, offline packages/media receipts, полную backup/restore-сверку 16
таблиц и служебных ролей, запуск принятого PR41 в отдельном процессе на **той же** БД после
новых записей. Отдельно сравнивается весь production source с принятым MVP, кроме встроенного
build SHA. Native Windows CI проверяет первый старт с временным stderr, TLS-отказом и неверным
SHA, ограниченный timeout, безопасную диагностику и синтаксис команд PowerShell5.1.
Исторический `test_release_business_ui_and_22_questions_are_byte_preserved` из транспортного
PR39 закреплён за PR38 `8737309...`, поэтому неприменим после принятых PR40/41/46 (при широком
локальном запуске ожидаемо не совпадает `release_online/app.js`). Его не переписывали ради
зелёного статуса: для этого выпуска действует более свежий full-source pin `366c7c4...` выше;
пять собственно транспортных контрактов проверены отдельно. Production проверяется только владельцем.

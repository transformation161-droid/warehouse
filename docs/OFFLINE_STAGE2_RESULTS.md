# Приёмка ДЕМО этапа 2 — один полный выезд

Основание: принятый серверный PR #29, SHA `817ae05ef46cc34bd356cd9613f247e8e4005012`.
Ветка `feat/offline-stage2-visit-sync`. Работа 09.11.2026, Europe/Moscow.
Только сгенерированные данные и одноразовые тестовые ресурсы; PR #27–29, main,
Amvera и действующая PostgreSQL на 8003 не изменяются.

## Что реализовано

Отдельный экран `/offline-visit/` на карточках/стилях принятого интерфейса:
назначенный выезд и исторический чек-лист, фото камерой/галереей, немедленные
шифрованные записи IndexedDB, неизменяемая очередь, foreground-отправка через API этапа 1.
У каждого фото UUID/SHA-256; у единого batch — устойчивый mutationId,
inspectionId/findingId и исходный expectedVersion выезда. Пароль/CSRF не сохраняются в IDB.

Перед отправкой проверяются действующая сессия, аккаунт, идентичность ДЕМО-стенда,
доступ к объекту и назначение/версия выезда. Необязательные серверные заголовки
`X-KSU-Expected-User` / `X-KSU-Offline-Deployment` закрывают гонку смены cookie/стенда,
не дают полномочий и не ослабляют прежние auth/CSRF/ACL. При обычном запуске API экран
не публикуется; требуется явный lab ID из нового тестового launcher.

После сбоя отправка начинается с receipt. Batch сохраняется в точности до POST;
ответы фото — до следующего шага; успешный receipt — до показа «Принято сервером».
Ни новые ID при повторе, ни last-write-wins, ни автоматическое удаление данных не используются.
Все шесть статусов видимы. Локальный снимок и очередь доступны после полного офлайн-перезапуска.

Сценарии каждого backend:

1. Подготовка назначенного выезда; без сети ответы/два нарушения/два фото,
   закрытие Chromium, холодный запуск, шифрованные данные и прежние ID.
   Истёкшая сессия и вход другим аккаунтом не отправляют очередь.
   Ответ первого фото теряется **после настоящего commit**; восстановление через receipt.
   Ответ batch удерживается после реального commit; JS останавливается, браузер закрывается
   с сохранённым «Отправляется». После офлайн-перезапуска и восстановления сети — receipt,
   один акт/два нарушения/два фото/одно завершение, fingerprints всех бизнес-таблиц не меняются.
   Принятое состояние снова переживает офлайн-перезапуск. API не попадает в Cache API.
2. Руководитель меняет план до отправки: конфликт без загрузки фото/акта,
   ответы/фото/ID сохраняются после перезапуска.
3. Доступ к объекту отозван: ошибка без загрузки фото/акта, очередь не удалена.
4. Cookie сменена на manager **после preflight**, перед POST фото:
   серверная проверка ожидаемого аккаунта запрещает запись; fingerprints неизменны.
5. Контролируемый отказ IDB/квоты: неподтверждённый текст явно помечен,
   очередь не фиксируется. После восстановления записи явное сохранение и перезапуск
   сохраняют текст; камера работает через fallback без showPicker.
6. Руководитель меняет версию уже после загрузки фото: сервер возвращает 409 receipt,
   весь batch акта/нарушений откатывается, фото и локальная очередь сохраняются.
   Повтор получает тот же конфликт без новых записей; конфликт переживает перезапуск.

Серверные тесты дополнительно проверяют отсутствие экрана по умолчанию,
whitelist статических файлов, scope Service Worker, auth/CSRF/context и отказ чужого
аккаунта/стенда до записи. Ранее принятые версии чек-листов/receipts/backup/restore
и API проверены общей регрессией на обеих БД. PostgreSQL создаётся только во временных
TLS-кластерах (0,5 CPU/1 GiB без swap), не в существующей установке.

Docker probe использует тот же whitelist mounts, что Windows launcher, отдельный
пустой каталог, случайный порт и CA, подтверждает HTTPS с проверкой сертификата/имени,
Secure-cookie и неизменность паролей/lab ID после restart. Изображение локальное;
ни прежний том, ни БД, ни DSN, ни порт 8003 не используются.

## Ручная приёмка

Точные команды Windows/Docker и Android LAN HTTPS, создание доверенного сертификата,
порядок 10 шагов, проверка руководителем и ограничения:
[experiments/offline_visit/README.md](../experiments/offline_visit/README.md).

В Cloud не заявляется приёмка реального объектива, Android Back, OS eviction или
физической мобильной радиосвязи. Это следующий ручной этап владельца.
Сохраняются подтверждённые IDB-транзакции; последние неподтверждённые символы при
OS-kill/поломке диска не могут быть гарантированы. Ошибки не маскируются статусом сохранения.

Ограничения MVP: один выезд/профиль, один активный tab, ручной foreground sync,
до 20 фото (одно на пункт), до 98 нарушений, TTL пакета этапа 1, без UI merge/GC/импорта
экспортированной копии. При позднем конфликте загруженные фото могут остаться без акта;
автоматического удаления нет. Финансовые функции/аналитика не подключаются.

Данные, базы, копии, ключи и пароли не публикуются в GitHub-артефакты.
Результаты CI и итоговый SHA приводятся в отдельном Draft PR.

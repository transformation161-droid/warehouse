## После отдельного согласования интеграции

Зависимости идут от ранних PR к поздним:

`№6 → №16 (включает №12 + №13) → №18 → №19 → №22 → №23 → №24 → №26 → №27 → №28 → №29 → №30 → №33 → №34 → №35 → этот кандидат`.

Для последовательного закрытия стека нужны merge-коммиты с сохранением ancestry и сверкой
баз/голов перед каждым шагом. Squash/rebase каждого звена меняет историю зависимых PR и
требует отдельного плана переноса. №12/13 не применять повторно поверх №16. №5/8/32 не
подмешивать в релиз. Старые PR не являются самостоятельными наборами изменений для cherry-pick.

Более короткий вариант для владельца репозитория: после одобрения создать интеграционный PR
из **полной вершины** кандидата в `main`, проверить весь итоговый diff и закрыть покрытые PR
как включённые. Это сохраняет уже интегрированный код и избегает двадцати повторных переносов.
Выбор способа и любые merge остаются за владельцем. Ни один из вариантов сейчас не выполнялся.

Перед изменением `main` обязательно отключить внешние автоматические связи Amvera с GitHub
и убедиться, что прежние Actions доставки/backup не смогут стартовать на старой версии workflow.
В кандидате оба legacy workflow заменены на ручные пустые заглушки без секретов, сети к Amvera,
скачивания БД и upload backup. Это **не** отключает настройки, которые ещё находятся в `main`,
или webhook/автосборку на стороне провайдера. Создание этого Draft PR ничего туда не отправляет.

# Независимая копия PostgreSQL на Windows — без установки Python

Нужен Docker Desktop с Linux-контейнерами и PowerShell 5.1+. Корпоративный рабочий контур не
менять: сначала проверить на синтетической копии. Скрипты не обращаются к Amvera сами по себе.

## Один раз подготовить инструменты, пока есть Интернет

Администратор скачивает исходники этой ветки и в их папке выполняет:

```powershell
docker build -f Dockerfile.postgres -t ksu-postgres:offline .
docker pull postgres:17-bookworm@sha256:839fbb5a4942a7758dd93e18b42ea5649807491a0545b5eeeb8f0b8bb11857a5
```

В Python на Windows нет необходимости: все модули уже внутри образа. Образы можно заранее
перенести через `docker save`/`docker load` в одобренном порядке, без данных/паролей в образах.

## Скачать проверенную копию

Создайте закрытую папку на шифрованном диске (например, BitLocker), вне OneDrive/Git/публичных папок.
Адрес — только разрешённый владельцем PostgreSQL-экземпляр приложения. Пока действующий пилот
остаётся SQLite, новый экспорт на нём не появится автоматически.

```powershell
.\tools\Backup-Postgres.ps1 -Origin 'https://APPROVED-APPLICATION.example/' -Destination 'D:\PrivateKSU\copy.ksubackup'
```

Скрипт запросит login manager и пароль скрытым вводом. Использует действительную TLS-проверку,
cookie/CSRF, потоковый FileStream и сверяет SHA-256. Пароль/токены не сохраняет. Файл создаётся
с доступом текущего пользователя и SYSTEM; существующий файл не заменяется. При ошибке partial
удаляется. Inspector не получает backup. В локальном демонстрационном режиме допустим localhost HTTP.

## Восстановить без исходного сервера и Интернета

Закройте исходное приложение, оставьте доступными только скачанный доверенный пакет, исходники
инструментов и подготовленные Docker-образы. Выполните:

```powershell
.\tools\Restore-Postgres.ps1 -Backup 'D:\PrivateKSU\copy.ksubackup' -Port 8000
```

Скрипт создаёт новые **локальные** контейнеры и тома с уникальными именами. Пакет подключает
read-only; исходный сервер и старые БД не используются. Служебные пароли генерируются в памяти,
передаются как environment без значений в аргументах и восстанавливают прежнюю среду PowerShell.
Схема восстанавливается с checksum-проверкой; API запускается только после успешной проверки.
PostgreSQL не публикует порт наружу, интерфейс доступен только на `http://localhost:8000`.

Войдите прежними паролями manager и inspector: они сохранены в виде хешей, не извлекаются из копии.
Проверьте календарь/план/акты, фото, историю, реестр решений и отчёты; повторный импорт того же файла
не должен создавать строки. Сессии из исходного сервера не действуют.

Команда остановки и имена локальных томов выводятся в конце. Том с данными автоматически не удаляется.
Не отправляйте `.ksubackup`, `.dump`, credentials, сертификаты или корпоративные файлы в GitHub/чат.

Синтаксис проверяется Windows CI. Backend, большая копия и независимый restore проверены в Linux
при 0,5 CPU / 1 ГиБ; приёмку Docker Desktop/BitLocker/ACL на конкретном Windows-компьютере нужно
выполнить по этим шагам. Это не установка или обновление работающей корпоративной системы.

## Запуск проверенной SQLite-копии на Windows (PR #26 и новее)

Это отдельная локальная тестовая установка PostgreSQL 17, без обращения к Amvera.
Сначала поместите **исходники нового Draft PR** в
`C:\KSU\warehouse-feat-issue-25-analytics-polish` (имя папки можно оставить прежним).
Один только архив старого PR #26 не содержит нового скрипта.
Существующий образ `ksu-postgres:offline` используется как среда Python/PG17;
актуальный код из папки подключается read-only поверх `/app`. Поэтому старый код,
запечённый в образ, не запустится вместо новой версии. Не меняйте эту папку во время работы.
Если образ слишком стар и в нём нет зависимостей текущего `requirements.txt`, пересоберите
его по команде выше. Нужны запущенный Docker Desktop в режиме Linux containers и оба
заранее загруженных образа; скрипт ничего не скачивает автоматически.

Одна команда в PowerShell (Python на Windows не нужен):

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'C:\KSU\warehouse-feat-issue-25-analytics-polish\tools\Start-Postgres.ps1'
```

`Bypass` действует только для этого процесса. Если политика организации запрещает запуск,
обратитесь к администратору; скрипт не меняет системную политику.

По умолчанию переносится **`C:\KSU\demo-data\backups\check1.sqlite3`**, а не
`C:\KSU\demo-data\ksu.sqlite3`. Проверенная копия должна быть закрытой, самостоятельной,
без файлов `-wal`, `-shm`, `-journal`. Исходная рабочая SQLite не подключается.
Путь можно явно заменить параметром `-Source`. Используйте только тестовые данные.
Копия монтируется read-only, её SHA-256 проверяется до/после переноса; обновление старой
схемы SQLite выполняется только во временной копии в отдельном Docker-томе.

Скрипт проверяет Docker, образы и порт; создаёт уникальные контейнеры и два постоянных тома,
создаёт отдельную Docker-сеть с отключённым обменом между контейнерами,
генерирует служебные пароли, создаёт схему v2, runtime без SUPERUSER/BYPASSRLS/создания ролей
и отдельную read-only backup-роль. Приложение не получает пароль администратора.
PostgreSQL не публикует порт 5432. Порт приложения опубликован только на loopback:8002.
Служебные пароли находятся в Docker environment (доступны локальным администраторам Docker),
но не в JSON-файлах/командной строке/образах. Защитите Windows-учётную запись и Docker Desktop.

Успех: сообщение `Migration verified`, адрес `http://localhost:8002` и файл
`var\windows-postgres-migration.json`. Миграция сравнивает **количество и SHA-256 каждой
переносимой таблицы** в одной транзакции; несовпадение отменяет перенос и не запускает приложение.
Хеши считаются по упорядоченным строкам, включая хеши бинарных файлов. Для старых схем
сравнивается обновлённая независимая копия. Сессии и попытки входа намеренно не переносятся.

В браузере должна появиться русская форма входа КСУ Контроль. Войдите прежними паролями
`manager` и `inspector` (второй — в приватном окне). Скрипт не сбрасывает и не извлекает их.
Сравните с проверенной SQLite-копией объекты, выезды, проверки, нарушения, фото, историю,
списания и итоговые суммы аналитики. В отчёте миграции для `users` ожидайте исходное число
пользователей; для остальных таблиц — исходные количества. Это техническая проверка точного
переноса; ручная проверка экранов на вашем компьютере остаётся обязательной.

Повторный запуск: **та же команда**. Остановка:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'C:\KSU\warehouse-feat-issue-25-analytics-polish\tools\Start-Postgres.ps1' -Action Stop
```

Сохраняйте `var\windows-postgres.json`: это указатель на созданную установку, без паролей.
Повторный запуск не читает SQLite, не создаёт роли и не выполняет повторную миграцию.
Контейнеры и тома не удаляются даже при ошибке. Если первая установка прервана, скрипт
откажет в автоматическом продолжении: сохраните журнал и попросите проверить указанные
контейнеры. Не удаляйте state-файл и не запускайте `docker volume prune` для исправления.
Исходные базы, `main` и другие установки не изменяются. При занятом 8002 скрипт останавливается;
первую установку можно явно запустить с `-Port 8003`.

### Независимая резервная копия и восстановление

Пока исходная установка работает, скачайте пакет существующим `Backup-Postgres.ps1`
с `-Origin 'http://localhost:8002/'` в новую приватную `.ksubackup` вне Git.
Остановите исходную установку командой выше. Запустите `Restore-Postgres.ps1 -Backup
'ПОЛНЫЙ_ПУТЬ_К_КОПИИ.ksubackup' -Port 8003`: создаётся **новый** экземпляр PostgreSQL
и новые тома, исходная БД для восстановления не нужна. Войдите обоими прежними аккаунтами,
сравните данные и фото. Не удаляйте исходные тома после этой проверки.

Отдельный автоматический тест: `python -m tests.pg_independent_restore`
(для разработчика, Linux Docker и образ `ksu-postgres:test`). Он создаёт синтетические данные,
переносит их, делает backup read-only ролью, **останавливает исходный PostgreSQL**, восстанавливает
в новый кластер, сверяет все количества/SHA-256 и вход обоих пользователей, проверяет отказ
перезаписи. Удаляет только собственные временные тестовые контейнеры. Windows CI проверяет
синтаксис и сценарии скрипта с имитацией Docker в PowerShell 5.1 и 7; это не заменяет приёмку
реального Docker Desktop на Windows и проверку локальных пользовательских файлов.

### Проверка исправления HTTP backup (ревью PR #27)

Локальный запуск передаёт приложению **оба** параметра: `KSU_PG_BACKUP_DSN` и
`KSU_PG_BACKUP_DIR=/work/backups`. Каталог создаётся внутри постоянного work-тома,
принадлежит `1000:1000`, имеет Linux-права `0700`; права задаются внутри Linux-контейнера,
поэтому не зависят от преобразования Windows ACL у bind mount. Настройка окружения
PowerShell восстанавливается и при успехе, и при ошибке. При остановке/повторном запуске
каталог и настройки сохраняются. Скачанный `.ksubackup` храните отдельно от Docker-томов.

`tests.pg_independent_restore` теперь запускает **сам Start-Postgres.ps1** через PowerShell 7
с синтетической SQLite-копией, проверяет реальные права каталога до и после stop/start,
входит по HTTP как inspector (backup должен вернуть 403), затем как manager
(backup должен вернуть 200), скачивает поток и проверяет `X-Backup-SHA256`.
После остановки исходного приложения и PostgreSQL восстанавливает скачанный пакет
в независимый кластер, сверяет все количества/SHA-256 и оба аккаунта. Этот тест включён
в PostgreSQL CI; Windows CI отдельно проверяет PowerShell 5.1/7 и передачу настройки.
Для запуска теста разработчику нужны `pwsh`, Docker и образ `ksu-postgres:test`.

Обновление исходников **не добавляет environment в уже созданный старой версией контейнер**.
Если до исправления установка уже была создана, не удаляйте state-файл/тома и не запускайте
миграцию повторно: администратору нужно пересоздать только контейнер приложения с сохранением
прежних DSN и work-тома, передав `KSU_PG_BACKUP_DIR` и создав каталог с указанными правами.
Для первой ручной приёмки используйте исправленную версию PR #27. Реальная проверка Docker Desktop
на Windows и файлов владельца остаётся ручной; cloud-тест использует только синтетические данные.

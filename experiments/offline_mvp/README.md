# ДЕМО · офлайн-прототип КСУ — этап 0

Изолированный технический эксперимент, не рабочий офлайн-режим корпоративного приложения.
База ветки: принятый локальный запуск PR #27, SHA `9ab36f1702a972931afe93a026c8f865739c1b37`.
Изменения находятся только в `experiments/offline_mvp`, тестах и отдельном CI. PR #27, main,
Amvera, рабочие SQLite/PostgreSQL и серверный API приложения не меняются.

## Быстрый запуск Windows / Docker Desktop

Распакуйте **этот PR в отдельную папку**, например `C:\KSU\warehouse-offline-stage0`.
Нужны Docker Desktop/Linux и уже имеющийся образ `ksu-postgres:offline` (в нём используется
только Python; PostgreSQL не запускается). Команда не скачивает образы.

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'C:\KSU\warehouse-offline-stage0\experiments\offline_mvp\Start-Prototype.ps1'
```

Откройте **http://127.0.0.1:8010** в Chrome. Рабочее приложение на 8003 не затрагивается.
Контейнер `ksu-offline-stage0` видит только папку прототипа и read-only `styles.css` КСУ.
Базы, тома рабочей системы, DSN и корпоративные данные ему не передаются. Сервер имеет
строгий список статических маршрутов, только GET/HEAD, POST/PUT/DELETE возвращают 405.
Синтетические пакет/PNG генерируются сервером; пользовательские фото на сервер не отправляются.

Остановка (другое окно PowerShell):

```powershell
docker stop ksu-offline-stage0
```

Удаляется только временный контейнер прототипа (`--rm`); состояние находится **в браузере**,
его остановка контейнера не удаляет. Следующий запуск — та же первая команда с тем же origin.
Не запускайте второй сервер на другом порту для проверки восстановления: браузерное хранилище
привязано к origin. Не используйте инкогнито.
Порт не изолирует cookies: используйте именно 127.0.0.1 для прототипа, если рабочая КСУ
открыта на localhost. Сервер прототипа не принимает Cookie-заголовок; при отказе выберите
отдельный обычный тестовый профиль, не удаляя cookies рабочей КСУ.

Альтернатива для разработчика с Python 3.12+, без сторонних runtime-пакетов:

```sh
python experiments/offline_mvp/server.py
```

## Ручной сценарий

1. Дождитесь «Офлайн-оболочка активна». Создайте локальный ДЕМО-профиль с отдельной длинной
   фразой (минимум 12 символов, не пароль рабочей КСУ). Фразу сохраните самостоятельно:
   восстановления через сервер нет.
2. «Загрузить ДЕМО-пакет и фото». Появятся три контрольных пункта и цветной синтетический
   PNG-образец с постоянным ID. Проверяются SHA-256 шаблона и фото. Версия `demo-checklist-v1`
   сохраняется внутри зашифрованного пакета и не заменяется повторной подготовкой.
3. Полностью отключите Wi-Fi/мобильную связь или остановите сервер; обычный уже загруженный
   экран сам по себе ещё не доказывает офлайн-холодный запуск.
4. Заполните чек-лист. Для «Нарушение» введите описание. «Сохранить черновик на устройстве».
   Отдельно отображаются подтверждённое локальное сохранение и отсутствие серверного подтверждения.
5. Доступны две кнопки: **«Сделать фото»** и **«Из галереи»**. Первая открывает input
   `accept="image/*" capture="environment"` с предпочтением задней камеры Android.
   Вторая открывает обычный выбор файла без capture. Камеру окончательно выбирает браузер/ОС:
   при отсутствии поддержки capture может открыться стандартный chooser; при недоступной
   камере/отказе разрешения используйте «Из галереи». Live-video/getUserMedia не используется.
   Оба пути используют **один** обработчик проверки, JPEG-сжатия, SHA-256, шифрования и
   атомарной записи state + Blob. Допускаются JPEG/PNG/WebP, HEIC по-прежнему не поддерживается.
   Перед открытием камеры/галереи введённый текст сохраняется на устройстве. Если сохранение
   не удалось, выбор не открывается. При потере browser user activation после сохранения
   появится просьба нажать кнопку ещё раз — второй тап синхронно открывает chooser.
   Добавление фото само атомарно сохраняет весь текущий черновик и его ссылку на фото. Повтор того же файла не создаёт новый ID. У нового фото UUID,
   SHA-256 и бинарный шифртекст; имя исходного файла не сохраняется.
   Отмените съёмку Android-кнопкой «Назад», не подтверждая снимок: новый Blob/ID не должны
   появиться, ответы и уже сохранённые фото остаются. Затем снова откройте камеру и сделайте
   тестовый снимок. Повторите отмену галереи и выбор того же файла: дубля быть не должно.
   На старых браузерах без события `cancel` сообщение об отмене может отсутствовать,
   но данные не меняются и интерфейс не остаётся заблокированным.
6. Закройте браузер полностью. Сеть оставьте выключенной. Откройте тот же адрес/ярлык,
   введите локальную фразу: должны восстановиться ответы, описание, фото и их ID.
7. После заполнения всех ответов можно «Завершить локально». Это сохраняет неизменяемый локальный
   результат с operationId/inspectionId/findingId, но **ничего не отправляет серверу**.
8. «Заблокировать» очищает интерфейс, ссылки Blob и in-memory ключ. По умолчанию то же
   происходит через **10 минут** бездействия; интервал 1–60 минут настраивается и хранится
   вместе с пакетом. Для быстрой ручной проверки выберите 1 минуту.
9. Через 24 часа пакет запрещает новую работу, но остаётся доступным после разблокировки
   для просмотра/экспорта: черновик и фото не удаляются. Часы устройства могут быть подменены —
   это локальная политика эксперимента, не надёжная защита от отзыва доступа.

Доступна одна синтетическая проверка, один локальный профиль и одна активная вкладка.
Для нового независимого опыта — отдельный профиль браузера. Удалять данные origin можно
только осознанно после проверки/экспорта; это удалит ключ и черновик. Рабочий origin 8003
и его IndexedDB не имеют отношения к отдельному origin прототипа 8010.

## Хранение и защита

IndexedDB `ksu-offline-stage0-encrypted-v1`: `meta` содержит соль, версию KDF и обёрнутый ключ;
`records` — AES-GCM ciphertext состояния и отдельных бинарных Blob. У каждой записи случайный
96-битный IV и привязка AAD к ДЕМО-профилю/ключу записи. Ключ данных — случайные 256 бит,
обёртка через отдельную фразу + PBKDF2-SHA256, 310000 итераций. Ключ после разблокировки
non-extractable, живёт в памяти, фраза в IDB/localStorage/Cache API не хранится.

Параметр KDF фиксирован для прототипа; скорость на целевом Android ещё предстоит измерить.
Короткая/предсказуемая фраза уязвима к перебору офлайн. Шифрование не защищает от XSS,
вредоносного расширения или уже разблокированного устройства; JS/ОС не гарантируют физическое
обнуление всех копий памяти. Это не серверная авторизация и не заменяет будущие ACL/RLS.
CSP запрещает сторонние скрипты и inline JS. У устройства нет роли/сессии реальной КСУ.

Криптооперации выполняются до короткой IndexedDB-транзакции. Состояние и Blob сохраняются
одной транзакцией; при отказе сохраняется предыдущая подтверждённая версия. Нажатие «Сохранить»
и подтверждение `oncomplete` принципиально отличаются от введённого, ещё не сохранённого текста.
Этап 0 использует явное сохранение текстового черновика; полноценный autosave — следующий этап.
Перед ручной блокировкой/обновлением делается попытка сохранения. При авто-блокировке и отказе
диска **последние неподтверждённые правки могут потеряться**, предыдущая версия остаётся.

«Скачать зашифрованную копию» выгружает ciphertext и обёрнутый ключ, не plaintext. UI импорта
такой копии в этапе 0 отсутствует; нельзя считать это проверенным механизмом независимого
восстановления. Основная проверка восстановления — та же браузерная IndexedDB после рестарта.

## Отказы, квота и память

Раздел «Лаборатория отказов» виден и явно обозначен как ДЕМО:

- «Следующую запись отклонить как QuotaExceededError» **реально отменяет IDB-транзакцию**,
  имитируя отказ квоты. Проверяйте, что после перезапуска вернулась предыдущая версия,
  новое фото не появилось частично и нет ложного статуса успешного сохранения.
- «Следующее фото отклонить до декодирования» — детерминированная имитация отказа бюджета
  памяти. Это не реальное исчерпание RAM и не доказательство устойчивости при OS-kill.
- Рабочие ограничения: входной файл до 10 МБ, декодированное изображение до 16 Мп,
  нормализация JPEG до 1600 px / 3 МБ, бюджет сохранённых фото профиля 100 МиБ.
  Большой декодер может потратить память **до** проверки размеров. Реальный OOM может убить
  вкладку без catch/finally; гарантируется только восстановление ранее подтверждённых данных.
- `StorageManager.estimate` приблизителен; `persist()` может быть запрещён. Persistent storage
  не защищает от ручной очистки, удаления PWA/профиля, поломки диска или потери устройства.
- Chromium CDP quota override на малых перезаписях может не вызвать отказ из-за внутреннего
  резервирования. В этом стенде override=1 байт не запретил даже запись 32 МиБ:
  **не считаем CDP override достоверным тестом физического диска**. Автотест проверяет
  атомарную отмену транзакции и отдельный логический лимит 100 МиБ. Реальный disk-full
  на целевом устройстве остаётся ручным испытанием.

## Service Worker и обновление

SW кэширует только фиксированный список оболочки (HTML, JS, CSS, manifest и иконка).
Пакет, образец фото, пользовательские фото, API и cookies в Cache API **не попадают**.
Оболочка устанавливается только при успешной загрузке всего списка. Waiting worker
активируется кнопкой после сохранения dirty-черновика и блокировки профиля. Автоматического
skipWaiting при редактировании нет. Старые shell-кэши намеренно сохраняются в этапе 0:
протокол их безопасной уборки вместе с несколькими поколениями клиентов ещё не реализован.

При установке исправления камеры обновите файлы PR #28 **в той же папке**, не удаляя
browser storage. Перезапустите только контейнер прототипа с прежними IP/портом/сертификатом.
Сервер автоматически добавляет hash JS/HTML/CSS в SW revision: даже с прежним `-Build`
браузер увидит новую оболочку. Онлайн нажмите «Проверить обновление интерфейса», дождитесь
waiting-версии, затем «Обновить интерфейс безопасно»; перезагрузите и разблокируйте профиль.
Чек-лист/ID/фото и локальная фраза остаются прежними. Очистка IndexedDB или полное удаление
PWA для обновления не нужны.

Для проверки обновления: сохраните/экспортируйте ДЕМО-данные, остановите только контейнер
прототипа и запустите ту же команду с `-Build stage0-v2`. Верните сеть, нажмите «Проверить
обновление интерфейса». Кнопка активации не должна уничтожить несохранённый черновик.
После сохранения/активации перезагрузите страницу, разблокируйте — ID и фото сохраняются.
Build-v2 меняет версию оболочки при **той же** схеме; это не тест произвольной будущей миграции
IndexedDB. Неизвестная версия schema/KDF отклоняется без удаления данных.

## Автоматическая проверка

```sh
python -m unittest tests.test_offline_stage0_server -v
python -m tests.offline_stage0 --backend sqlite
python -m tests.offline_stage0 --backend postgres
```

Нужны зависимости разработчика из `requirements-dev.txt`, Chromium/Playwright; для PostgreSQL
— Docker с закреплённым PG17-образом, как в существующем тестовом harness. CI выполняет оба
backend-варианта, HTTP/TLS boundary и парсер Windows PowerShell 5.1. Backend sentinel создаётся
**синтетически**: SQLite SHA-256 и PostgreSQL fingerprints сравниваются до/после эксперимента.
Это проверка отсутствия влияния/зависимости, **не совместимость будущей синхронизации**, которой
ещё нет. Таблицы, RLS, receipts и migration-схема рабочего приложения не меняются.

Браузерный тест: сервер остановлен, browser process закрыт и новый persistent context запущен
с offline=true; неверная фраза, сохранённые ответы/Blob/ID, IDB atomic abort, логический бюджет квоты,
имитация памяти, второй писатель, безопасный SW update, неуспешная установка новой оболочки,
истечение 24 часов без удаления, настраиваемая автоблокировка. Desktop Chromium 390px не является
физическим Android. Физический сценарий — [ANDROID_HTTPS.md](ANDROID_HTTPS.md).

## Граница этапа

**Не реализованы:** реальная аутентификация/права, серверная синхронизация/идемпотентность
приёма, receipts, межустройственные конфликты, offline packages рабочего API, многозадачная
очередь, миграции SQLite/PostgreSQL и публикация версий рабочих чек-листов. Устойчивые ID и
снимок версии подготовлены локально; это не обещание «exactly once» сервера. HEIC/Safari/
реальная память телефона, удаление storage ОС, установка с домашнего экрана требуют отдельных
испытаний. Переход к этапу 1 — только после согласования результатов этапа 0.


Регрессия кнопок камеры: автоматический тест проверяет атрибут capture/environment,
отдельный input галереи, оба настоящих события filechooser, пустой выбор/событие cancel,
сохранение dirty-текста до chooser и cold restart после отмены, fallback без showPicker,
дедупликацию между обоими источниками и общий отказ типа/размера/квоты. Физическую камеру
тест не эмулирует: её открытие, выбор заднего объектива, разрешения и Android Back должны
повторно пройти ручную приёмку. Старый успешный полевой тест подтверждает общий офлайн-путь,
но не является результатом проверки этих новых кнопок.

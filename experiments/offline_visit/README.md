# ДЕМО · Один полный офлайн-выезд КСУ — этап 2

Отдельная ветка от принятого серверного этапа PR #29 (`817ae05`). PR #27–29,
main, Amvera и действующая установка на 8003 не изменяются. Только синтетика.
Новый экран использует карточки/стили, камеру/галерею и AES-GCM/IndexedDB подход этапа 0,
а также серверные контракты этапа 1. Аналитика и финансовые функции не подключаются.

## Windows / Docker Desktop: отдельная установка

1. Скачайте ZIP **этой ветки** и распакуйте в новую папку, например
   `C:\KSU\warehouse-offline-stage2`. Не переключайте ветку и не подменяйте файлы
   папки, из которой работает PostgreSQL/приложение PR #27. В ней может быть read-only
   bind к коду работающего контейнера — новое приложение должно иметь свою папку.
2. Нужен Docker Desktop с Linux containers и уже имеющийся локальный образ
   `ksu-postgres:offline` из принятой установки. Его PostgreSQL-сервер **не запускается**:
   здесь используется Python этого образа и отдельная **SQLite** для ДЕМО.
   Python/Node на Windows устанавливать не требуется, скрипт образы не скачивает.
3. В PowerShell выполните:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'C:\KSU\warehouse-offline-stage2\experiments\offline_visit\Start-VisitLab.ps1'
```

4. Оставьте окно работающим. После первого запуска откройте в Проводнике
   `C:\KSU\warehouse-offline-stage2\var\offline-stage2-lab\demo-accounts.txt`.
   Там автоматически созданы случайные пароли **только этой** SQLite-установки
   для `manager` и `inspector`. Не используйте аккаунты рабочей БД.
5. Chrome: **http://127.0.0.1:8012/offline-visit/**, обычный отдельный тестовый профиль.
   Локальный loopback является secure context для WebCrypto и Service Worker.
   Не заменяйте 127.0.0.1 на localhost: cookies не изолируются портом,
   а рабочая установка использует localhost:8003. На Android этот адрес не подходит —
   нужен отдельный доверенный LAN HTTPS, описанный ниже.

Остановка только стенда, в другом окне:

```powershell
docker stop ksu-offline-visit-stage2
```

Повторный запуск — та же первая команда, **та же папка и origin**. SQLite, пароли,
идентификатор стенда и browser storage сохраняются. Завершённый выезд не создаётся заново.
Скрипт запрещает порт 8003, не монтирует прежние БД/тома/DSN и отказывается принимать
чужую непустую папку или файлы существующей установки в корне `var`.
Нет автоматического удаления, reseed, миграции PostgreSQL или замены контейнера с занятым именем.

Если локального образа нет, разработчик может отдельно собрать новый образ, не заменяя
образ/контейнер рабочей установки (это только локальная сборка, не платная услуга):

```powershell
docker build -f Dockerfile.postgres -t ksu-postgres:stage2-test 'C:\KSU\warehouse-offline-stage2'
powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'C:\KSU\warehouse-offline-stage2\experiments\offline_visit\Start-VisitLab.ps1' -AppImage ksu-postgres:stage2-test
```

Для нового независимого испытания распакуйте исходники в ещё одну новую папку и остановите
только прежний stage2-стенд. Старые данные/профиль не удаляйте. Этот MVP намеренно
не заменяет старый локальный выезд новым, даже после получения receipt.

## Android / Chrome: локальный HTTPS

Выберите этот вариант **с самого начала** полного испытания. Если единственный выезд
уже завершён на Windows, для нового испытания нужна новая отдельная папка стенда.
Windows и телефон должны быть в разрешённой тестовой LAN; не открывайте доступ из интернета.
Нужен mkcert (или сертификат разрешённого локального CA), с SAN фактического LAN-IP.
Пример ниже: ПК `192.168.1.20`, тестовый телефон `192.168.1.30` — замените своими IP.

```powershell
$ip='192.168.1.20'
$tls='C:\KSU\stage2-tls'
New-Item -ItemType Directory -Force $tls | Out-Null
mkcert -install
mkcert -cert-file "$tls\lan.pem" -key-file "$tls\lan-key.pem" localhost 127.0.0.1 $ip
Copy-Item (Join-Path (mkcert -CAROOT) 'rootCA.pem') "$tls\ksu-stage2-ca.crt"
powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'C:\KSU\warehouse-offline-stage2\experiments\offline_visit\Start-VisitLab.ps1' -BindAddress $ip -Port 8445 -CertificatePath "$tls\lan.pem" -KeyPath "$tls\lan-key.pem"
```

Передайте на телефон **только публичный** `ksu-stage2-ca.crt`, например по USB, и установите
его через настройки безопасности Android как сертификат ЦС. Приватные `rootCA-key.pem`
и `lan-key.pem` не переносить в телефон/чат/GitHub. Откройте
**https://192.168.1.20:8445/offline-visit/** без предупреждений сертификата.
Не обходите предупреждение и не отключайте проверку TLS: проверьте CA, SAN/IP, часы.

Если нужен Windows Firewall, администратор разрешает лишь Private-профиль,
фактический IP телефона и этот порт, без Public/Any/проброса маршрутизатора:

```powershell
New-NetFirewallRule -DisplayName 'KSU Stage2 Android HTTPS' -Direction Inbound -Action Allow -Protocol TCP -LocalPort 8445 -LocalAddress 192.168.1.20 -RemoteAddress 192.168.1.30 -Profile Private
```

Cookies зависят от hostname, а не порта. Для испытания используйте отдельный профиль
Chrome и тестовый LAN-IP, не общий origin рабочей системы. Запишите origin, папку стенда
и локальную фразу: их смена не переносит browser storage. Старый этап 0 на 8443 не менять.

## Ручная проверка одного выезда

1. На инспекторском устройстве дождитесь **«Офлайн-оболочка активна»**.
   Войдите `inspector` с паролем **нового стенда**. Создайте локальный шифрованный профиль:
   отдельная фраза от 12 символов, не пароль КСУ. Сервер её не знает и не восстанавливает.
2. «Показать назначенные выезды» → единственный **«ДЕМО · Полный офлайн-выезд КСУ»** →
   «Сохранить выезд для работы без сети». Проверьте объект, версию выезда, ID чек-листа,
   срок пакета и статус **«Сохранено на устройстве»**.
3. Полностью отключите Wi-Fi **и** мобильную связь/включите авиарежим. Отметьте ответы
   во всех пунктах; для двух выберите «Нарушение» и заполните тестовое описание.
   Текст автоматически сохраняется в шифрованный IndexedDB; дожидайтесь подтверждённого
   локального статуса. Если отображается ошибка сохранения, не закрывайте страницу.
4. Выберите первое нарушение в «Фото для нарушения». «Сделать фото» использует input
   `capture=environment`; объектив/разрешения выбирает Android. Сначала отмените съёмку:
   ответы и ID не должны измениться. Снова нажмите, снимите тестовый предмет и подтвердите.
   Для второго нарушения — «Из галереи» и синтетическое изображение. До внешнего chooser
   текст сохраняется; при запросе повторного тапа нажмите кнопку ещё раз.
5. Дождитесь локального подтверждения, полностью закройте Chrome, оставив сеть выключенной.
   Откройте тот же URL/ярлык, разблокируйте фразой. Должны сохраниться ответы, описания,
   оба фото и их ID. Для чтения серверный вход/интернет не нужны.
6. «Завершить и поставить в очередь». Получите **«Ожидает отправки»**. Ответы/фото/ID
   теперь зафиксированы, автоматическое редактирование очереди запрещено. Можно снова
   закрыть браузер офлайн: после разблокировки очередь должна остаться той же.
7. Включите сеть. «Отправить / проверить receipt». При истёкшей сессии появится **«Ошибка»**
   с просьбой войти тем же инспектором. Войдите и повторите. Вход другим аккаунтом не должен
   отправлять очередь; локальная копия остаётся у прежнего инспектора.
8. Во время отправки — **«Отправляется»**. Сначала проверяются сессия/права/назначение и receipt,
   затем фото с сохранёнными UUID/SHA-256, затем один batch: акт + нарушения + завершение
   выезда с исходным expectedVersion. После подтверждения — **«Принято сервером»**.
9. Повторите кнопку и перезапустите браузер. Новых актов/нарушений/фотографий быть не должно;
   после офлайн-перезапуска принятый receipt и локальная копия остаются доступны.
10. На ПК в **другом профиле** Chrome откройте корень того же стенда
    (например `https://192.168.1.20:8445/`), войдите `manager` из нового accounts-файла.
    В плане выезд завершён, связан один акт; в нём два нарушения, в карточках доступны фото
    и история. Не используйте существующую установку на 8003 для этой проверки.

Для конфликта используйте отдельный свежий стенд: после подготовки/офлайн-завершения
руководитель в другом профиле изменяет цель или дату выезда и сохраняет. Синхронизация
должна показать **«Конфликт»**, не загружая фото и не перезаписывая новый план. Локальные
ответы/фото/очередь сохраняются; можно скачать **только зашифрованную копию** для сохранности.
Не создавайте новую операцию/новый выезд для обхода конфликта: сначала нужна ручная сверка.
Автоматический импорт экспортированной копии и GUI разрешения конфликтов в MVP не включены.

Потеря ответа после commit воспроизводится автоматически контролируемым сетевым перехватом
в тестах, а не обещанием поймать точный момент переключателем телефона. Физическое отключение
сети во время «Отправляется» также должно оставлять очередь: повтор проверяет receipt,
а не меняет mutationId. На случайно выбранном моменте commit может ещё не произойти —
важны сохранённые ID и отсутствие дублей, а не конкретное число повторных сетевых запросов.

## Контракт и ограничения

- Одновременно один локальный профиль/вкладка и один выезд. Нет фоновой отправки:
  после восстановления сети нужна кнопка в разблокированном экране.
- Не более 20 фото, по одному на пункт; новые снимки не заменяют прежние автоматически.
  До 98 нарушений в batch (ещё две операции — акт/выезд). Пакет этапа 1 — до 24 часов.
- Если план изменится уже после загрузки фото, сервер отклонит весь batch по версии;
  ранее загруженные фото могут остаться без акта. Они и локальные копии не удаляются
  автоматически. В тесте этого случая получен стабильный 409 receipt без частичного акта.
- Все API прежние; дополнительно необязательные заголовки `X-KSU-Expected-User` и
  `X-KSU-Offline-Deployment` только сужают права и блокируют смену cookie/стенда во время
  отправки. Активная сессия, CSRF, ACL, immutable акты, expectedVersion и серверные проверки
  этапа 1 сохраняются. Клиент не назначает себе права и не обходит TTL.
- Пакет и очередь, фото и receipts хранятся шифрованно; пароль/CSRF не пишутся в IndexedDB,
  API-ответы не попадают в Cache API. Service Worker управляет только `/offline-visit/`.
- Подтверждения фото/акта записываются локально до следующего шага. При прерывании/закрытии
  сохраняется точное тело batch и IDs, повтор начинает с receipts. Даже уже загруженные фото
  остаются локально; нет автоматического удаления черновиков/подтверждённых данных.
- Истечение сессии/отзыв доступа не удаляют локальную копию. Но отправка блокируется.
  Скачанный пакет нельзя удалённо стереть с отключённого телефона.
- Не гарантируются последние **неподтверждённые** символы при OS-kill/поломке диска,
  browser eviction или ручной очистке storage. Ошибка IDB/квоты явно показывается, очередь
  при ней не фиксируется; предыдущая подтверждённая копия остаётся. После восстановления
  места повторите «Сохранить». Автоблокировка после ошибки сохраняет прежнюю подтверждённую
  копию, не обещая сохранность неподтверждённых правок. Фразу/зашифрованный экспорт хранить отдельно.
- Физическая камера, Android Back, доверие CA и реальное управление памятью Android
  требуют ручной приёмки владельца. Cloud-тесты не заявляют съёмку настоящим объективом.
- Серверный экран включается только явным `KSU_OFFLINE_VISIT_LAB_ID` стенда. Обычный запуск
  API не публикует экран. Никакого обновления рабочей PostgreSQL до v3 не выполняется;
  автоматические PG-тесты используют новые одноразовые TLS-кластеры.

## Автоматическое воспроизведение разработчиком

```sh
python -m pip install -r requirements-dev.txt
python -m playwright install chromium
python -m tests.offline_stage2 --backend sqlite
python -m tests.offline_stage2 --backend postgres
python -m unittest tests.test_offline_stage2_server -v
python -m tests.offline_stage1_environment --output var/stage2-checks
docker build -f Dockerfile.postgres -t ksu-postgres:stage2-test .
python -m tests.offline_stage2_container --image ksu-postgres:stage2-test
```

Browser tests используют persistent Chromium, настоящий сервер и настоящие транзакции,
закрывают браузер/открывают профиль без сети, перехватывают ответ **после** успешного POST
к реальному API и сравнивают fingerprints всех бизнес-таблиц после receipt-recovery.
Проверяются 2 фото/2 нарушения/1 акт/1 завершение, сессия, другой аккаунт, смена cookie после
preflight, конфликт/отзыв прав до загрузки фото, контролируемый отказ IDB, fallback камеры.
Контейнерный probe проверяет whitelist mounts, доверенный HTTPS/Secure cookie и restart без reseed.
Никаких БД/паролей/книг/копий в GitHub-артефакты не загружается.

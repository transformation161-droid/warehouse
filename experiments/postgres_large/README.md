# Приёмка большого реестра PostgreSQL — Issue #20

Локальный Docker, без облачных API. Из корня репозитория, Python 3.12+, Docker и OpenSSL:

```sh
python -m pip install -r requirements-dev.txt
docker build -f Dockerfile.postgres -t ksu-postgres:test .
python -m experiments.postgres_large.run --image ksu-postgres:test --output "$PWD/var/postgres-large"
```

Образ должен быть заранее доступен. Runner создаёт временную Docker-сеть, два отдельных PostgreSQL 17
с TLS verify-full и контейнер приложения/генератора/HTTP-клиента. **Каждый контейнер: 0,5 CPU, 1 ГиБ,
без swap.** Это три отдельных квоты, не обещание разместить всё в суммарном 1 ГиБ. На приложении
read-only root и /tmp 32 МиБ; большие рабочие файлы находятся на дисковом томе `/out`, не в tmpfs.
Роль runtime не владеет схемой и не имеет BYPASSRLS. Backup работает отдельной read-only ролью.

Книги ровно 18 000 000 и 30 000 000 байт, только вымышленные данные. Дополнительная независимая
18-МБ книга даёт накопленный реестр 22 189 строк при неизменном cap 268 435 456 байт. Сверяются
все 17 полей каждой строки, исходные ячейки/стили, ведущие нули, длинные комментарии, кэш формул,
четыре десятичных знака, нулевые значения и все пять количественных/денежных показателей.
Ожидаемые SHA и суммы вычисляет генератор независимо от импортера.

Есть полный HTTP upload/preview/commit/repeat, запрет чужого объекта, SQL RLS, ограниченные страницы,
весь журнал по 100 строк, потоковый CSV, обычные отчёты CSV/XLSX/PDF, фото и конфликты версий.
Две HTTP-копии сверяются по SHA и fingerprint всех бизнес-таблиц; вторая восстанавливается в новую БД
на другом PostgreSQL. После restore проверяются все строки/суммы/журнал/роли/экспорт, отозванная
сессия, новый импорт, редактирование выезда и новая HTTP-копия восстановленной БД.

Отказы: cap в обоих порядках 18→30 / 30→18 и после накопления; исключение БД на строке Excel 500
с полным откатом; убийство только дочернего импортера SIGKILL; уменьшенный до 1 с timeout и повтор
после перезапуска. **Настоящий kernel OOM намеренно не вызывается**: SIGKILL проверяет симптом
внезапной смерти worker, а counters/exit state отдельно фиксируют фактические OOM. Это не проверка
автоматического перезапуска всего контейнера провайдером.

Итоги: `postgres-large-metrics.json`, `postgres-large-db-resources.json`, `postgres-large-container.json`,
`postgres-large-log.txt`. Только эти верхнеуровневые файлы допустимы в GitHub artifacts. Не публиковать
содержимое временных вложенных каталогов. При обычном выходе книги/БД/дампы/секреты удаляются,
Docker-ресурсы снимаются в finally; после аварии ОС рабочий каталог нужно удалить локально.

RAM замеряется через cgroup v2 раз в 0,5 с (anon, file cache, total и kernel memory.peak), PG — раз в
секунду. Пики могут приходиться на разные моменты, складывать их нельзя. CPU — фактически потреблённые
секунды и throttling. Диск — логические размеры файлов, не обещание фактических блоков/тарифа.
Статистика WAL относится ко всему временному кластеру: в нём несколько изолированных тестовых БД.
Генератор и HTTP-клиент включены в квоту приложения, поэтому это консервативная общая оценка стенда.

Ограничение новых SHA/логических версий зафиксировано в отдельном синтетическом probe и [#21](https://github.com/transformation161-droid/warehouse/issues/21).
KPI из #15 здесь не реализуются. Отчёт и расчёт вместимости: [POSTGRESQL_LARGE_ACCEPTANCE.md](../../docs/POSTGRESQL_LARGE_ACCEPTANCE.md).

# ИНСТРАКТ · КСУ Контроль — совместный демонстрационный пилот

Сохранён русскоязычный интерфейс v1.1: объекты, проверки, план выездов, нарушения, инвентаризации, аналитика и недельная сводка. Два независимых аккаунта работают через локальный API с одной базой. **Все вводимые данные должны быть тестовыми. Внешние интеграции не подключены.**

Начните с [README_START.txt](README_START.txt). Результаты аудита и границы текущей версии: [docs/AUDIT.md](docs/AUDIT.md). Для администратора: [docs/DEPLOY.md](docs/DEPLOY.md).

Интернет-пилот задачи №4 подготовлен для **Amvera**, лимит до 500 ₽/30 дней: [конфигурация и статус](docs/AMVERA.md). Платный запуск требует отдельного подтверждения; публичный URL ещё не создан. Oracle не используется.

## Запуск на компьютере

Нужен Python 3.12+ и доступ к установке Python-пакетов. Откройте терминал в папке проекта.

**Linux / macOS:**

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m server init-demo --generate
.venv/bin/python -m server run
```

**Windows (PowerShell):**

```powershell
py -m venv .venv
.venv\Scripts\python -m pip install -r requirements.txt
.venv\Scripts\python -m server init-demo --generate
.venv\Scripts\python -m server run
```

Откройте в браузере адрес `http://localhost:8000`. Команда `init-demo` выполняется **только один раз**: создаёт пустую общую базу с демонстрационными объектами и чек-листом, а также два аккаунта. Логины и сгенерированные пароли находятся в локальном файле `var/demo-accounts.txt`. Файл исключён из Git. Пароли не встроены в код. Чтобы задать свои тестовые пароли вместо генерации, выполните `init-demo` без `--generate`.

Повторный запуск: только `.venv/bin/python -m server run` (Windows: `.venv\Scripts\python -m server run`). Для остановки нажмите Ctrl+C. Данные находятся в `var/ksu.sqlite3`, сохраняются после остановки и общие для обоих аккаунтов. Прямое открытие `index.html` и `python -m http.server` для совместной версии не подходят.

PDF требует шрифт DejaVu Sans на Linux: `/usr/share/fonts/truetype/dejavu/DejaVuSans.ttf` (пакет `fonts-dejavu-core`). На Windows/macOS используйте «PDF / печать» браузера; нативный серверный PDF в этой версии ориентирован на Linux.

## Проверка без программирования

1. Откройте приложение в обычном окне браузера и войдите как **manager**. В приватном окне или другом браузере войдите как **inspector**. Используйте пароли из локального файла.
2. Руководитель: «План выездов» → «Запланировать выезд» → «ДЕМО · Нова», дата, цель «ДЕМО · Проверить маркировку» → сохранить.
3. Исполнитель: откройте «План выездов». Через несколько секунд появится тот же выезд. Нажмите «Проверить», заполните все пункты, у одного выберите «Нарушение», опишите его и добавьте тестовое фото. Сохраните.
4. Руководитель увидит «Выполнен» и «Акт проверки». В «Нарушения» появится замечание. Обмен файлами для синхронизации не нужен.
5. Исполнитель: откройте замечание, выберите «Устранено», напишите результат и загрузите фото-подтверждение. Руководитель увидит изменение и историю с автором и временем UTC.
6. «Инвентаризации» → «Шаблон CSV». Заполните тестовые строки, затем «Импорт CSV / XLSX» → выберите файл → сопоставьте колонки → «Проверить файл» → «Сохранить импорт». Повторная загрузка того же файла не добавит строки.
7. «Аналитика и отчёты»: выберите источник, период, объект и группировку; скачайте CSV, XLSX с диаграммой или PDF. «Недельная сводка» печатается отдельно, «CSV недели» выгружает календарную неделю.
8. Руководитель может открыть пересчёт → «Стадия расхождений» и указать основание решения. **Первичные недостачи не являются установленным ущербом.**
9. «Настройки» → «Журнал изменений»: руководителю доступна история всей базы, исполнителю — собственных операционных записей.

На смартфоне применяется то же меню через кнопку в левом верхнем углу. Для физического телефона нужен согласованный HTTPS-сервер: `localhost` телефона не является компьютером. Мобильная вёрстка и независимая сессия проверяются автоматическим тестом при ширине 390 px.

## Права и сохранение

- Руководитель: справочники, план, все доступные записи, подтверждение стадий, отчёты и журнал.
- Исполнитель: просмотр назначенных объектов и их записей, создание проверок/замечаний/пересчётов, изменение собственных операционных записей, выполнение назначенных выездов. Нельзя изменить роль, справочники, чужие записи или подтвердить финансовую стадию.
- Завершённый акт нельзя редактировать ни одной роли. Он хранит снимок вопросов.
- Изменения записываются атомарно с историей. Устаревшая версия получает конфликт; чужая работа не перезаписывается.
- При потере связи отправляемый запрос сохраняется на устройстве по аккаунту. После восстановления связи нажмите «Повторить». При конфликте скачайте свою копию, отмените отправку и сравните актуальную запись.
- Черновик чек-листа сохраняется на устройстве раз в секунду и восстанавливается после перезагрузки для того же аккаунта. Остальные незавершённые формы пока хранятся в памяти до нажатия «Сохранить». Не очищайте данные браузера с неподтверждёнными изменениями.
- Доступ к фото требует действующей сессии и назначения объекта. Ссылки не публичны. Исходные EXIF-метаданные не сохраняются.

## Проверки для разработчика

```sh
.venv/bin/python -m pip install -r requirements-dev.txt
.venv/bin/python deploy/get_caddy.py --output /tmp/ksu-caddy
CADDY_BIN=/tmp/ksu-caddy .venv/bin/python -m unittest discover -s tests -v
.venv/bin/python smoke_test.py
.venv/bin/python v11_flow_test.py
node --check app.js
node --check sync.js
```

Браузерным тестам нужен Chromium (`CHROMIUM_PATH` позволяет задать путь). На этой среде используется `/usr/bin/chromium`. Альтернатива: `.venv/bin/python -m playwright install chromium`. Тесты используют временные БД и вымышленные аккаунты; случайные пароли генерируются в памяти при запуске и не сохраняются в исходниках. После тестов временные БД удаляются. Снимки сохраняются в `/tmp/ksu_desktop.png` и `/tmp/ksu_mobile.png`.

## Структура

- `app.js`, `styles.css`, `index.html` — сохранённый интерфейс и клиентские сценарии;
- `sync.js` — сессии, API, синхронизация, восстановление запросов, импорт и серверные выгрузки;
- `server/` — API, контракты, проверка прав, схема общей БД, аудит, фото, импорт и отчёты;
- `tests/`, `smoke_test.py`, `v11_flow_test.py` — API и браузерные проверки;
- `deploy/` — примеры службы, HTTPS-прокси и ежедневной копии;
- `schema.sql` — исторический проект Supabase, **не действующая миграция и не применять**;
- `CODEX_HANDOFF.md`, `CODEX_START.md`, `START_HERE.txt` — исходные документы прототипа; текущий статус указан здесь и в аудите.

Перенос на React/TypeScript, PostgreSQL, корпоративный SSO, сохранённые шаблоны отчётов, частичные финансовые решения и внешние интеграции остаются отдельными следующими этапами. Текущая версия — локальный тестовый пилот, не опубликованная корпоративная система.
